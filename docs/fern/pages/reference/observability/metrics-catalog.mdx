Dynamo exposes metrics in Prometheus exposition format at the `/metrics` HTTP endpoint. All Dynamo-generated metrics use the `dynamo_*` prefix and carry the hierarchy labels documented in [Metric Labels](metric-labels.mdx). This page is the field catalog; for setup and dashboards see the [Metrics guide](../../cli/operations/observability.mdx#view-metrics-and-dashboards).

## Metric types

The `type` on each field below is a [Prometheus metric type](https://prometheus.io/docs/concepts/metric_types/):

- **counter** — a cumulative value that only increases (or resets to zero on restart), e.g. total requests.
- **gauge** — a single value that can go up or down, e.g. in-flight requests.
- **histogram** — samples observations into configurable buckets and exposes `_bucket`, `_sum`, and `_count` series, e.g. request duration. Labeled histograms/counters/gauges register a metric *family*, not one series. The frontend latency and sequence-length histograms take their bucket ranges from environment variables — see [Histogram buckets](../components/frontend-configuration.mdx#histogram-buckets).

<Info>
  Labeled metrics (`HistogramVec`, `CounterVec`, `GaugeVec`) register a metric *family*, not individual time series. For request-populated metrics, a series for a given label combination appears at `/metrics` only after the first matching request. Other families create or remove series from runtime state; their entries below document those semantics.
</Info>

## Where each family is exposed

| Family | Emitted by | Scrape endpoint |
|--------|------------|-----------------|
| `dynamo_frontend_*` | HTTP frontend (`python -m dynamo.frontend`) | `/metrics` on `DYN_HTTP_PORT` (default 8000) |
| `dynamo_component_*` | Backend workers, standalone router | `/metrics` on `DYN_SYSTEM_PORT` (must be set) |
| `dynamo_router_overhead_*` | Frontend with KV routing | `/metrics` on `DYN_HTTP_PORT` |
| `dynamo_epp_*` | Endpoint picker (Gateway API Inference Extension routing) | `/metrics` on `DYN_EPP_METRICS_PORT` (default 9090) |
| `dynamo_operator_*` | Kubernetes operator | See [Operator Metrics](operator-metrics.mdx) |

Backend workers expose `dynamo_component_*` only when `DYN_SYSTEM_PORT` is set (disabled by default; the Kubernetes operator typically sets `9090`, local examples use `8081`). See [Environment Variables](environment-variables.mdx#system-and-metrics).

Engine pass-through metrics (`vllm:*`, `sglang:*`, `trtllm_*`) are emitted by the backend engines themselves and are cataloged separately — see [Metrics Comparison](metrics-comparison.md). NIXL transfer metrics are exposed on their own port and owned by the [upstream NIXL project](https://github.com/ai-dynamo/nixl/blob/main/docs/telemetry.md).

## Frontend metrics

Emitted by the HTTP frontend at `/metrics` on port 8000 by default. Most carry a `model` label. For endpoints that canonicalize aliases, that label holds the primary served model name — the first `--served-model-name` value — so a request sent to an alias is counted under the primary. A name the frontend has not registered is counted under `unknown_model`.

<ParamField path="dynamo_frontend_active_requests" type="gauge">
  Requests currently being handled by the frontend, from HTTP handler entry until the response stream completes. The top-level in-flight count with no stage breakdown.
</ParamField>

<ParamField path="dynamo_frontend_stage_requests" type="gauge">
  Requests currently in a given frontend pipeline stage. Labeled by `stage` and `phase` — see [Stage values](metric-labels.mdx#stage-values) and [Phase values](metric-labels.mdx#phase-values).
</ParamField>

<ParamField path="dynamo_frontend_inflight_requests" type="gauge" deprecated={true}>
  Inflight requests. Kept for backward compatibility; prefer `dynamo_frontend_active_requests`, which has identical semantics with a clearer name.
</ParamField>

<ParamField path="dynamo_frontend_queued_requests" type="gauge" deprecated={true}>
  Requests in the HTTP processing queue. Kept for backward compatibility; the "waiting for first token" window is now the sum of `dynamo_frontend_stage_requests` across the `preprocess`, `route`, and `dispatch` stages.
</ParamField>

<ParamField path="dynamo_frontend_awaiting_first_token_requests" type="gauge">
  **Experimental.** Admitted requests that have not produced an output token yet: being tokenized, queued, routed, or prefilled. Requests to endpoints that never stream tokens (embeddings, images, videos, tensors) stay here until they finish. Unit: requests. Labeled by `model`. Requests producing output tokens are `clamp_min(dynamo_frontend_active_requests - dynamo_frontend_awaiting_first_token_requests, 0)`; the clamp covers the two gauges being sampled a moment apart.
</ParamField>

<ParamField path="dynamo_frontend_inflight_input_tokens" type="gauge">
  **Experimental.** Known prompt tokens of in-flight requests. Unit: tokens. Labeled by `model` and `state`: `awaiting_first_token` (the requests in `dynamo_frontend_awaiting_first_token_requests`) or `generating`. Summing over `state` gives all in-flight prompt tokens. A request still being tokenized contributes zero.
</ParamField>

<ParamField path="dynamo_frontend_input_tokens_total" type="counter">
  **Experimental.** Prompt tokens of admitted requests, counted at tokenization, including requests that fail or are cancelled before producing output. Unit: tokens. Labeled by `model`. Unlike the sum of `dynamo_frontend_input_sequence_tokens`, which is observed at the first output token, this counts every admitted request when it is tokenized.
</ParamField>

<ParamField path="dynamo_frontend_disconnected_clients" type="gauge">
  Number of disconnected clients.
</ParamField>

<ParamField path="dynamo_frontend_input_sequence_tokens" type="histogram">
  Input sequence length in tokens.
</ParamField>

<ParamField path="dynamo_frontend_cached_tokens" type="histogram">
  Cached tokens (prefix cache hits) per request.
</ParamField>

<ParamField path="dynamo_frontend_tokenizer_cache_hits_total" type="counter">
  L1 tokenizer prefix-cache hits across all models. One outcome is recorded per encode operation or batch item.
</ParamField>

<ParamField path="dynamo_frontend_tokenizer_cache_misses_total" type="counter">
  L1 tokenizer prefix-cache misses across all models.
</ParamField>

<ParamField path="dynamo_frontend_tokenizer_cache_cached_tokens_total" type="counter">
  Tokens returned from the L1 tokenizer prefix cache. Labeled by `model`.
</ParamField>

<ParamField path="dynamo_frontend_tokenizer_cache_uncached_tokens_total" type="counter">
  Tokens freshly encoded after an L1 tokenizer cache lookup. Labeled by `model`.
</ParamField>

Use this PromQL expression to calculate the five-minute token reuse ratio by model:

```promql
sum by (model) (rate(dynamo_frontend_tokenizer_cache_cached_tokens_total[5m]))
/
(
  sum by (model) (rate(dynamo_frontend_tokenizer_cache_cached_tokens_total[5m]))
  +
  sum by (model) (rate(dynamo_frontend_tokenizer_cache_uncached_tokens_total[5m]))
)
```

The ratio is defined only when the model has an active L1 cache and observed tokens. Partial hits increment both token counters. When the cache is disabled with `DYN_TOKENIZER_CACHE=0`, the per-model series are never created, so they are absent from the scrape rather than reported as zero; detect that state with `absent()`, since a `== 0` comparison never matches a missing series. Only the literal value `0` disables the cache; values such as `false` or `off` leave it enabled. With the cache enabled, the counters remain zero when encoding fails or the tokenizer has no registered special-token boundaries.

<ParamField path="dynamo_frontend_inter_token_latency_seconds" type="histogram">
  Inter-token latency in seconds.
</ParamField>

<ParamField path="dynamo_frontend_output_sequence_tokens" type="histogram">
  Output sequence length in tokens.
</ParamField>

<ParamField path="dynamo_frontend_output_tokens_total" type="counter">
  Total output tokens generated.
</ParamField>

<ParamField path="dynamo_frontend_request_duration_seconds" type="histogram">
  End-to-end LLM request duration in seconds.
</ParamField>

<ParamField path="dynamo_frontend_requests_total" type="counter">
  Total LLM requests.
</ParamField>

<ParamField path="dynamo_frontend_time_to_first_token_seconds" type="histogram">
  Time to first token in seconds.
</ParamField>

<ParamField path="dynamo_frontend_ttft_stage_seconds" type="histogram">
  Exclusive wall-clock contributions to frontend Time To First Token (TTFT), in seconds. Labeled by
  `model`, `stage`, and `phase`. Enabled by default. Every request in the enabled cohort that records
  total TTFT records every legal stage/phase pair, including zeros for unused stages. See
  [TTFT stage durations](#ttft-stage-durations).
</ParamField>

<ParamField path="dynamo_frontend_ttft_detail_degraded_total" type="counter">
  Requests whose first-token breakdown is entirely `unclassified` because reliable detail is
  unavailable. Labeled by a fixed `reason`; not labeled by model or request ID. Observed once per
  request at the first token in `metrics` and `both` modes.
</ParamField>

<ParamField path="dynamo_frontend_ttft_detail_coarse_total" type="counter">
  First-token requests with an opaque operation, unsupported worker clock, or missing finer coverage. Labeled by a
  fixed `reason`; not labeled by model or request ID. Observed once per request in `metrics` and
  `both` modes. See [coverage states](#ttft-stage-durations).
</ParamField>

<ParamField path="dynamo_frontend_ttft_detail_unexpected_overlap_total" type="counter">
  First-token requests with overlapping independent frontend stages. Has no labels. The fixed
  attribution order still preserves the total. Observed at most once per request in `metrics` and
  `both` modes, regardless of how many overlaps occurred.
</ParamField>

### TTFT stage durations

`dynamo_frontend_ttft_stage_seconds` partitions the same interval as
`dynamo_frontend_time_to_first_token_seconds`: from the HTTP request metrics start to the first
observed nonzero output token count. The total and all contributions share that first-token
timestamp. Durations are clipped to that interval, concurrent work is counted once, and gaps are
assigned to `frontend_overhead`. The contributions sum to the request's total TTFT exactly in
integer durations, subject to floating-point rounding when exported. If timing data is invalid or
exceeds its bound, the whole interval is assigned to `unclassified` instead.

| `stage` | `phase` | Measured interval |
|---------|---------|-------------------|
| `frontend_overhead` | `""` | Time outside instrumented stages, including request setup and gaps between stages |
| `preprocess` | `""` | Native or Python chat preprocessing, including process-pool dispatch and IPC when used, excluding separately attributed nested stages |
| `preprocess_queue` | `""` | Waiting for the Python preprocessing concurrency semaphore |
| `template_render` | `""` | Template rendering where the renderer exposes a separate call |
| `tokenize` | `""` | Tokenization where the tokenizer exposes a separate call |
| `template_tokenize` | `""` | Opaque third-party calls that combine rendering and tokenization; never recorded alongside separate timings for the same call |
| `structural_tag_build` | `""` | Building and serializing structural-tag or guided-decoding constraints |
| `multimodal_prepare` | `""` | Frontend multimodal input preparation, including media processing and shared-memory or NIXL sender preparation |
| `mm_routing_build` | `""` | Building multimodal routing information from prepared inputs |
| `route` | `prefill`, `decode`, `aggregated` | Worker selection, scheduling, and selection tracking for KV and built-in routing policies |
| `dispatch_prepare` | `prefill`, `decode`, `aggregated` | Work after KV worker selection and before backend dispatch; zero on paths without a separate preparation interval |
| `dispatch` | `prefill`, `decode`, `aggregated` | The existing dispatch boundary to the first backend response, excluding separately attributed preparation |
| `first_token_wait` | `prefill`, `decode`, `aggregated` | First backend response to its first nonempty token output; zero when the first response contains tokens |
| `backend_overlap` | `prefill_decode` | Concurrent prefill and decode backend waits, counted once |
| `first_token_postprocess` | `""` | First decode or aggregated backend token to the HTTP first-token observation, including detokenization, parser buffering, and delivery |
| `unclassified` | `""` | The entire TTFT when bounded collection cannot provide trustworthy attribution |

Only these legal pairs are exported; the metric does not create a Cartesian product of all stages
and phases. The registry also defines parent stages, attribution priority, and Python availability.

The existing metric contracts remain unchanged. They answer different questions from this request
view:

| Existing view | Reuse in TTFT detail | Preserved contract |
| --- | --- | --- |
| `stage_requests{stage="route",phase=...}` | Shared selection lifecycle and canonical `route` stage name | The KV gauge still ends after selection/tracking. Preparation has its own detail interval. |
| `stage_requests{stage="dispatch",phase=...}` | Same dispatch entry and first-response event | The gauge still starts before KV dispatch preparation. The detail view subtracts the nested `dispatch_prepare` contribution without moving that boundary. |
| `stage_requests{stage="preprocess",phase=""}` | Shared lifecycle where boundaries match | Original gauge scopes and cleanup on errors or cancellation remain unchanged. |
| `template_seconds`, `tokenize_seconds` | Existing native timing pairs feed `template_render` and `tokenize` | Inclusive operation durations retain their boundaries and successful-operation sample populations. |
| `stage_duration_seconds{stage=...}` | Native chat `preprocess` reuses the same timing result | Existing stage values, buckets, and samples remain unchanged; no `model` or `phase` label is added. |
| `time_to_first_token_seconds{model=...}` | Same start, first-token observation, and request population | Existing total TTFT remains enabled in all modes. |

The gauges count concurrent requests; they do not measure duration. Existing operation histograms
remain inclusive and can record multiple samples per HTTP request, including retries according to
their existing rules. The detail histogram removes overlap, clips at the first HTTP token, and
records zero for unused stages. Summing operation histograms would neither remove overlap nor
preserve the total-TTFT denominator. Existing dashboards need no migration.

Python requests carry the optional timeline separately from the legacy request tracker. Enabling
detail does not create a tracker or add requests to existing router timing metrics.

The empty `phase` means the stage does not distinguish serving phases. `aggregated` identifies a
single worker serving both prefill and decode. Each dispatch snapshots its phase; later tracker
changes cannot relabel it. `backend_overlap` applies when prefill and decode each have an active
`dispatch` or `first_token_wait`, after higher-priority frontend work is removed.

The fixed attribution order, from highest to lowest priority, is:

1. `first_token_postprocess`.
2. `dispatch_prepare`, then `route`, with decode before prefill before aggregated within each.
3. `structural_tag_build`, `template_render`, `tokenize`, then opaque `template_tokenize`.
4. `mm_routing_build`, `multimodal_prepare`, `preprocess_queue`, then residual `preprocess`.
5. `backend_overlap`.
6. `first_token_wait`, then `dispatch`, for decode, prefill, then aggregated.
7. `frontend_overhead` for uncovered time.

This policy attributes observable frontend work ahead of simultaneous backend waits. It is not a
distributed critical-path calculation. Repeated intervals of the same stage form a union, and
sequential retry intervals remain in the request. Unexpected overlaps between independent frontend stages
use the same fixed priority and increment a diagnostic count. When an attempt is aborted or retried
before HTTP observes a token, its postprocessing interval closes so the replacement attempt keeps
its own route and backend contributions. Tokens held and discarded by migration do not freeze
HTTP TTFT.

The metric is enabled on the frontend's existing `/metrics` endpoint by default with
`DYN_FRONTEND_TTFT_DETAIL=metrics`. Use `both` to add per-request logs. The `metrics` and `both` modes
collect regardless of the log filter. In `logs` mode, collection also requires the
`dynamo_frontend::ttft` DEBUG target to be enabled. With `off`, or `logs` with that target disabled,
requests allocate no detail timeline or histogram handles, read no additional stage clocks, and
skip Python stage calls and pool timing results. Fixed enablement checks remain; this is not a claim
of zero CPU overhead. The setting is resolved at startup; CLI
`--ttft-detail` takes precedence over the environment. See
[TTFT Detail](../components/frontend-configuration.mdx#ttft-detail). The SGLang and vLLM Python chat processors and native Rust
preprocessor provide preprocessing timings. Chat and text completions carry the HTTP timing context
through the in-process routing host, including KV, round-robin, random, direct, and other built-in
policies. These paths record worker selection,
backend waits, and first-token postprocessing. The `route` label also covers the built-in
policies. Batched text completion children share the parent HTTP timeline, so overlapping child
work is counted once.

The timing context stays within one frontend process; a standalone router reached over the
network does not receive it. Other HTTP endpoints and uninstrumented operations retain their time
in `frontend_overhead`. A large value does not establish that the frontend consumed that time on
CPU.

Native Rust rendering and tokenization use their existing separate operation clocks. Python paths
use separate boundaries only where the backend API exposes them: SGLang's explicit text encoder
and tokenizer can be measured independently, while fused `apply_chat_template` calls remain
`template_tokenize`. A vLLM renderer that returns token IDs is also opaque; a renderer that returns
text uses `template_render`, followed by a separately measured tokenizer call. Rendering may fetch
media, so renderer time is not necessarily pure template computation. Later media processing and
transfer preparation contribute to `multimodal_prepare`. The frontend never repeats tokenization
to manufacture a split.

The SGLang process pool returns a versioned batch with fixed stage IDs and integer nanosecond
intervals. Supported same-host monotonic clocks are checked against the parent's submission and
completion window. The parent reads one Python timestamp and imports elapsed ages in one PyO3
call; Python monotonic values are never subtracted from a Rust `Instant` epoch. Re-anchoring still
has a bounded call-delay uncertainty. Unsupported clock domains retain the reliable outer
`preprocess` interval and report coarse coverage; remote backend clocks are not aligned. Backend
stages include transport, scheduling, and processing, not isolated GPU compute or KV transfer. A
control response ends `dispatch` without ending `first_token_wait`.

Collection is bounded to 256 intervals per request and 64 per worker batch. Once the HTTP first
token freezes the result, late intervals and guard cleanup cannot alter it. Normal later calls
check the frozen flag before reading the clock or locking; a call racing with freeze may already
have started. No detail interval is recorded for every output token.

Coverage has three fixed states:

| State | Meaning | Attribution |
| --- | --- | --- |
| `complete` | All declared measurable boundaries are valid; this does not mean every internal function is measured | Normal exclusive contributions |
| `coarse` | A known opaque call or unsupported clock prevents finer detail, but the outer window remains reliable | `template_tokenize` or parent residual |
| `degraded` | An interval limit or invalid timing data makes the detailed partition unreliable | Full TTFT in `unclassified`, all other contributions zero |

Degradation never fabricates frontend CPU time or drops the total-TTFT sample. Existing active
guards can still close safely when a limit is reached. Diagnostics use fixed reason values;
request IDs, attempt IDs, prompt text, and tool schemas are never metric labels. The
[`reason` label reference](metric-labels.mdx#metric-specific-labels) lists the fixed values.
`missing_timeline` makes an enabled request with no attached timeline visible as degraded,
preserving its stage sample count. Opaque `template_tokenize` intervals mark coverage coarse.

When metrics are enabled, every legal pair for each model has the same sample count and request
population as total TTFT on that enabled frontend. Requests that end, fail, or are canceled before the first output token produce neither total
nor stage TTFT observations. Later tokens do not add TTFT observations. Labels never contain
request IDs. See [Per-Request First-Token Log](logging.mdx#per-request-first-token-log) for the
corresponding per-request event.

For a stacked chart of mean stage durations in milliseconds, use:

```promql
1000 * (
  sum by (model, stage, phase) (
    rate(dynamo_frontend_ttft_stage_seconds_sum[$__rate_interval])
  )
  /
  sum by (model, stage, phase) (
    rate(dynamo_frontend_ttft_stage_seconds_count[$__rate_interval])
  )
)
```

Set the legend to `{{model}} / {{stage}} / {{phase}}` and select one model per stacked panel. Apply
the same deployment selectors when comparing with mean total TTFT:

```promql
1000 * (
  sum by (model) (
    rate(dynamo_frontend_time_to_first_token_seconds_sum[$__rate_interval])
  )
  /
  sum by (model) (
    rate(dynamo_frontend_time_to_first_token_seconds_count[$__rate_interval])
  )
)
```

Zero observations preserve the common denominator, so the sum of stage means matches mean total
TTFT over the same requests. Select the same enabled instances, model, and time window for both
queries; do not compare detail from a subset of instances with service-wide total TTFT. Stage P95
or P99 values are not additive: different requests can
determine each percentile, and unused stages contribute zero observations. Use total TTFT
percentiles separately to assess tail latency. A scrape overlapping metric updates or differing
series scrape histories can cause small temporary differences between the sums.

The default stage histogram has 26 finite buckets, including zero, plus `+Inf`. Set
`DYN_METRICS_TTFT_STAGE_MIN`, `DYN_METRICS_TTFT_STAGE_MAX`, and `DYN_METRICS_TTFT_STAGE_COUNT` before
frontend startup to customize the logarithmic boundaries. Bucket resolution affects percentile
estimates; `_sum` and `_count` retain the observed durations independently of the boundaries. See
[Histogram buckets](../components/frontend-configuration.mdx#histogram-buckets) for defaults,
validation, and cardinality considerations.

See [Request Migration Architecture](../../developer-guide/knowledge-base/concepts/fault-tolerance/request-migration-architecture.md) for the internals.

<ParamField path="dynamo_frontend_model_migration_total" type="counter">

<ParamField path="dynamo_frontend_model_migration_duration_seconds" type="histogram">

Counters for requests that end early: [cancellations](../../developer-guide/knowledge-base/concepts/fault-tolerance/request-cancellation-architecture.md) (the client or frontend aborts an in-flight request) and [rejections](../../kubernetes/fault-tolerance/request-rejection.md) (the Frontend sheds load with HTTP 529 by default when all workers are busy). <ParamField path="dynamo_frontend_model_cancellation_total" type="counter">

</ParamField>

<ParamField path="dynamo_frontend_model_rejection_total" type="counter">

</ParamField>

### Per-worker load and timing gauges

`dynamo_frontend_worker_*` gauges appear once workers register and begin serving. They live on the frontend's local registry (not component-scoped) and do **not** carry `dynamo_namespace` or `dynamo_component` labels. Frontend-only — not available on the standalone router. Labeled by `worker_id`, `dp_rank`, and `worker_type`.

At each HTTP scrape, these six gauges include only workers in the current committed router membership that pass hard availability checks, and only their current data-parallel (DP) ranks. The timing gauges also allow `dp_rank="none"` when the rank is unknown, provided the worker remains available. The `worker_type` label describes serving attribution: an Encode worker serving Chat/Completions reports its load and timing samples as `decode`, while the inventory metrics below retain its `encode` topology role. Removed or excluded workers disappear from the output; late request completions or load updates cannot restore their exposed series.

<ParamField path="dynamo_frontend_worker_active_decode_blocks" type="gauge">
  Active KV cache decode blocks per worker.
</ParamField>

<ParamField path="dynamo_frontend_worker_active_prefill_tokens" type="gauge">
  Active prefill tokens queued per worker.
</ParamField>

<ParamField path="dynamo_frontend_worker_active_requests" type="gauge">
  Active requests booked per worker, split by an additional [`request_phase`](metric-labels.mdx#metric-specific-labels) label. A request counts as `prefill` from booking until its worker returns the first output token, then as `decode` until it completes. Sum both phases for the worker's total concurrency. The count is the router's view, including requests booked by peer routers when router replica sync is enabled.
</ParamField>

<ParamField path="dynamo_frontend_worker_last_time_to_first_token_seconds" type="gauge">
  Last observed time to first token per worker, in seconds.
</ParamField>

<ParamField path="dynamo_frontend_worker_last_input_sequence_tokens" type="gauge">
  Last observed input sequence length per worker.
</ParamField>

<ParamField path="dynamo_frontend_worker_last_inter_token_latency_seconds" type="gauge">
  Last observed inter-token latency per worker, in seconds.
</ParamField>

### Router Worker Inventory

These frontend-only metrics describe each Frontend's independent view of normalized base model-card discovery and router admission. They do not report Kubernetes Pod existence, and LoRA overlays do not count as additional workers. Both metrics carry `model`, `target_namespace`, `target_component`, `target_endpoint`, and `worker_type` labels. The target labels identify the discovered serving endpoint.

Admission uses first-wins semantics within each Frontend's model and target group. The first observed checksum cohort remains the incumbent; later incompatible worker IDs are excluded individually and do not remove or replace it. If the incumbent cohort disappears, the next remaining cohort can become its successor after initialization.

<ParamField path="dynamo_frontend_router_workers" type="gauge">
  Number of unique physical worker IDs in a model and target group, labeled by `state`. DP ranks do not increase the count. The `available`, `pending`, and `excluded` states are disjoint; `discovered` is their sum. `available` requires successfully committed worker-set membership and current hard availability; `pending` means discovery has observed the worker but initialization has not completed; `excluded` means discovered but currently unavailable for routing.
</ParamField>

Hard availability uses the committed group's client and, when a prefill or encode hop targets that group, the hop's local availability. A matching hop that is still activating reports no available workers. If no hop targets the group, its own client availability applies. These counts describe individual worker groups; use `dynamo_frontend_model_ready` to check whether the frontend has a complete routable serving topology.

Each currently observed group emits all four counts, including zero values for states with no workers. When discovery withdraws a group after its last worker disappears, its count and per-worker state series disappear on the next scrape. Retired rolling-update namespaces are not retained as permanent zero-count groups. Groups never observed by that frontend also have no series. Do not aggregate these counts across Frontends as worker-global readiness; separate Frontends can choose different incumbents from the same discovered workers.

<ParamField path="dynamo_frontend_router_worker_state" type="gauge">
  One sample with value `1` for each discovered worker, additionally labeled by `router_worker_id`, `state`, and `reason`. The state is `available`, `pending`, or `excluded`. The sample changes with the worker's current state and disappears when discovery removes the ID.
</ParamField>

The bounded `reason` values describe the current admission or availability condition:

| Reason | Meaning |
|--------|---------|
| `none` | Available for routing |
| `initializing` | Waiting for initialization |
| `checksum_mismatch` | The individual worker's Model Deployment Card checksum differs from the incumbent; emitted only for rejected worker IDs |
| `materialization_failed` | Creating the serving configuration failed |
| `commit_blocked` | The serving configuration could not be committed |
| `invalid_config` | The discovered configuration is invalid |
| `unavailable` | Absent from the current availability view; includes local inhibition and other availability changes without identifying their exact cause |

When an incumbent is still initializing and an incompatible newcomer is discovered, counts are `discovered=2`, `available=0`, `pending=1`, and `excluded=1`. The incumbent carries `state="pending",reason="initializing"`; only the newcomer carries `state="excluded",reason="checksum_mismatch"`. Once the incumbent is healthy, the same group reports `discovered=2`, `available=1`, `pending=0`, and `excluded=1`. Rejection of the newcomer never makes the incumbent pending or excluded.

To detect an unexpected absence of workers, select one frontend, model, worker role, and the namespaces belonging to one deployment. The following expression alerts when the frontend is being scraped successfully but no selected group has a positive discovered-worker count. It handles both explicit zero counts and series disappearing after group withdrawal:

```promql
(up{job="<frontend-job>", instance="<frontend-instance>"} == 1)
unless on (job, instance)
(
  sum by (job, instance) (
    dynamo_frontend_router_workers{
      job="<frontend-job>",
      instance="<frontend-instance>",
      model="<model>",
      target_namespace=~"<deployment-namespace-pattern>",
      worker_type="<worker-role>",
      state="discovered"
    }
  ) > 0
)
```

Replace the selectors with your scrape labels and a namespace pattern that includes only the rolling versions of one deployment. Enable the rule only for deployments expected to have workers, and use an alert duration such as `for: 3m` to tolerate startup and brief rollout transitions. To alert when no selected worker is available for routing, use `state="available"` instead of `state="discovered"`. Monitor `up == 0` separately for frontend scrape failures. A raw `sum(...) == 0` expression does not match when all selected group series have disappeared.

Preserve `target_namespace` when diagnosing an individual namespace. Do not aggregate independent deployments or different frontend instances.

Inspect workers still discovered but excluded from routing:

```promql
dynamo_frontend_router_worker_state{state="excluded"} == 1
```

Scope these queries to the target frontend and deployment. Evaluate each Frontend separately because discovery order and first-wins admission can produce different incumbents. A missing series does not mean zero workers; check Prometheus `up` separately for scrape health. These metrics reflect updates after the frontend processes discovery and routing state changes, not at the instant a worker process terminates.

### KV-cache reuse telemetry

The cache reuse funnel shows how much of the incoming prompt could be reused, and how much the worker reports reusing. Each step counts tokens, not requests.

All metric names below start with `dynamo_component_router_`.

| Step | Meaning | Metric suffix |
| --- | --- | --- |
| **F0 — Incoming tokens** | Tokens received by the router. | `input_sequence_tokens_sum` |
| **F2 — Best available match** | Prefix the router estimates is cached on the best-matching eligible worker. | `kv_best_eligible_cached_prefix_tokens_total` |
| **F3 — Selected worker's match** | Prefix the router estimates is cached on the worker it chooses. | `kv_selected_cached_prefix_tokens_total` |
| **F4 — Reported reuse** | Tokens the worker reports reusing. Missing reports count as zero. | `kv_worker_reused_tokens_total` |

These counters need no enable flag.

Compare token increases over the same time window and matching KV-routing traffic. Use a long enough window: the steps are recorded at different times, and F4 depends on worker reports arriving after routing. Short windows may therefore compare different requests. Divide each step by F0 to express it as a percentage of incoming tokens.

vLLM, SGLang, and TensorRT-LLM workers report F4 on the final response chunk of each aggregated or prefill attempt, as `engine_data.kv_cache_hit` with `prompt_tokens` and `reused_tokens`. `reused_tokens` is the engine's per-request cached-token count, so it includes hits on host and storage tiers and KV connectors, the same tiers F2 and F3 count.

- Disaggregated decode attempts do not report, because each engine counts the KV transferred from the prefill worker as cached; read worker reuse from the `prefill` phase. The exception is a decode attempt that prefills locally under conditional disaggregation, which reports under `phase="decode"`.
- Attempts take their `phase` from the frontend's request tracker. A standalone router (`python -m dynamo.router`) does not set one, so all of its attempts are labeled `aggregated`.
- The router counts a report only when its `prompt_tokens` equals the routed prompt length. Engines count multimodal prompts after placeholder expansion, so a multimodal report counts only when the router also routed on expanded tokens; TensorRT-LLM does not report multimodal requests. F2 and F3 count expanded routing tokens while F0 counts the unexpanded prompt, so multimodal ratios to F0 can exceed 100%.
- With `n > 1`, vLLM and SGLang do not report. Later samples reuse the prompt blocks earlier samples just cached, vLLM keeps the first buffered sample's count when it merges outputs, and SGLang caches the prompt before running the samples.
- Engines recompute the last prompt token, so a full-prefix hit reports at least one token less than F3, and up to one block less for vLLM.
- Preemption, partial-block reuse in TensorRT-LLM, and KV loads that fail under a recompute policy can also make F4 differ from F3 when the router's estimate is accurate.

### Availability by configuration

Not all router metrics appear in every deployment. This matrix shows which groups are **registered** and **populated** in each configuration.

| Metric group | Frontend + KV (agg) | Frontend + KV (disagg) | Frontend + non-KV | Standalone router |
|---|---|---|---|---|
| `dynamo_component_router_*` | Registered and populated | Registered and populated | Registered, **always zero** | Populated (on `DYN_SYSTEM_PORT`) |
| `dynamo_router_overhead_*` | Registered and populated | Registered and populated | **Not registered** | **Not created** |
| `dynamo_frontend_router_queue_*` | Registered; populated when a CLI or policy-class queue threshold is set | Registered; populated when a CLI or policy-class queue threshold is set | **Not registered** | **Not created** |
| `dynamo_component_kv_cache_events_applied` | Populated when KV events received | Populated when KV events received | **Not registered** | Populated when KV events received |
| `dynamo_component_ckf_mutation_total` | Registered, **always zero** | Registered, **always zero** | **Not registered** | Registered, **always zero** |
| `dynamo_frontend_worker_*` | Registered and populated | Registered and populated (`worker_type` = `prefill`/`decode`) | Registered and populated (`worker_type` = `decode`) | **Not created** |

**Key:**

- **Registered and populated** — the metric appears at `/metrics` with real values.
- **Registered, always zero** — the metric appears at `/metrics` but is never incremented (useful for dashboards that expect it to exist).
- **Not registered / Not created** — the metric does not appear at `/metrics` at all.

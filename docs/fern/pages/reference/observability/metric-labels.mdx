subtitle: Every label dimension attached to Dynamo metric series — where each one comes from and the values it can take.

Labels are the **dimensions** attached to Dynamo metric series, not metrics in their own right. A single metric such as `dynamo_component_requests_total` becomes many Prometheus time series once it is split by `dynamo_namespace`, `dynamo_component`, `dynamo_endpoint`, and the labels the scraper adds. This page catalogs those dimensions; for the metrics themselves see the [Metrics Catalog](metrics-catalog.mdx).

A label reaches a series through one of four origins:

- **Auto-injected by the Dynamo runtime** — added to every metric registered through the namespace/component/endpoint hierarchy.
- **Added at registration time by backend code** — passed by the worker when it registers an endpoint, so presence depends on the backend.
- **Added by the metric itself** — specific to one metric family.
- **Injected by Prometheus/Kubernetes** — attached by the scraper, not present in the exposition text the process emits.

## Scope legend

Each label is tagged with the scope in which it appears:

- `[Shared]` — emitted by the Dynamo process itself; present whether you run locally or on Kubernetes.
- `[Kubernetes]` — attached by the Prometheus scraper in a Kubernetes deployment; absent when you scrape a process directly.

## Runtime-injected labels

Added by `create_metric()` in `lib/runtime/src/metrics.rs` for every metric registered through the namespace/component/endpoint hierarchy.

<ParamField path="dynamo_namespace" type="string">
  `[Shared]` The Dynamo runtime namespace — the logical scope shared by every component (router / prefill / decode / encode) in one deployment. **Not** the Kubernetes namespace. Example: `dynamo_cloud_vllm_v1_disagg_router_071de157`.

  On worker and router metrics this is the emitting component's own namespace, injected from its position in the hierarchy. On the frontend request metrics listed under [Frontend metrics and the namespace label](#frontend-metrics-and-the-namespace-label) it is instead the namespace of the worker set **selected to serve that request** — a frontend discovering one model in several namespaces load-balances across them per request. The two meanings coincide for the frontend's per-namespace routers, so `sum by (dynamo_namespace)` aggregates across both sets consistently.
</ParamField>

<ParamField path="dynamo_component" type="string">
  `[Shared]` Service role of the emitting component. See [Component names](#component-names) for the enumeration of values. Example: `backend`, `prefill`, `router`.
</ParamField>

<ParamField path="dynamo_endpoint" type="string">
  `[Shared]` The RPC within that component. See [Endpoint names](#endpoint-names) for the enumeration of values. Example: `generate`, `clear_kv_blocks`, `worker_kv_indexer_query_dp0`.
</ParamField>

<ParamField path="worker_id" type="string">
  `[Shared]` Hex-encoded discovery instance ID of the endpoint, providing a stable per-worker identity that does not depend on Kubernetes. Injected only when the endpoint hierarchy has a connection ID. Example: `1a2b3c4d`.

  On the per-worker frontend gauges (`dynamo_frontend_worker_*`) this label carries the worker's etcd lease ID instead. Example: `7890`.
</ParamField>

### Frontend metrics and the namespace label

A frontend can serve one model name from several namespaces at once, so some `dynamo_frontend_*` families carry `dynamo_namespace` and some deliberately do not. The split follows *when* the value is recorded, not the metric's importance.

**Namespace-aware** — recorded after a worker set has been selected, so the serving deployment is known:

- Per-response families, labeled by the namespace that served the request: `output_tokens_total`, `time_to_first_token_seconds`, `inter_token_latency_seconds`, `input_sequence_tokens`, `output_sequence_tokens`, `cached_tokens`, `images_per_request`, `videos_per_request`, `audio_per_request`, `image_tokens_per_request`.
- Per-deployment gauges, which also carry `worker_type` because a disaggregated deployment's prefill and decode cards advertise different limits. Capacity: `model_total_kv_blocks`, `model_max_num_seqs`, `model_max_num_batched_tokens`. Configuration facts: `model_context_length`, `model_kv_cache_block_size`, `model_migration_limit`. See the aggregation note below — the two kinds do not combine the same way.
- Router scheduler queue metrics, labeled by the namespace whose scheduler owns the queue: `router_queue_pending_requests`, `router_queue_pending_isl_tokens`, `router_queue_pending_cached_tokens`, `router_queue_backpressure_total`.
- Routing-overhead histograms, labeled by the namespace of the router that did the work: `dynamo_router_overhead_block_hashing_ms`, `_indexer_find_matches_ms`, `_seq_hashing_ms`, `_scheduling_ms`, `_shared_cache_query_ms`, `_total_ms`. See the note below for the one counter in that family that is not.

**Namespace-free**, in three categories:

1. *Recorded before or across worker-set selection.* The request-lifecycle guards are created when the HTTP handler starts, so that failures during model resolution are still counted — at that point no deployment has been chosen. Covers `requests_total`, `requests_started_total`, `request_duration_seconds`, `inflight_requests`, `queued_requests`, `active_requests`, `stage_requests`, `stage_duration_seconds`, and `disconnected_clients`.
2. *Frontend-internal work that is not per-deployment.* Tokenization, templating, and event-loop health belong to the frontend process itself: `tokenize_seconds`, `template_seconds`, `detokenize_token_count`, `detokenize_total_us`, `tokenizer_latency_ms`, `tokenizer_cache_*`, `event_loop_delay_seconds`, `event_loop_stall_total`.
3. *Already keyed by worker identity.* The `worker_last_*` gauges carry `worker_id`, `dp_rank`, and `worker_type`, which identify a single worker unambiguously.

<Note>
`dynamo_router_overhead_*` also carries `dynamo_namespace`, alongside its `router_id` const label. It is registered once for the process on the frontend's own registry, but a frontend serving one model from several namespaces runs one router per namespace, so the label is what keeps a slow deployment's routing latency out of the other deployments' quantiles.

One exception within that family: `dynamo_router_overhead_shared_cache_errors_total` is namespace-free. One of its two increment sites is the shared-cache subscriber background task, which is process-wide and has no router namespace, so splitting the counter would leave half its increments in a sentinel bucket.
</Note>

<Note>
The per-deployment gauges do not all aggregate the same way, because they are not all the same kind of value:

- **Capacity** — `model_total_kv_blocks`, `model_max_num_seqs`, `model_max_num_batched_tokens`. Each deployment contributes its own share, so `sum by (model)` recovers the fleet total.
- **Configuration facts** — `model_context_length`, `model_kv_cache_block_size`, `model_migration_limit`. Every deployment reports the same kind of value rather than a share of one, so summing is meaningless; use `max by (model)`, and expect disagreement between series to mean the deployments really are configured differently.

Counters and additive gauges elsewhere aggregate with `sum by (model)`; histograms with `histogram_quantile(..., sum by (model, le) (rate(..._bucket[5m])))`.
</Note>

#### Series lifecycle

The per-deployment gauges publish a point-in-time configuration rather than a running total, so the frontend stops exporting a series once the last worker set backing that `(model, dynamo_namespace, worker_type)` deployment disappears. Without that, a torn-down deployment would keep winning `max by (model)` with a stale `model_context_length` and keep inflating `sum by (model)` with capacity that no longer exists.

Removal is keyed on the deployment, not on model availability: a namespace losing its workers retires only its own series, and the model's remaining namespaces are untouched. Two components in one namespace serving the same role count as one deployment — the series survives until both are gone.

Counters and histograms are **not** removed. Their value is the history they carry, so a rate over a torn-down deployment's traffic stays correct. Samples already scraped into Prometheus are also unaffected: dropping a series only stops the frontend from continuing to present an old configuration as current.

#### Models served in-process

A model registered by an in-process engine (`--engine-type echo`, single-process serving) has no Dynamo namespace — nothing registers in etcd and no worker is addressed over the network. These report `dynamo_namespace="__local__"`, one series per model regardless of how many endpoint families it serves. The value is reserved; an operator-chosen namespace never collides with it.

## Registration-time labels

Passed via `metrics_labels=` when the worker calls `serve_endpoint()`. Not auto-injected, so presence depends on the backend.

<ParamField path="model" type="string">
  `[Shared]` The model being served (OpenAI-style label). Added by vLLM, SGLang, and TRT-LLM workers on inference endpoints; absent on internal endpoints like `worker_kv_indexer_query_dp{N}`. Example: `Qwen/Qwen3-0.6B`.
</ParamField>

<ParamField path="model_name" type="string">
  `[Shared]` Same model identifier under a second label name, retained for engine-native and dashboard back-compat. Added by vLLM and TRT-LLM workers; **not** added by SGLang. Example: `Qwen/Qwen3-0.6B`.
</ParamField>

## Metric-specific labels

Added by an individual metric family. Each label appears only on the metrics noted.

<ParamField path="error_type" type="string">
  `[Shared]` On `dynamo_component_errors_total` — the stage of request handling that failed. See [Component error types](#component-error-types) for the enumeration. On `dynamo_operator_reconcile_errors_total` the value set is different; see [Operator Metrics](operator-metrics.mdx).
</ParamField>

<ParamField path="stage" type="string">
  `[Shared]` On `dynamo_frontend_stage_requests` — the frontend pipeline stage a request currently occupies. See [Stage values](#stage-values).

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>preprocess</Badge> <Badge intent="note" minimal>route</Badge> <Badge intent="note" minimal>dispatch</Badge></span>
</ParamField>

<ParamField path="phase" type="string">
  `[Shared]` On `dynamo_frontend_stage_requests` — the serving phase. See [Phase values](#phase-values). The empty value is used when the stage does not distinguish phases (e.g. `preprocess`).

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>prefill</Badge> <Badge intent="note" minimal>decode</Badge> <Badge intent="note" minimal>aggregated</Badge> <Badge intent="note" minimal>"" (empty)</Badge></span>
</ParamField>

<ParamField path="worker_type" type="string">
  `[Shared]` On `dynamo_frontend_worker_*` and `dynamo_frontend_router_queue_*` — the worker role. In disaggregated mode both values appear; in aggregated mode all workers report as `decode`.

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>prefill</Badge> <Badge intent="note" minimal>decode</Badge></span>
</ParamField>

<ParamField path="dp_rank" type="integer">
  `[Shared]` On `dynamo_frontend_worker_*` — the data-parallel rank of the worker. Example: `0`.
</ParamField>

<ParamField path="policy_class" type="string">
  `[Shared]` On `dynamo_frontend_router_queue_*` — the resolved physical scheduler queue. With policy-family or cache-bucket configuration, this can differ from the family requested by the client.
</ParamField>

<ParamField path="reason" type="string">
  `[Shared]` On `dynamo_frontend_router_queue_backpressure_total` — the configured queue limit that rejected the request.
</ParamField>

<ParamField path="migration_type" type="string">
  `[Shared]` On request migration counters and the duration histogram — the category of request migration triggered by worker unavailability.

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>new_request</Badge> <Badge intent="note" minimal>ongoing_request</Badge></span>
</ParamField>

<ParamField path="outcome" type="string">
  `[Shared]` On `dynamo_frontend_model_migration_duration_seconds` — whether the migration recovered on another worker, ended without recovery, or was cancelled.

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>success</Badge> <Badge intent="note" minimal>failure</Badge> <Badge intent="note" minimal>cancelled</Badge></span>
</ParamField>

<ParamField path="request_type" type="string">
  `[Shared]` On `dynamo_frontend_model_cancellation_total` — whether the cancelled request was unary or streaming.

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>unary</Badge> <Badge intent="note" minimal>stream</Badge></span>
</ParamField>

<ParamField path="status" type="string">
  `[Shared]` On `dynamo_component_kv_cache_events_applied` — the outcome of applying a KV cache event to the router's radix-tree index.

  <span className="enum-values"><span className="enum-label">Allowed values:</span> <Badge intent="note" minimal>ok</Badge> <Badge intent="note" minimal>parent_block_not_found</Badge> <Badge intent="note" minimal>block_not_found</Badge> <Badge intent="note" minimal>invalid_block</Badge> <Badge intent="note" minimal>capacity_exhausted</Badge> <Badge intent="note" minimal>indexer_invariant_violation</Badge></span>

## Scraper-injected labels (Kubernetes)

Attached by the Prometheus scraper, not present in the exposition text the process emits. These appear only when Prometheus scrapes the pod in a Kubernetes deployment.

<ParamField path="instance" type="string">
  `[Kubernetes]` Scrape target as `<podIP>:<metricsPort>`. Example: `192.168.133.236:9090`.
</ParamField>

<ParamField path="pod" type="string">
  `[Kubernetes]` Kubernetes pod name; the per-replica disambiguator. Example: `vllm-v1-disagg-router-vllmdecodeworker-...`.
</ParamField>

<ParamField path="container" type="string">
  `[Kubernetes]` Container name inside the pod (usually `main`). Example: `main`.
</ParamField>

<ParamField path="namespace" type="string">
  `[Kubernetes]` Kubernetes namespace the pod runs in. **Not** the same as `dynamo_namespace`. Example: `dynamo-cloud`.
</ParamField>

<ParamField path="job" type="string">
  `[Kubernetes]` Prometheus scrape-job name, `<k8s-namespace>/<service-name>`. Example: `dynamo-cloud/dynamo-worker`.
</ParamField>

<ParamField path="endpoint" type="string">
  `[Kubernetes]` Named port on the Kubernetes Service that Prometheus scraped. **Not** the same as `dynamo_endpoint`. Example: `system`.
</ParamField>

## Label collisions

<Warning>
  Two pairs of labels share a name but mean different things depending on origin:

  - `dynamo_namespace` (Dynamo deployment scope, runtime-injected) vs. `namespace` (Kubernetes namespace, scraper-injected).
  - `dynamo_endpoint` (Dynamo RPC, runtime-injected) vs. `endpoint` (Kubernetes Service port name, scraper-injected).

  Always qualify with the `dynamo_` prefix when you mean the runtime dimension.
</Warning>

## Enumerations

### Component names

Values you will see in the `dynamo_component` label on `dynamo_component_*` series. The HTTP frontend (`python -m dynamo.frontend`) is **not** in this list — it exposes its own `dynamo_frontend_*` metric family, not `dynamo_component_*`.

| Value | Meaning |
|-------|---------|
| `router` | The standalone KV router (`python -m dynamo.router`). |
| `Planner` | The planner component (`python -m dynamo.planner`). Note the capital `P`. |
| `prefill` | The prefill worker in disaggregated serving (all backends). |
| `backend` | The decode worker in disaggregated serving for all backends, **and** the combined worker for vLLM in aggregated mode. |
| `encode` | The encode worker for vLLM, SGLang, and TRT-LLM. |
| `diffusion` | The diffusion worker for TRT-LLM. |

Internal subsystems (e.g. `kvbm` from the block manager, `sequences` from the KV router) also create components and may appear in `dynamo_component_*` series. The default for vLLM/SGLang can be overridden by passing `--endpoint dyn://<ns>.<component>.<endpoint>` on the worker command line.

<Note>
  The name `backend` for the decode worker is historical. The runtime has a TODO to introduce a `decode` constant and migrate to it (see `lib/runtime/src/metrics/prometheus_names.rs::component_names`).
</Note>

### Endpoint names

Values you will see in the `dynamo_endpoint` label on backend workers.

| Value | Meaning |
|-------|---------|
| `generate` | Main inference RPC; one increment per request received. On a prefill worker this counts prefill-stage `generate` calls; on a decode worker this counts decode-stage `generate` calls. |
| `clear_kv_blocks` | vLLM distributed admin RPC to flush the worker KV cache. |
| `worker_kv_indexer_query_dp{N}` | KV-router queries to the worker's local KV indexer about its cached prefix blocks. One endpoint per data-parallel rank (`_dp0`, `_dp1`, …). Appears on the worker that owns the prefix caches the router consults — in disaggregated serving that is the prefill worker. |

### Component error types

The `dynamo_component_errors_total` counter is labeled with `error_type`, identifying which stage of request handling failed.

| `error_type` | Stage | Meaning |
|--------------|-------|---------|
| `deserialization` | Ingress | Could not parse the incoming request payload. |
| `invalid_message` | Ingress | Wire-format violation in the incoming message. |
| `response_stream` | Pre-generate | The worker received the request but could not open the response stream back to the frontend (transport problem before `generate` was called). |
| `generate` | Engine | The engine's `generate()` itself returned an error. This is the counter that reflects engine/inference failures. |
| `publish_response` | Streaming | The engine produced response chunks but the worker could not push one back to the frontend. **Also fires on client cancellation** — the frontend disconnecting before the stream finishes — so this counter can be inflated by user-aborted requests. |
| `publish_final` | Teardown | All response chunks were sent, but the worker could not deliver the final stream-complete marker. The connection died right at the end. |

### Stage values

`dynamo_frontend_stage_requests` decomposes the lifetime of an active frontend request into three sequential pipeline stages. A request is counted in exactly one stage at a time.

| Stage | What it covers | Enters when | Exits when |
|-------|----------------|-------------|------------|
| `preprocess` | Tokenization and chat-template application | The frontend enters `preprocess_request` | Preprocessing returns |
| `route` | Worker selection (including parking in the KV-router queue while waiting for a worker) | The router's `generate()` is called | A worker is selected or the request is queued for one |
| `dispatch` | Serialization, transport to the chosen worker, and waiting for the backend's first response (includes backend prefill time) | `generate()` is called in `AddressedPushRouter` | The first response is received from the backend |

### Phase values

The `phase` label on `dynamo_frontend_stage_requests`.

| Phase | Meaning |
|-------|---------|
| `prefill` | The request is being handled by a prefill worker in disaggregated serving. |
| `decode` | The request is being handled by a decode worker in disaggregated serving. |
| `aggregated` | Aggregated (non-disaggregated) serving — a single worker handles both prefill and decode. |
| `""` (empty) | The stage does not distinguish phases (used by `preprocess`). |

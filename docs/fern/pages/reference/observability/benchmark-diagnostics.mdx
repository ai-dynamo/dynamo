A throughput regression, high Time To First Token (TTFT), or unexpected cache result is a symptom, not an explanation. To determine whether the cause is worker selection, queueing, KV reuse, engine saturation, or the workload itself, NVIDIA Dynamo maintainers need to correlate individual requests with component state and routing events from the same time window.

The evidence applies to local, SLURM, bare-metal, and Kubernetes deployments. Use the collection support in `srt-slurm` workflows when it is available. The Kubernetes sections below show how to collect the same evidence when no benchmark collector is already doing so.

## What We Need

Capture these signals while reproducing the benchmark. Keep them in any storage location that fits your environment; the folder layout does not matter. Preserve the Pod name and timestamp for every record so the artifacts can be joined later.

| Evidence | Capture | What it answers |
| --- | --- | --- |
| Benchmark context | Benchmark command or configuration, result, start and end time in UTC, model, and image identifiers | Can we reproduce the workload and align the evidence with the measured regression? |
| Request traces | `DYN_REQUEST_TRACE=1` on every frontend | Which worker served each request? How much KV overlap was available? Where did queueing, TTFT, or Inter-Token Latency (ITL) increase? |
| Metrics | Samples from every frontend and worker `metrics` endpoint | Was a component saturated, building a queue, losing cache capacity, or failing while the requests slowed down? |
| Structured logs | JSONL `INFO` logs from every frontend and routing component | What configuration, warnings, retries, or errors occurred during the affected interval? |
| Router debug logs | Short, low-rate JSONL `DEBUG` capture when worker selection is the question | How was each candidate worker scored, and why did the router choose one? |
| Deployment snapshot | Applied DynamoGraphDeployment (DGD), `kubectl get pods -o yaml`, and relevant image digests | What replicas, ports, images, and placement were present during the run? |

Do not capture request payloads unless the investigation requires them. The default `request_end` trace record captures request metadata without prompts or generated text.

## Capture Request Traces and Structured Logs

Enable traces before the benchmark begins because Dynamo records them only while the frontend handles requests. The following DGD fragment writes request traces to a Pod-local volume and emits structured JSONL logs to standard output. If your cluster already collects logs, retain that JSONL output through the existing collector instead of adding another log pipeline.

```yaml
apiVersion: nvidia.com/v1beta1
kind: DynamoGraphDeployment
metadata:
  name: <dgd-name>
spec:
  components:
    - name: Frontend
      type: frontend
      podTemplate:
        spec:
          volumes:
            - name: benchmark-artifacts
              emptyDir: {}
          containers:
            - name: main
              env:
                - name: DYN_REQUEST_TRACE
                  value: "1"
                - name: DYN_REQUEST_TRACE_SINKS
                  value: file
                - name: DYN_REQUEST_TRACE_FILE_PATH
                  value: /var/lib/dynamo-benchmark/request-trace
                - name: DYN_REQUEST_TRACE_FILE_FORMAT
                  value: jsonl_gz
                - name: DYN_LOGGING_CONSOLE_FORMAT
                  value: jsonl
                - name: DYN_LOG
                  value: info
              volumeMounts:
                - name: benchmark-artifacts
                  mountPath: /var/lib/dynamo-benchmark
```

Set the same logging variables on an EPP or other router component when it routes traffic independently of the frontend. Start with `DYN_LOG=info`. To investigate a worker-selection decision, temporarily set `DYN_LOG=debug` on the routing component and lower the request rate; candidate scoring can generate substantial log volume at high request rates or with many workers. `DYN_LOG` controls Dynamo logging, not backend-engine logging. See [Logging Reference](logging.mdx) for the supported fields and filters.

<Warning>
The `emptyDir` in this example survives container restarts but not Pod deletion. Copy its contents before cleanup. Use a PVC or object-store trace sink when Pods might be removed before collection.
</Warning>

## Capture Metrics

Scrape every frontend and worker for the whole benchmark window. Use the cluster's Prometheus deployment when it already stores these metrics. For a one-off capture without a metrics backend, run Tachometer alongside the benchmark. The collector below scrapes one frontend and one worker every five seconds, labels the samples by component, and writes a Parquet file to an existing PVC.

Before applying it, replace the image with a Tachometer image that contains `/tachometer-scraper`, set the output PVC, and set a reachable hostname or Pod IP for each endpoint. Copy and edit a frontend or worker `[[endpoints]]` block for every additional Pod. The defaults are frontend port `8000` and worker port `9090`; change the URLs if the DGD overrides either port. The Tachometer image is not bundled with Dynamo.

<Steps>
<Step title="Create the collector manifest">

Save the following as `tachometer-benchmark-capture.yaml` after replacing the image, PVC, and endpoint host placeholders.

```yaml
# Replace the image, PVC, and every endpoint host before applying.
# Copy and edit a frontend or worker endpoint block for each additional Pod.
apiVersion: v1
kind: ConfigMap
metadata:
  name: tachometer-benchmark-config
data:
  tachometer.toml: |
    storage = "file:///data/tachometer"
    rows_per_parquet = 1000000
    save_interval_secs = 5

    [[endpoints]]
    name = "frontend-0"
    url = "http://REPLACE_WITH_FRONTEND_HOST:8000/metrics"
    frequency = 0.2
    filter = "frontend"
    [endpoints.node_metadata]
    component = "frontend"

    [[endpoints]]
    name = "worker-0"
    url = "http://REPLACE_WITH_WORKER_0_HOST:9090/metrics"
    frequency = 0.2
    filter = "backend"
    [endpoints.node_metadata]
    component = "worker"
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: tachometer-benchmark
spec:
  replicas: 1
  selector:
    matchLabels:
      app: tachometer-benchmark
  template:
    metadata:
      labels:
        app: tachometer-benchmark
    spec:
      terminationGracePeriodSeconds: 300
      containers:
        - name: tachometer
          image: REPLACE_WITH_TACHOMETER_IMAGE
          command: ["/tachometer-scraper"]
          args:
            - --config
            - /etc/tachometer/tachometer.toml
            - --local-dir
            - /tmp/tachometer
          volumeMounts:
            - name: config
              mountPath: /etc/tachometer
              readOnly: true
            - name: output
              mountPath: /data
      volumes:
        - name: config
          configMap:
            name: tachometer-benchmark-config
        - name: output
          persistentVolumeClaim:
            claimName: REPLACE_WITH_EXISTING_PVC
```

</Step>
<Step title="Start the collector">

After the DGD reaches its planned replica count, apply the manifest in the DGD namespace.

```bash
kubectl apply --namespace <namespace> --filename tachometer-benchmark-capture.yaml
```

</Step>
<Step title="Verify the targets">

Check the collector logs before starting the load generator. Resolve endpoint failures before the benchmark; a missing worker makes the time-series evidence incomplete.

```bash
kubectl logs --namespace <namespace> deployment/tachometer-benchmark --container tachometer
```

</Step>
<Step title="Stop the collector">

After the benchmark, delete the collector Deployment. Kubernetes sends `SIGTERM`, allowing Tachometer to compact its samples into `final.parquet` on the output PVC. Retrieve `/data/tachometer/final.parquet` with the normal procedure for your storage class.

```bash
kubectl delete --namespace <namespace> deployment/tachometer-benchmark
```

</Step>
</Steps>

Update the endpoint list after any scale-up, scale-down, or rolling replacement. A collector with a stale Pod IP can look healthy while omitting the worker that handled the slow requests.

## Retrieve Traces, Logs, and Deployment Context

Collect the trace files, structured logs, and deployment snapshot before deleting the DGD. The following commands use one local directory, but only the raw files, timestamps, and Pod names matter. If a cluster log collector already retains the JSONL output, export the matching frontend and router log interval from that system instead.

```bash
NAMESPACE=<namespace>
DGD_NAME=<dgd-name>
ARTIFACT_DIR=benchmark-diagnostics

mkdir -p "${ARTIFACT_DIR}/logs" "${ARTIFACT_DIR}/request-traces" "${ARTIFACT_DIR}/deployment"

for POD in $(kubectl get pods --namespace "${NAMESPACE}" \
  --selector "nvidia.com/dynamo-graph-deployment-name=${DGD_NAME}" \
  --output jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  kubectl logs --namespace "${NAMESPACE}" "${POD}" --all-containers \
    --prefix --timestamps > "${ARTIFACT_DIR}/logs/${POD}.log"
done

for POD in $(kubectl get pods --namespace "${NAMESPACE}" \
  --selector "nvidia.com/dynamo-graph-deployment-name=${DGD_NAME},nvidia.com/dynamo-component-type=frontend" \
  --output jsonpath='{range .items[*]}{.metadata.name}{"\n"}{end}'); do
  mkdir -p "${ARTIFACT_DIR}/request-traces/${POD}"
  kubectl cp --namespace "${NAMESPACE}" --container main \
    "${POD}:/var/lib/dynamo-benchmark/." \
    "${ARTIFACT_DIR}/request-traces/${POD}"
done

kubectl get dynamographdeployment "${DGD_NAME}" --namespace "${NAMESPACE}" --output yaml \
  > "${ARTIFACT_DIR}/deployment/dgd.yaml"
kubectl get pods --namespace "${NAMESPACE}" \
  --selector "nvidia.com/dynamo-graph-deployment-name=${DGD_NAME}" --output yaml \
  > "${ARTIFACT_DIR}/deployment/pods.yaml"
```

If a Pod restarted, collect its previous container logs with `kubectl logs --previous` before the replacement logs expire. Record the benchmark's UTC start and end time even when the exact symptom has no single request ID; that interval is enough to join traces, logs, and metrics.

## Ask for Help With the Evidence

When asking for help, include the benchmark workload and result, the UTC interval, the applied DGD and image identifiers, request traces from every frontend, metrics from every frontend and worker, and JSONL `INFO` logs from every frontend and router. Add short router `DEBUG` logs when the question is why a worker was selected. State the symptom you observed, such as increased p99 TTFT, a cache-hit regression, a worker imbalance, or an unexpected error rate.

Do not reorganize or summarize the raw data before sharing it. The ability to match a request trace to the corresponding Pod logs and metrics sample is more useful than a prescribed archive layout.

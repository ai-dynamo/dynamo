Use this reference for a `DynamoGraphDeployment` (DGD) that routes requests through the Gateway API
Inference Extension (GAIE) and the Dynamo Endpoint Picker Plugin (EPP). For the procedure and
topology, see [Using GAIE with Dynamo](../../kubernetes/kv-aware-routing/gateway-api.mdx).

## EPP Modes

The EPP runs in one of two modes, selected by the `DYN_EPP_MODE` environment variable. This reference
covers Dynamo mode only.

| Concern | Dynamo mode (`dynamo`, default) | Standalone mode (`standalone`) |
|---|---|---|
| Deployed by | Dynamo operator, from a DGD `epp` component | User-applied manifests |
| Dynamo runtime | Required, with etcd and NATS | Not used |
| Worker discovery | Dynamo runtime discovery | Kubernetes pod watch driven by `InferencePool.spec.selector` |
| EPP ServiceAccount and RBAC | Created by the operator against the ClusterRole or Role from the `dynamo-platform` chart | Supplied with the deployment manifests |
| EPP replication | Available; active-sequence state shared over the Dynamo event plane | Available; active-sequence state shared over ZMQ, peers discovered through `DYN_EPP_PEER_SERVICE` |

Standalone mode does not install or run the Dynamo operator, so no operator-generated resource
described on this page applies to it, including the EPP ServiceAccount and the chart's EPP RBAC. A
standalone EPP carries its own ServiceAccount and Role, which grant the permissions that mode needs.
Do not bind a standalone EPP to the operator's EPP ClusterRole; its rules cover only the resources a
Dynamo-mode EPP reads. For the standalone path, see
[Using GAIE with vanilla vLLM](../../kubernetes/kv-aware-routing/vanilla-vllm-onramp.mdx).

## DGD EPP Fields

The EPP is a DGD component with `type: epp`. The Dynamo operator creates the EPP workload, Service,
and `InferencePool` from these fields. The Dynamo EPP runs the full Dynamo KV-aware router natively
and is configured through `DYN_*` environment variables. It implements the GAIE
[Lightweight Endpoint Picker (LW-EPP)](https://github.com/kubernetes-sigs/gateway-api-inference-extension/blob/main/pkg/lwepp/README.md)
`ext_proc` interface and does not use a plugin or scheduling-profile config.

<ParamField path="spec.components[].type" type="string" required={true}>
  Set to `epp` for the Endpoint Picker Plugin component. A DGD can contain at most one EPP component.

  <span className="enum-values"><span className="enum-label">Value:</span> <Badge intent="note" minimal>epp</Badge></span>
</ParamField>

<ParamField path="spec.components[].eppConfig" type="object">
  Deprecated Go-EPP configuration. When present, keep the EPP image pinned to 1.4; upgrading only
  the Dynamo Operator does not require migration. To select the native Rust EPP, remove this field
  and switch the image to 1.5 or later in the same update. Admission rejects mixed combinations. See
  [Route Requests with Gateway API](../../kubernetes/kv-aware-routing/gateway-api.mdx).
</ParamField>

<ParamField path="spec.components[].replicas" type="integer" default="1">
  Number of EPP pods. Increase it for endpoint-picker throughput or to survive the loss of a single
  EPP pod. For a native Rust EPP above `1`, the operator defaults `DYN_ROUTER_REPLICA_SYNC` to `true`
  so replicas share active-load state, and the routing accuracy of the fleet becomes approximate. Read
  [EPP Replication and Routing Accuracy](#epp-replication-and-routing-accuracy) before scaling it.

  The deprecated Go EPP, selected by the presence of `eppConfig`, hosts no Dynamo KV router and has
  no way to share state between replicas. It must have exactly `1` replica, and admission rejects any
  other value.
</ParamField>

<ParamField path="spec.components[].frontendSidecar" type="string" required={true}>
  Name of the Frontend container in each routable worker pod. The named container must exist in
  `podTemplate.spec.containers` and run with `--router-mode direct`.
</ParamField>

For the complete component schema, see the
[DynamoComponentDeployment Reference](../kubernetes-api/dynamo-component-deployment.mdx).

## EPP Runtime Environment

Set these values on the EPP component's `main` container. Shared KV router settings use the same
semantics as Frontend-hosted routing; this section identifies the settings most relevant to the
Gateway topology.

<ParamField path="DYN_MODEL_NAME" type="string">
  Model identifier used to load tokenizer and model configuration. Set it when discovery does not
  provide the model name. It must match the model served by the workers.
</ParamField>

<ParamField path="DYN_KV_CACHE_BLOCK_SIZE" type="integer">
  Backend KV cache block size. Set it when discovery does not provide the value. It must match the
  worker backend's block size; a mismatch changes prefix block hashes and produces incorrect overlap
  scores.
</ParamField>

<ParamField path="DYN_USE_KV_EVENTS" type="boolean" default="true">
  Enables worker-published KV event consumption in the EPP router. When `false`, the router relies on
  predicted local state instead of precise worker cache events.
</ParamField>

<ParamField path="DYN_ROUTER_KV_OVERLAP_SCORE_CREDIT" type="number" default="1.0">
  Credit applied to device-local prompt-prefix overlap. Higher values prefer workers that already hold
  more of the prompt prefix. Set to `0` to remove device-local cache overlap from endpoint scoring.
</ParamField>

<ParamField path="DYN_ROUTER_KV_OVERLAP_SCORE_CREDIT_DECAY" type="number" default="0.0">
  Reduces overlap credit as active prefill load rises above the least-loaded eligible worker. `0`
  disables decay.
</ParamField>

<ParamField path="DYN_ROUTER_PREFILL_LOAD_SCALE" type="number" default="1.0">
  Scales prompt-side prefill load after cache-hit credits are applied.
</ParamField>

<ParamField path="DYN_ROUTER_DECODE_ACTIVE_REQUEST_WEIGHT" type="number" default="0.0">
  Adds block-equivalent routing cost for each active request on a candidate worker. Tune this value
  only when decode step latency depends materially on active batch size.
</ParamField>

<ParamField path="DYN_ROUTER_TEMPERATURE" type="number" default="0.0">
  Controls worker exploration through normalized softmax sampling. `0` selects deterministically.
</ParamField>

<ParamField path="DYN_ROUTER_REPLICA_SYNC" type="boolean" default="false">
  Publishes and consumes best-effort active-sequence state across EPP replicas through the Dynamo event
  plane. For a native Rust EPP, the operator defaults it to `true` when `replicas` is above `1`, and a
  value set in `podTemplate` takes precedence. The deprecated Go EPP never receives it and cannot be
  replicated. It has no peer to synchronize with at one replica. It reduces cross-replica divergence
  rather than removing it. See
  [EPP Replication and Routing Accuracy](#epp-replication-and-routing-accuracy).
</ParamField>

<ParamField path="DYN_ROUTER_TRACK_ACTIVE_BLOCKS" type="boolean" default="true">
  Includes blocks used by active generation in worker load accounting.
</ParamField>

<ParamField path="DYN_ROUTER_TRACK_OUTPUT_BLOCKS" type="boolean" default="false">
  Predicts output blocks during generation and decays them as requests make progress.
</ParamField>

<ParamField path="DYN_ROUTER_TRACK_PREFILL_TOKENS" type="boolean" default="true">
  Includes active prompt-side prefill tokens in worker load accounting.
</ParamField>

For the full shared configuration surface and tuning guidance, see
[Configuration and Tuning](../../developer-guide/knowledge-base/modular-components/router/configuration-and-tuning.md).

## EPP Replication and Routing Accuracy

Running more than one EPP replica trades exact load accounting for endpoint-picker throughput and
fault tolerance. The trade is the same one the Frontend-hosted KV router already makes when it is
replicated, described in
[Router Operations](../../developer-guide/knowledge-base/modular-components/router/router-operations.md).
This section states what a replicated EPP gets wrong, and by how much.

The router keeps two kinds of state, and only one of them is affected.

**Prefix-cache state converges on its own.** Workers publish KV `Stored` and `Removed` events to the
Dynamo event plane, and every subscriber receives every event, so each replica builds an equivalent
radix tree without any router-to-router traffic. Cache-overlap scoring, which dominates worker choice
on prefix-heavy traffic, is therefore as accurate with ten replicas as with one. A replica that starts
late rebuilds prefix state by querying each worker's local indexer.

**Active-block state does not.** A booking is recorded by the replica that routed the request, so each
replica sees only the load it placed itself. `DYN_ROUTER_REPLICA_SYNC` shares the request lifecycle —
add, prefill-complete, and free — across replicas, which is why the operator defaults it on above one
replica. That channel is fire-and-forget: its outbound queue drops the newest event when full, there is
no acknowledgement, replay, or resynchronization, and replicas can disagree for a bounded period.
Output-block growth is never shared, because it changes at a frequency that would consume
disproportionate bandwidth, so decode-side load estimates drift between replicas whenever
`DYN_ROUTER_TRACK_OUTPUT_BLOCKS` is on.

Enabling it does not make active-load accounting correct. It changes the error from permanent to
transient. Left off, each replica scores workers from its own slice of the traffic and understates load
by roughly the replica count, and every replica is wrong in the same direction, so the errors compound
rather than averaging out. Turned on, replicas converge on a fleet-wide view between the gaps above.
Those gaps are not symmetric when the outbound queue drops an event: a dropped `add` hides a request
from a peer for that request's lifetime, while a dropped `free` leaves a phantom booking on the peer
until the reaper clears it.

### Booking Ownership on Disconnect and Retry

This is the sharpest accuracy limit, and it is specific to the EPP rather than inherited from the
router.

The Frontend owns a request end to end: it selects a worker, dispatches, and observes completion, so it
frees the booking exactly when the work ends. The EPP only selects. Envoy dispatches, and the EPP's
booking lives for the life of the `ext_proc` stream. When that stream ends the EPP frees the booking,
whether or not the backend request it accounted for has finished.

At one replica the consequences are self-correcting. At several replicas they are not:

- **A retry can land on a different EPP.** Envoy load-balances `ext_proc` streams across EPP pods with
  no request affinity, so a retried request is picked by whichever replica Envoy chooses next. Backend
  load and booking state then diverge, and they move in opposite directions.
- **Backend work can outlive the stream.** An `ext_proc` disconnect does not cancel work already
  dispatched to the worker, so the original attempt can still be generating when the retry is
  dispatched. Two attempts consume capacity for one logical request.
- **Booking state undercounts that, and briefly overcounts on some replicas.** The replica that placed
  the original booking frees it when its stream ends, and that `free` propagates. Replicas that receive
  it stop accounting for the original attempt while it is still running, so the fleet understates the
  worker. A replica whose `free` has not yet arrived holds the original booking alongside the retry's
  and counts the request twice until it does.
- **Expiry bounds the error but does not correct it.** A quiet booking is reclaimed by a router-owned
  reaper at `DYN_ROUTER_ACTIVE_REQUEST_EXPIRY_SECS` (default `300` seconds). Lease expiry is local to
  the replica that holds it and publishes no `free`, so peers reclaim their copies on their own timers.

The practical effect is a transient over- or under-estimate of one worker's active load, on some
replicas and not others, lasting until the affected requests complete or the reaper runs. It shifts
load balancing, not correctness: a misrouted request is still served by a worker that holds the model.

### Selection-to-Booking Race

Replica synchronization is eventually consistent, so it cannot serialize selection. Two replicas can
evaluate the same worker as least-loaded before either one's booking has propagated, and both send work
to it. The size of the error grows with request arrival rate and with propagation delay, and no setting
removes it. `DYN_ROUTER_TEMPERATURE` above `0` decorrelates replicas by sampling among near-equal
workers, which reduces how often they converge on the same choice.

### Choosing a Replica Count

Use one replica when active-load precision matters more than endpoint-picker throughput, or when the
workload is long-generation and sensitive to decode-side balance. Use several when the EPP itself is
the bottleneck or its availability is, and the traffic is prefix-heavy enough that cache-overlap
scoring — the part that stays accurate — drives most of the routing decision.

## Generated Resource Contract

For a DGD named `<dgd-name>`, the operator generates an `InferencePool` named `<dgd-name>-pool` in
the DGD namespace. Its `endpointPickerRef` points to the generated EPP Service on gRPC port `9002`,
and its target port points to worker Frontend sidecars on port `8000`.

```yaml
spec:
  selector:
    matchLabels:
      nvidia.com/dynamo-component-class: worker
      nvidia.com/dynamo-namespace: <dynamo-namespace>
  endpointPickerRef:
    kind: Service
    name: <epp-service-name>
    port:
      number: 9002
  targetPorts:
  - number: 8000
```

Treat the generated `InferencePool`, EPP Service, and Deployment as operator-owned resources. Make
persistent changes in the DGD.

mutated request to the selected Frontend sidecar.

</ParamField>

<ParamField path="x-dynamo-dp-rank" type="HTTP header">

</ParamField>

<ParamField path="x-dynamo-routing-mode" type="HTTP header">

  <span className="enum-values"><span className="enum-label">Values:</span> <Badge intent="note" minimal>aggregated</Badge> <Badge intent="note" minimal>disaggregated</Badge></span>
</ParamField>

`nvext.token_data` so the Frontend sidecar does not repeat tokenization.

## agentgateway and Istio Injection

When namespace-level Istio injection is enabled, an injected `istio-proxy` in an agentgateway data
plane pod can intercept the EPP external-processing gRPC connection and cause HTTP 500 responses.
Use an `AgentgatewayParameters` resource in the same namespace as the `Gateway`:

```yaml
apiVersion: agentgateway.dev/v1alpha1
kind: AgentgatewayParameters
metadata:
  name: inference-gateway-params
spec:
  deployment:
    spec:
      template:
        metadata:
          annotations:
            sidecar.istio.io/inject: "false"
```

Reference it from the Gateway:

```yaml
spec:
  gatewayClassName: agentgateway
  infrastructure:
    parametersRef:
      group: agentgateway.dev
      kind: AgentgatewayParameters
      name: inference-gateway-params
```

`AgentgatewayParameters` is a local reference and must be in the Gateway namespace. Use a
per-Gateway resource unless disabling injection is an intentional cluster-wide policy.

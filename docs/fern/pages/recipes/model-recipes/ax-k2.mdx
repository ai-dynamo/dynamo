Each target below is an NVIDIA Dynamo + vLLM deployment of SK Telecom's `skt/A.X-K2`, a 688B-parameter mixture-of-experts model (33B active) with DeepSeek-V3-style Multi-head Latent Attention (MLA), a block-scaled FP8 checkpoint, and a 256K context window. Both targets run on 32x H200 (four 8-GPU nodes) and were measured on 16K-input / 1K-output traffic whose requests share a 10K-token few-shot prefix. The disaggregated target is the recommended pick: from 32 concurrent requests upward it delivers +16 to +51 % total throughput over the aggregated TP8 baseline and roughly one tenth of its decode inter-token latency (ITL) p99. Pick your serving topology; every command on this page updates to match.

<Warning>
**Experimental.** The A.X-K2 model implementation lives in the [SKT-AI vLLM fork](https://github.com/SKT-AI/vllm) until it lands upstream, so the worker image is a custom build on the Dynamo 1.4.2 vLLM runtime. Build it per the [container README](https://github.com/ai-dynamo/dynamo/blob/main/recipes/a.x-k2/container/README.md) and replace the placeholder image before deploying.
</Warning>

## Prerequisites

<div data-variant="disagg">

- A Kubernetes cluster with the Dynamo platform installed and **four 8-GPU H200 nodes** available, with RDMA (InfiniBand or RoCE) between them exposed to the pods for NIXL KV transfer. See the [Kubernetes Deployment Guide](../../kubernetes/getting-started/quickstart.mdx).
- A custom worker image built from the A.X-K2 vLLM fork on `vllm-runtime:1.4.2` ([container README](https://github.com/ai-dynamo/dynamo/blob/main/recipes/a.x-k2/container/README.md)).
- A filled cluster Kustomization or a private copy of the manifest that adds node selection, tolerations, image pull Secrets, RDMA device resources and network attachments, and the RDMA device names (`UCX_NET_DEVICES`, `NCCL_IB_HCA`). The portable base omits them; the measured values are listed in the [source README](https://github.com/ai-dynamo/dynamo/blob/main/recipes/a.x-k2/README.md#cluster-bindings-used-in-the-measurement).
- Optionally a Hugging Face token for the download Job. `skt/A.X-K2` is public and ungated (Apache-2.0); a token only raises rate limits.

</div>

<div data-variant="agg">

- A Kubernetes cluster with the Dynamo platform installed and **one 8-GPU H200 node per worker replica** (the manifest ships with four replicas). See the [Kubernetes Deployment Guide](../../kubernetes/getting-started/quickstart.mdx).
- A custom worker image built from the A.X-K2 vLLM fork on `vllm-runtime:1.4.2` ([container README](https://github.com/ai-dynamo/dynamo/blob/main/recipes/a.x-k2/container/README.md)).
- A filled cluster Kustomization or a private copy of the manifest that adds node selection, tolerations, and image pull Secrets. The portable base omits them.
- Optionally a Hugging Face token for the download Job. `skt/A.X-K2` is public and ungated (Apache-2.0); a token only raises rate limits.

</div>

Create the namespace and, optionally, the token secret:

```bash
export NAMESPACE=your-namespace
kubectl create namespace ${NAMESPACE}
# Optional; the download Job runs without it.
kubectl create secret generic hf-token-secret \
  --from-literal=HF_TOKEN="your-token" \
  -n ${NAMESPACE}
```

<Warning>
Set `storageClassName` in `model-cache/model-cache.yaml` to a ReadWriteMany class on your cluster, replace the placeholder worker image, and bind the cluster-owned fields before applying.
</Warning>

## Deploy

Create the `shared-model-cache` PVC and download the checkpoint (~647 GiB; 1-3 hours). The workers read it offline and keep their JIT kernel caches on the same volume, so later starts skip the ~25-minute cold warmup:

```bash
kubectl apply -f recipes/a.x-k2/model-cache/model-cache.yaml -n ${NAMESPACE}
kubectl apply -f recipes/a.x-k2/model-cache/model-download.yaml -n ${NAMESPACE}
kubectl wait --for=condition=Complete job/model-download -n ${NAMESPACE} --timeout=14400s
```

Then apply the manifest for your target.

<div data-variant="disagg">

```bash
kubectl apply -f recipes/a.x-k2/vllm/disagg-h200/deploy.yaml -n ${NAMESPACE}
kubectl wait --for=condition=Ready pod \
  -l nvidia.com/dynamo-graph-deployment-name=axk2-vllm-disagg-h200 \
  -n ${NAMESPACE} --timeout=5400s
```

</div>

<div data-variant="agg">

```bash
kubectl apply -f recipes/a.x-k2/vllm/agg-h200/deploy.yaml -n ${NAMESPACE}
kubectl wait --for=condition=Ready pod \
  -l nvidia.com/dynamo-graph-deployment-name=axk2-vllm-agg-h200 \
  -n ${NAMESPACE} --timeout=5400s
```

</div>

To change a running deployment, delete the DGD and apply the new manifest instead of patching it: a patched deployment can leave old and new worker pods contending for the same nodes.

Both targets serve the model as `A.X-K2`:

```bash
curl http://localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"A.X-K2","messages":[{"role":"user","content":"A.X K2를 한 문장으로 소개해줘."}],"max_tokens":256}'
```

Thinking mode is on by default, so a small `max_tokens` budget can be spent on `reasoning_content` before any `content` appears. Pass `"chat_template_kwargs": {"enable_thinking": false}` to disable it per request.

## Benchmark

One AIPerf Job, `perf/perf.yaml`, covers both targets. It runs a closed-loop concurrency sweep at 16,384 input / 1,024 output tokens and writes artifacts to the shared PVC. Edit the `env` block to select the target and workload:

| Variable | Values |
| --- | --- |
| `ENDPOINT` | `axk2-vllm-disagg-h200-frontend:8000` or `axk2-vllm-agg-h200-frontend:8000` |
| `WORKLOAD` | `w1` (32 shared 10K prefixes + 6K unique), `w2` (16K cold), `w3` (one shared 10K prefix + 6K unique) |
| `CONCURRENCIES` | Space-separated sweep, default `8 16 32 64 128` |

```bash
kubectl apply -f recipes/a.x-k2/perf/perf.yaml -n ${NAMESPACE}
kubectl logs -f job/axk2-bench -n ${NAMESPACE}
```

<div data-variant="disagg">

Keep `w2` (cold) concurrency at or below 128 on this target: at 256 the decode workers saturate their KV cache and stall (see [Notes](#notes)).

</div>

## Compare All Targets

| | Disaggregated (recommended) | Aggregated |
|---|---|---|
| **GPUs** | 32x H200: 2 prefill + 2 decode workers, 8 GPUs each | 8x H200 per worker, 4 workers measured |
| **Parallelism** | TP2 x DP4 + EP prefill / TP8 + EP decode | TP8 + EP |
| **Routing** | KV-aware (event-driven, prefill workers publish KV events) | Round-robin |
| **Prefill batch budget** | 8,192 (engine default) prefill / 2,048 decode | 32,768 |
| **KV capacity per worker** | 1.77M tokens prefill / 864K tokens decode (49 x 16K) | 864K tokens (49 x 16K) |
| **MoE backend** | flashinfer_cutlass prefill / triton decode | triton |
| **KV transfer** | NIXL over UCX/RDMA | N/A |
| **Best at** | 32 to 128 concurrent requests per 32 GPUs | Up to 16 concurrent requests per 32 GPUs (within 8 % of disaggregated) |
| **Operating limit** | About 100 concurrent cold 16K requests per 32 GPUs | KV-bound above 49 requests per worker; completes with long TTFT |

## Notes

- **Decode KV saturation stall (open).** On the disaggregated target, cold 16K prompts above ~100 concurrent requests per 32 GPUs fill both decode workers to 51 running sequences and 100 % KV usage, after which generation stops until the client aborts. NIXL reported no errors, and the workers recover without a restart. Prefix-hit traffic and the aggregated target complete at the same KV usage. Cap concurrency, or set `--max-num-seqs` on the decode workers near the per-worker KV limit.
- **KV-aware routing is essential on 2P2D and counterproductive on this aggregated layout.** On 2P2D it halves TTFT p50 and prevents the random-routing stall at 128 concurrent cold requests. On aggregated TP8 it adds only +2 to +7 % throughput and raises TTFT p50 2-4x between 32 and 128 concurrent requests, so the aggregated target ships with round-robin.
- **Prefill batch budgets differ by layout.** TP8 prefills a 16K prompt in one 32,768-token step. TP2 x DP4 does not fit that budget (dense weights are replicated per GPU) and uses the 8,192 default, so a 16K prompt is two chunks and TTFT has a ~2 s floor.
- **FlashInfer autotune is off.** With no warm JIT cache the TP2 x DP4 warmup hung for 25+ minutes until the NCCL watchdog killed the worker. Both targets persist the DeepGEMM, FlashInfer, and Triton caches on the shared PVC.
- Reasoning uses the `deepseek_v3` parser and tool calling the `hermes` parser. Thinking mode is enabled by default via `--dyn-default-thinking-mode enabled`.

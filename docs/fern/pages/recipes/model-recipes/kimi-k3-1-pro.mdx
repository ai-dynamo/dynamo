```bash
export NAMESPACE=your-namespace
```

## Deploy

<div data-sku="b200 gb300">

Create the shared model cache and download the main checkpoint:

<Warning>
Edit `storageClassName` in `recipes/kimi-k3.1/model-cache/model-cache.yaml` to a ReadWriteMany class on your cluster before you apply it.
</Warning>

```bash
kubectl apply -f recipes/kimi-k3.1/model-cache/model-cache.yaml -n ${NAMESPACE}
kubectl apply -f recipes/kimi-k3.1/model-cache/model-download.yaml -n ${NAMESPACE}
kubectl wait --for=condition=Complete job/model-download -n ${NAMESPACE} --timeout=7200s
```

The weights are stored at `/shared-model-cache/moonshotai/Kimi-K3.1-Pro` on the PVC. The download Job downloads only the main model.

</div>

<div data-sku="b200">

For B200, also stage the `Inferact/Kimi-K3-DSpark` draft checkpoint at the path in the worker's `SPECULATIVE_CONFIG` on the same PVC, or update that setting to your staged checkpoint path.

</div>

<div data-sku="vr200">

The manifests mount these node-local directories at `/shared-model-cache/moonshotai/Kimi-K3.1-Pro` and `/draft-model`; change the `hostPath` values if your storage layout differs. The shared-storage download Job above does not populate these directories.

## Smoke Test

The deploy command sets `DGD` to the selected resource name. Wait for readiness and forward the frontend port:

```bash
kubectl wait --for=condition=Ready dynamographdeployment/${DGD} \
  -n ${NAMESPACE} --timeout=7200s
kubectl port-forward svc/${DGD}-frontend 8000:8000 -n ${NAMESPACE}
```

Send a chat completion with the served model name `moonshotai/Kimi-K3.1-Pro`:

```bash
curl http://localhost:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"moonshotai/Kimi-K3.1-Pro","messages":[{"role":"user","content":"Reply with exactly: READY"}],"temperature":0,"max_tokens":256}'
```

## Benchmark

Use [perf.yaml](https://github.com/ai-dynamo/dynamo/blob/main/recipes/kimi-k3.1/perf/perf.yaml) to run AIPerf 0.13.0 against the deployment. It runs `aiperf profile` with the chat endpoint type and streaming on the AgentX agentic trace (`semianalysis_cc_traces_weka_062126`), with an agentic warmup and a 1200 s profiling phase. The tokenizer is read from the model path on the `shared-model-cache` PVC.

The performance results use text-only AgentX traffic. Apply the selected benchmark variant before running AIPerf; normal serving commands above use natural acceptance.

<div data-recipe-framework="vllm" data-sku="b200" data-variant="agg">

```bash
kubectl apply -f recipes/kimi-k3.1/vllm/agg-b200-agentx/deploy-b200-synthetic-al.yaml -n ${NAMESPACE}
```

</div>

<div data-recipe-framework="vllm" data-sku="vr200" data-variant="agg">

```bash
kubectl apply -f recipes/kimi-k3.1/vllm/agg-vr200-agentx/deploy-vr200-synthetic-al.yaml -n ${NAMESPACE}
```

</div>

<div data-recipe-framework="vllm" data-sku="vr200" data-variant="disagg">

```bash
kubectl apply -f recipes/kimi-k3.1/vllm/disagg-vr200-agentx/deploy-vr200-synthetic-al.yaml -n ${NAMESPACE}
```

</div>

Set these values in the Job `env` section for your target:

- `ENDPOINT`: the frontend Service of the DynamoGraphDeployment, `${DGD}-frontend:8000` (substitute the selected deployment name).
- `CONCURRENCY`: GB300 uses 32 for vLLM aggregated and 48 for disaggregated. Reported VR200 points use 180 for aggregated and 174 for disaggregated; B200 uses 48.

The benchmark Job mounts `shared-model-cache` even when the server uses VR200 node-local storage. Prepare that PVC with the tokenizer files for the Job, or adapt its volume and placement to your storage layout.

```bash
kubectl apply -f recipes/kimi-k3.1/perf/perf.yaml -n ${NAMESPACE}
kubectl logs -f job/kimi-k3-1-aiperf -n ${NAMESPACE}
```

Results are written to `/shared-model-cache/perf/<epoch>_<job-name>/`. Restart the workers between independent runs to reset KV-cache and routing state.

## Notes

- SGLang targets are experimental, text-only, and functional-only. No SGLang performance claims are made. Use the vLLM multimodal overlays for image and video input.
- On SGLang, disable thinking for strict `json_schema` output (`"chat_template_kwargs": {"thinking": false}`). Earlier validation returned JSON in `reasoning_content` with thinking enabled; this needs re-validation with the current structural-tag configuration.
- Synthetic draft acceptance is for benchmarking. Use the natural-acceptance variants for normal serving.
- Disaggregated performance depends on your fabric; RDMA tuning is cluster-specific.

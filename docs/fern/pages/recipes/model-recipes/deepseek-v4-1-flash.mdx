## Overview

DeepSeek-V4.1-Flash is a Mixture-of-Experts model. The checkpoint also accepts images; every target here serves text only.

<div data-recipe-framework="vllm">

vLLM resolves the attention path from the checkpoint. On Blackwell it selects the `FLASHMLA_SPARSE_DSV41` attention backend, which brings DeepSeek's `fp8_ds_mla` KV cache format and fixes the KV block size at 128. The recipes leave all three at their resolved values and override two others:

| Overridden setting | Recipe value | Resolved default |
| --- | --- | --- |
| MoE backend | `deep_gemm_mega_moe` | `FLASHINFER_TRTLLM_MXFP4_MXFP8` |
| Sparse-indexer KV dtype | `mxfp4` | `fp8` |

The vLLM targets share one serving configuration across both GPUs. The aggregated recipe is identical on B200 and GB200 apart from the architecture label, the GPU product label, and the deployment name. The disaggregated recipes differ only in their KV fabric settings.

On identical settings GB200 measures about 9 percent higher than B200 aggregated. The cause is KV capacity rather than compute: a B200 TP4 worker holds roughly 19 percent fewer KV tokens, and prefix-cache hit rate follows. On a workload whose input median is near 67,600 tokens, each miss is a full prefill.

</div>

<div data-recipe-framework="sglang">

The aggregated target caps the decode CUDA graph batch at 64. DSpark verify graphs run out of memory at batch 256.

</div>

## Prerequisites

- A Kubernetes cluster with the Dynamo platform installed. See the [Kubernetes Deployment Guide](../../kubernetes/getting-started/quickstart.mdx).
- A ReadWriteMany PVC named `shared-model-cache`, with at least 1000Gi.

```bash
kubectl logs -n ${NAMESPACE} -l job-name=dsv41-flash-vllm-bench -f
```

The workload is a Mooncake-format agentic trace of 3,541 requests, with an input median near 67,600 tokens, an output median near 400, and about 90 percent designed KV reuse. Both SLO floors are measured at p50: output token throughput per user at or above 50 tok/s, and time to first token under 5,000 ms.

## Notes

<div data-recipe-framework="vllm">

- The single largest lever on this workload is `--prefix-cache-retention-interval 1024`. The resolved default is 0, which tells the sliding-window group to retain only a 160-token tail at the previous prompt end. The reconciled prefix hit is the minimum across groups, so that tail caps every request even though the compressed-KV group holds the prefix densely.
- `enable_kv_cache_events` inside `--kv-events-config` is load-bearing. Omit it and it defaults to false: Dynamo logs `KV event publishing skipped`, the router receives no events, and `DYN_ROUTER_MODE=kv` silently degrades to load-based routing with `overlap_blocks=0` on every request.
- Both reasoning parsers are required and they are not duplicates. `--reasoning-parser` is the engine-side one and gates guided decoding; `--dyn-reasoning-parser` is the Dynamo frontend one and splits the response into `reasoning_content` and `content`. Do not also set the engine-side `--tool-call-parser`: Dynamo refuses both halves of the tool-call pair at once.
- Adaptive verification is disabled in the speculative config. It is the established cause of a CUDA illegal memory access on this model. Disabling it also rules out `--enforce-eager`, because that path structurally requires captured CUDA graphs.
- Do not set `--attention-backend`, an unlisted `--moe-backend`, or `--linear-backend`. Do not set `--block-size` either; it resolves to 128 for this backend, and the DeepSeek-V4-Flash recipes' 256 belongs to a different model.
- The vLLM recipes are authored as Kustomize matrices. Edit `kustomize/base/` or the Components, then regenerate with `scripts/kustomize-matrix.py unfold` followed by `render`. Never edit a `deploy-*.yaml` by hand.

</div>

<div data-recipe-framework="vllm" data-variant="disagg">

- 2 prefill to 1 decode is balanced for this workload, not a free parameter. Both sides saturate together at the operating point: the prefill queue grows into TTFT, which still holds headroom, while decode inter-token latency grows into the per-user token rate, which is what binds. Other ratios measured worse or the same per GPU.
- Each worker requests four RDMA devices (`rdma/ib: 4`). Without one, UCX falls back to TCP silently, with no error and a Ready deployment, and TTFT degrades by roughly an order of magnitude. The resource name is cluster-specific: these recipes request `rdma/ib`, other clusters expose `rdma/shared_ib` or a vendor-specific name, and GKE uses multi-network devices instead.
- `UCX_TLS` keeps `tcp` in the list deliberately. `cuda_ipc` and `cuda_copy` are memory-type transports only and cannot carry NIXL's UCX active-message control plane, so removing `tcp` breaks the handshake rather than just the data path.
- `UCX_IB_GID_INDEX` is set only on the GKE variant. Index 3 is the RoCEv2 convention, which applies to GKE's RDMA networks and does not apply where ports report `link_layer: InfiniBand`.
- After the workers are Ready, confirm KV is moving over the expected transport from the NIXL metrics on the worker `/metrics` endpoint, with `nixl_num_failed_transfers` and `nixl_num_failed_notifications` both zero.

</div>

<div data-recipe-framework="vllm" data-sku="gb200" data-variant="disagg">

<Warning>
All pools must share one NVLink clique. A fabric memory handle cannot be imported across cliques, and a split placement does not error: the deployment reports Ready and chat completions return HTTP 200 with `content: null`. The ComputeDomain in this manifest is the supported mechanism for that guarantee. A dangling `resourceClaim` leaves pods `SchedulingGated` indefinitely with no error, so verify the DRA driver is installed before applying.
</Warning>

- There is deliberately no `NCCL_*` tuning. The KV transfer is NIXL over UCX; NCCL only forms the intra-worker TP4 group, which lives inside one node. Setting `NCCL_MNNVL_ENABLE`, `NCCL_NVLS_ENABLE`, or `NCCL_P2P_LEVEL` broke that group with `unhandled system error` in `ncclCommInitRank`.

</div>

<div data-recipe-framework="sglang">

- The disaggregated target has no speculative decoding. SGLang refuses DSpark under prefill and decode disaggregation for this model. Use the aggregated target for speculative decoding.
- Each worker needs TP4 and a GB200 node holds 4 GPUs. So prefill and decode always sit on different nodes, and KV crosses nodes. The generic target pins Mooncake to TCP with `MC_FORCE_TCP=1`. The GKE variant drops that pin and uses RDMA, because it attaches RDMA devices. Mooncake does not default to TCP on its own: with no RDMA device it reports `Found 0 HCAs` and takes the NVLink fabric, which is why the pin is explicit.
- The NVLink fabric is the faster KV path, and this recipe does not take it. To opt in, remove `MC_FORCE_TCP` and set `SGLANG_MOONCAKE_CUSTOM_MEM_POOL=NVLINK` and `MC_FORCE_MNNVL=true` on both workers. Measured on GB200: TCP across cliques 0.707 GB/s, NVLink inside one clique 1.7 to 2.2 GB/s, so the fabric is about 3 times faster on KV. Read the warning that follows first.

<Warning>
The NVLink fabric KV path needs both workers in one NVLink clique. A fabric memory handle cannot be imported across cliques, and a split gives no error: the deployment reports Ready, and chat completions return HTTP 200 with `content: null` and zero completion tokens. The workers log `cuMemImportFromShareableHandle failed: 400`. Readiness does not exercise the KV path. Pin both workers to one clique with a `nvidia.com/gpu.clique` nodeSelector, read from `kubectl get nodes -L nvidia.com/gpu.clique`, and send one request to confirm the answer is not empty.
</Warning>

- If completions come back empty on the disaggregated target, read the worker log. `cuMemImportFromShareableHandle failed: 400` means prefill and decode landed in different NVLink cliques, and only the fabric KV path fails this way. `Failed to register memory: Bad address [14]` means GPU memory did not register for RDMA, because the nodes load no `nvidia_peermem` module. The GKE target sets `WITH_NVIDIA_PEERMEM=0` for that reason, which selects the DMA-BUF path instead.
- Both targets set the router to KV-aware. On the disaggregated target this is a no-op today, because one decode worker gives the router nothing to choose between. To make it count, raise the decode replicas and add `--kv-events-config` to the decode worker.
- Both targets set `SGLANG_DEFAULT_THINKING=true`. Thinking is off by default for this model, and then `reasoning_content` is empty.
- Both targets keep `--enable-metrics` on and set `DYN_FORWARDPASS_METRIC_PORT` to an empty value. The forward-pass publisher crashes this model on a null `seq_lens_cpu`.
- Both targets pair the native `reasoning-parser` with `--dyn-reasoning-parser`. The native parser gates guided decoding, and Dynamo builds the response. Do not pair the native and Dynamo tool-call parsers. Dynamo rejects that pair.
- The disaggregated target is authored as a Kustomize matrix. Edit `kustomize/base/`, then regenerate with `scripts/kustomize-matrix.py`. Never edit `deploy-generic.yaml` or `deploy-gke-rdma.yaml` by hand.

</div>

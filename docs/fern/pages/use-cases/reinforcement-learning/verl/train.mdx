title: Train with verl and Dynamo on KubeRay

---

A KubeRay `RayJob` describes a Ray cluster and the job to run on it. KubeRay creates the cluster, here a single head Pod with 8 GPUs in Dynamo's vLLM runtime image, then starts a submitter Pod that runs `ray job submit` with the job's entrypoint and streams the driver log. When the job ends, KubeRay deletes the Ray cluster and every process in it.

The entrypoint runs verl's trainer. verl-recipe's Dynamo backend starts etcd, NATS, a Dynamo frontend, and four vLLM engines inside the job, so applying the RayJob starts both Dynamo and training, with no DynamoGraphDeployment. The engines share the GPUs with the trainer. Each training step generates a batch of rollouts through the Dynamo frontend, puts the engines to sleep while Fully Sharded Data Parallel (FSDP) trains the policy, and sends the new weights to the engines over CUDA IPC.

## Prerequisites

- Complete [Installation and Setup](installation.mdx). The commands use its `NAMESPACE` variable.
- Have one node with 8 free GPUs, 64 CPUs, and 800 GiB of memory.
- If your GPU nodes have taints, add matching tolerations to the Ray head's Pod template.

## Start Training

<Steps toc={true}>
  <Step title="Submit the RayJob" id="submit-the-rayjob">

```bash
kubectl apply -n "$NAMESPACE" -f - <<'EOF'
apiVersion: ray.io/v1
kind: RayJob
metadata:
  name: verl-grpo
spec:
  entrypoint: >-  # KubeRay pastes this into a shell script unquoted, so it can't hold comments
    python3 -m verl.trainer.main_ppo
    --config-path /data/verl/recipe/dynamo/config
    --config-name dynamo_trainer_v1_colocate
    hydra.run.dir=/data/runs/verl-grpo/hydra
    algorithm.adv_estimator=grpo
    algorithm.use_kl_in_reward=False
    data.train_files=/data/gsm8k/train.parquet
    data.val_files=/data/gsm8k/test.parquet
    data.train_batch_size=64
    data.max_prompt_length=512
    data.max_response_length=1024
    data.filter_overlong_prompts=True
    data.truncation=error
    actor_rollout_ref.model.path=/data/models/Qwen2.5-7B-Instruct
    actor_rollout_ref.model.use_remove_padding=True
    actor_rollout_ref.model.enable_gradient_checkpointing=True
    actor_rollout_ref.actor.optim.lr=1e-6
    actor_rollout_ref.actor.ppo_mini_batch_size=16
    actor_rollout_ref.actor.ppo_micro_batch_size_per_gpu=4
    actor_rollout_ref.actor.use_kl_loss=True
    actor_rollout_ref.actor.kl_loss_coef=0.001
    actor_rollout_ref.actor.kl_loss_type=low_var_kl
    actor_rollout_ref.actor.entropy_coeff=0
    actor_rollout_ref.actor.fsdp_config.param_offload=False
    actor_rollout_ref.actor.fsdp_config.optimizer_offload=False
    actor_rollout_ref.ref.fsdp_config.param_offload=True
    actor_rollout_ref.ref.log_prob_micro_batch_size_per_gpu=8
    actor_rollout_ref.rollout.name=dynamo
    actor_rollout_ref.rollout.mode=async
    actor_rollout_ref.rollout.tensor_model_parallel_size=2
    actor_rollout_ref.rollout.gpu_memory_utilization=0.6
    actor_rollout_ref.rollout.n=8
    actor_rollout_ref.rollout.calculate_log_probs=True
    actor_rollout_ref.rollout.log_prob_micro_batch_size_per_gpu=8
    ++actor_rollout_ref.rollout.engine_kwargs.dynamo.router_mode=kv
    ++actor_rollout_ref.rollout.engine_kwargs.dynamo.thunderagent.enabled=false
    ++actor_rollout_ref.rollout.engine_kwargs.dynamo.request_engine_data=true
    ++actor_rollout_ref.rollout.engine_kwargs.dynamo.request_completion_token_ids=true
    ++actor_rollout_ref.rollout.engine_kwargs.dynamo.request_timeout_s=1800
    ++actor_rollout_ref.rollout.engine_kwargs.dynamo.free_engine_on_train=true
    ++ray_kwargs.ray_init.runtime_env.env_vars.VERL_DYNAMO_LOG_DIR=/data/runs/verl-grpo/dynamo-logs
    "trainer.logger=[console]"
    trainer.project_name=verl-dynamo
    trainer.experiment_name=gsm8k-grpo
    trainer.n_gpus_per_node=8
    trainer.nnodes=1
    trainer.val_before_train=True
    trainer.test_freq=5
    trainer.save_freq=-1
    trainer.total_training_steps=15
    trainer.default_local_dir=/data/runs/verl-grpo/checkpoints
    trainer.rollout_data_dir=/data/runs/verl-grpo/rollouts
    trainer.validation_data_dir=/data/runs/verl-grpo/validation
  shutdownAfterJobFinishes: true  # Delete the Ray cluster when the job ends
  ttlSecondsAfterFinished: 30     # Wait 30 seconds first
  activeDeadlineSeconds: 3600     # Stop a run that lasts more than an hour
  backoffLimit: 0                 # Don't retry a failed run
  submitterPodTemplate:
    spec:
      restartPolicy: Never
      containers:
        - name: ray-job-submitter
          image: rayproject/ray:2.60.0-py312  # Ray's image: the Dynamo image has no Ray CLI
          resources:
            requests:
              cpu: 200m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi
  rayClusterSpec:
    rayVersion: "2.60.0"  # The Ray version that the setup Job installed
    headGroupSpec:
      rayStartParams: {}
      template:
        spec:
          enableServiceLinks: false  # Keep Service variables out of etcd, NATS, and Dynamo
          containers:
            - name: ray-head
              image: nvcr.io/nvidia/ai-dynamo/vllm-runtime:1.5.1  # Dynamo 1.5.1 with vLLM 0.28.0
              # KubeRay runs this command before its own ray start: install the setup Job's wheels.
              command: ["python3", "-m", "pip", "install", "--quiet", "--no-index", "--no-deps",
                        "--find-links", "/data/wheelhouse", "-r", "/data/wheelhouse/requirements.txt"]
              securityContext:
                runAsUser: 0  # Root, to install the wheels into the image's Python environment
              env:
                - name: PYTHONPATH                 # Import verl and the recipe from the volume
                  value: /data/verl
                - name: VERL_USE_EXTERNAL_MODULES  # Register the recipe's dynamo rollout backend
                  value: recipe.dynamo.register
                - name: VERL_DYNAMO_REFIT_STRICT   # Stop if the weight-update self-test fails
                  value: "1"
                - name: PYTHONUNBUFFERED           # Print each training step when it finishes
                  value: "1"
                - name: HF_HOME                    # Keep the Hugging Face cache on the volume
                  value: /data/hf-home
                - name: POD_IP                     # The Pod's IP address, for DYN_TCP_RPC_HOST
                  valueFrom:
                    fieldRef:
                      fieldPath: status.podIP
                - name: DYN_TCP_RPC_HOST           # Bind Dynamo's request plane to the Pod IP
                  value: $(POD_IP)
              resources:
                requests:
                  cpu: "64"
                  memory: 800Gi
                  nvidia.com/gpu: "8"  # The trainer and the four vLLM engines share the 8 GPUs
                limits:
                  cpu: "64"
                  memory: 800Gi
                  nvidia.com/gpu: "8"
              volumeMounts:
                - name: verl-data
                  mountPath: /data
                - name: dshm
                  mountPath: /dev/shm  # Shared memory for NCCL, vLLM, and the Ray object store
          volumes:
            - name: verl-data
              persistentVolumeClaim:
                claimName: verl-data
            - name: dshm
              emptyDir:
                medium: Memory
                sizeLimit: 256Gi
EOF
```

The entrypoint loads the recipe's `dynamo_trainer_v1_colocate` preset, which runs verl's V1 trainer with the engines and the trainer on the same GPUs. `actor_rollout_ref.rollout.name=dynamo` sends the rollouts through the recipe's Dynamo backend, and the `engine_kwargs.dynamo` keys configure it: KV-aware routing, the generated token IDs in every response, and engines that sleep while FSDP trains. These keys need the `++` prefix, which adds a key that the preset doesn't declare. The other overrides set up GRPO on GSM8K: 64 prompts per step with 8 answers each, 15 steps, and the test accuracy before training and every 5 steps. Because the entrypoint can't hold comments, [verl Configuration](../../../reference/reinforcement-learning/verl-configuration.mdx) describes each override.

  </Step>

```bash
kubectl wait -n "$NAMESPACE" --for=jsonpath='{.status.jobStatus}'=RUNNING rayjob/verl-grpo --timeout=30m
```

1. verl joins the Ray cluster that KubeRay created, instead of starting its own. It then loads the model into 8 FSDP workers, which takes about 3 minutes.
2. The recipe starts etcd and NATS, one `dynamo.vllm` engine on each pair of GPUs, and the frontend with the KV router.
3. All four engines register with the frontend, about 2 minutes later. The recipe tests the weight-update channel to the engines (`refit self-test PASSED`) and sends one request through the frontend to check that the engines return token IDs and log-probabilities (`logprob channel probe OK`).
4. `step:0` reports the accuracy before training. `val-core/openai/gsm8k/acc/mean@1` is the fraction of the 1,319 GSM8K test questions that the model answers correctly.
5. In each step, the recipe pauses the engines (`abort_all_requests`) while FSDP trains, and resumes them after the new weights arrive (`resume_generation`).
6. Each `step:N` line reports one training step. `critic/score/mean` is the mean reward of the step's 512 answers. `rollout_corr/k3_kl` compares the engines' token probabilities with the trainer's. `timing_s/update_weights` is the time to send the new weights to the engines, about 5 seconds.
7. Steps 5, 10, and 15 also report the test accuracy. After step 15, the job succeeds.

Each step takes about 20 seconds, and the whole run about 15 minutes.

Just before `logprob channel probe OK`, the log also shows `ERROR ... [DynamoHttpServer] NO TOKEN IDS in the frontend response (hit #1)`. The probe causes it: the recipe builds the probe's one-token prompt with the function that substitutes for missing token IDs, and that function logs the error. Hits after training starts mean that the engines return no token IDs.

## Routing

The frontend routes with Dynamo's KV router (`router_mode=kv`). The engines publish their KV-cache events through NATS, and GRPO samples each prompt 8 times, so the router can send a prompt's samples to the engine that already holds the prompt's prefix in its KV cache. The recipe also accepts `round-robin`, `random`, and `least-loaded`, and it can route with ThunderAgent, a separate scheduling path, instead. To decide whether KV-aware routing suits your rollouts, see [KV-Aware Load Balancing for RL Rollouts](../routing.md).

## Clean Up

Delete the namespace. This removes the RayJob, the setup Job, and the PersistentVolumeClaim. If the StorageClass uses the `Delete` reclaim policy, the storage provider also deletes the volume with verl, the wheels, and the model:

```bash
kubectl delete namespace "$NAMESPACE"
```

To train again instead, delete only the RayJob, then apply it again. The next run writes to the same directories under `/data/runs/verl-grpo`:

```bash
kubectl delete rayjob verl-grpo -n "$NAMESPACE"
```

## Troubleshooting

| Symptom | Fix |
|---|---|
| The setup Job's Pod is `OOMKilled` while it compiles flash-attn | Each compile job can use about 9 GB of memory. Lower `MAX_JOBS` or raise the Job's memory, then delete the Job and apply it again. |
| The Ray head Pod stays `Pending`, and its events show `volume node affinity conflict` | The volume is zonal, and no GPU node with free GPUs is in its zone. Free GPUs on a node in the volume's zone, or delete the namespace and run the setup again. |
| The job fails with `dynamo frontend not healthy within 600.0s (expected 4 workers; ...)` | One engine never registered with the frontend, which happens in about 1 in 50 launches. Delete the RayJob and apply it again. |
| Loading the model fails in `accelerate/big_modeling.py` with a `TypeError` about `_is_hf_initialized` | The head has the image's accelerate 1.12.0. Check that `/data/wheelhouse/requirements.txt` lists `accelerate==1.13.0`. |
| Hydra fails with `Key 'router_mode' is not in struct` | Prefix each key under `engine_kwargs.dynamo` with `++`. |
| The log shows `NO TOKEN IDS in the frontend response` after training starts | The engines return no token IDs, so verl trains on one-token responses. Keep `request_engine_data=true` and `request_completion_token_ids=true`. |
| The first weight update fails with `ValueError: 'lm_head.weight' was skipped because it is tied to 'model.embed_tokens.weight'` | The model has tied embeddings, and the engines run vLLM 0.29.0 or later. Use the Dynamo 1.5.1 image. |
| The driver log ends with `Exception ignored in atexit callback` and `RuntimeError: DataLoader worker (pid ...) is killed by signal: Killed.` | The message comes from shutdown after training. Check `JOB STATUS` on the RayJob. |

## Current Limitations

- The pages use Dynamo 1.5.1 images, whose vLLM 0.28.0 is the version that the recipe tests. Dynamo 1.6 images ship vLLM 0.31.0. From vLLM 0.29.0 on, the first weight update fails for models with tied embeddings, such as Qwen2.5-0.5B, with the verl commit that the recipe pins. verl fixes this in [verl-project/verl#7973](https://github.com/verl-project/verl/pull/7973), which the pinned commit predates.
- Dynamo runs inside the Ray job, so no operator restarts a failed engine or frontend. The job fails instead.
- The Ray head's dashboard and Jobs API on port 8265 accept requests without authentication, and the recipe runs etcd and NATS without authentication in the same Pod. Anyone who can reach the Pod can run code in it. Restrict access to the Ray head, for example with a NetworkPolicy.
- Each Ray Pod installs the setup Job's wheels when it starts, because the Dynamo image doesn't include Ray or verl.

## Next Steps

- **Keep the trained model.** Set `trainer.save_freq` to a number of steps. verl saves checkpoints to `trainer.default_local_dir` and resumes from the latest one there. Checkpoints of the 7B policy with its optimizer state need a larger volume.
- **Compare routing.** Set `router_mode=round-robin` and compare the runs. See [Routing](#routing).
- **Train on more nodes.** Add a `workerGroupSpecs` group to the RayJob with the same Pod template, use a `ReadWriteMany` volume, and raise `trainer.nnodes`.
- **Try other presets.** The recipe's [README](https://github.com/verl-project/verl-recipe/tree/main/dynamo) covers running without Kubernetes and its other presets: SGLang engines, a separate GPU pool for rollouts, and ThunderAgent routing.

Run one SWE-bench Verified task with Harbor and Pi inside an Agent Substrate
sandbox, then inspect its agent logs and verification results. Use NVIDIA
Dynamo to serve the model, or connect to a compatible external API from a
cluster without GPUs. Optional steps add traces, sandbox metrics, golden
snapshots, and concurrent trials.

The runnable files are in the
[Harbor Substrate example](https://github.com/ai-dynamo/dynamo/tree/main/examples/agents/harbor-substrate).
This tutorial uses pinned dependencies. Keep those pins together when reproducing
it. The [model recipes](../../recipes/model-recipes/overview.mdx) own model
installation and hardware requirements.

<Warning>
This integration is experimental. It includes compatibility patches for the
pinned Pi adapter. Check the installation requirements before allocating
model-serving resources.
</Warning>

## What you build

```mermaid
flowchart LR
    H[Harbor runner with the Substrate adapter] -->|Create and delete actors| C[Substrate control plane]
    H -->|Commands and files over mTLS| R[Substrate router]
    subgraph S[Substrate worker pool]
        A[Actor: guest daemon, Pi, coding tools, and verifier]
    end
    R --> A
    A -->|Model requests| D[Dynamo frontend]
    D --> M[Inference engine]
    A -.->|Alternative| X[External model API]
```

| Component | Responsibility |
| --- | --- |
| **Harbor** | Orchestrates evaluation: selects tasks, limits concurrent trials, runs the agent and task verifier, and collects results. |
| **Pi** | Runs the coding-agent loop inside the sandbox: sends requests to the model, executes its tool calls against the task workspace, and returns tool results to the model. |
| **Substrate** | Provides the sandboxes: places actors on CPU workers, controls their lifecycle and network access, and supports checkpoint and restore. |
| **Dynamo** | Serves model inference outside the sandboxes: accepts Pi's API requests and routes them to the inference engine. A compatible external API can fill this role instead. |

For each trial, Harbor creates a sandbox actor, runs Pi and the task verifier
inside it, collects the results, and deletes the actor. Pi calls the model
endpoint and executes tools against the task workspace. The verifier grades
the resulting solution.

## Check prerequisites

Prepare these resources:

- A local clone of the Dynamo repository.
- A Kubernetes cluster with [Substrate installed and verified](../../kubernetes/agent-sandboxes/install-substrate.mdx#verify-the-installation),
  the pinned `kubectl-ate` CLI on `PATH`, and administrative access.
- Linux x86-64 (`amd64`) or ARM64 (`arm64`) sandbox nodes with capacity for a
  worker requesting 2 CPUs and 6 GiB of memory.
- An image registry for publishing guest and task images. The tutorial assumes
  anonymous image pulls; for private registries, follow
  [Configure image-pull authentication](../../kubernetes/agent-sandboxes/install-substrate.mdx#configure-image-pull-authentication).
- Git, `kubectl`, `curl`, `sha256sum`, OpenSSL, Python 3.12 or newer,
  Docker with BuildKit, Go 1.27 or newer, and `ko` on the preparation workstation.

<Note>
The ARM64 task base image is published, but this tutorial's ARM64 oracle and Pi
runs have not been validated. SWE-bench describes ARM64 support as
[experimental](https://github.com/SWE-bench/SWE-bench/blob/main/README.md).
</Note>

Follow [Install Substrate](../../kubernetes/agent-sandboxes/install-substrate.mdx)
to install and verify the platform.

From the root of your Dynamo clone, enter the tutorial directory:

```bash title="Workstation"
cd examples/agents/harbor-substrate
```

The steps below use the configuration files in this directory. Edit them as
directed.

<Step title="Choose an inference endpoint" id="choose-an-inference-endpoint">

Pi uses the inference endpoint to generate responses and tool calls. We
recommend serving the model with Dynamo so you can capture the inference and
tool traces shown later in this tutorial.

Start with the [GLM-5.3-Flash recipe](../../recipes/model-recipes/glm-5-3-flash.mdx)
for this coding workload, or browse our [model recipes](../../recipes/model-recipes/overview.mdx)
for other models, GPU types, and serving configurations. Choose a model with
reliable tool calling, enough context for repository files and tool results,
and serving requirements that fit your hardware.

Configure Pi's endpoint in `harbor-job.yaml` and allow it in `egress.yaml`.
Substrate denies actor egress by default. The adapter applies `egress.yaml` to
each actor, explicitly allowing Pi to send requests to the model endpoint by
protocol, hostname, and port. Other destinations remain blocked. See
[Substrate egress policies](https://github.com/agent-substrate/substrate/blob/v1.0.0-rc.1/docs/guides/egress-traffic.md)
for details.

<Tabs>
<Tab title="Serve with Dynamo">

Deploy the GLM-5.3-Flash recipe and complete its smoke test. The checked-in
configuration assumes **SGLang aggregated GB200** in namespace `inference`.
For another recipe target, update the served model ID and frontend address
in these excerpts. Keep the remaining settings in each file.

```yaml title="harbor-job.yaml: agents"
agents:
  - import_path: dynamo_pi:DynamoPi
    # Keep "dynamo/" and match the served model ID from /v1/models.
    model_name: dynamo/RadixArk/GLM-5.3-Flash-NVFP4
    kwargs:
      version: "0.72.1"
      thinking: "off"
    env:
      # SGLang aggregated GB200 recipe in namespace inference. Update for your deployment.
      DYNAMO_BASE_URL: http://glm53-flash-sglang-agg-gb200-frontend.inference.svc.cluster.local:8000/v1
      # Blank means "use the context window the endpoint advertises".
      DYNAMO_CONTEXT_WINDOW: ""
      DYNAMO_MAX_TOKENS: "8192"
      # Enable only for a scheduler that consumes session-final notifications.
      DYN_AGENT_SESSION_FINAL: "0"
```

For these recipes, the frontend address is
`http://<dgd-name>-frontend.<namespace>.svc.cluster.local:8000/v1`.
Use an address reachable from the sandbox; your workstation's `localhost`
port-forward address will not work.

The matching egress rule allows HTTP requests to that frontend:

```yaml title="egress.yaml: rules"
rules:
  - http:
      # Hostname only: no scheme or path.
      hostnames:
        - glm53-flash-sglang-agg-gb200-frontend.inference.svc.cluster.local
      ports:
        # Match the endpoint's port.
        numbers: [8000]
```

For a frontend served over HTTPS, use `tlsPassthrough` and its HTTPS port as
shown in the external-endpoint tab.

</Tab>
<Tab title="Use an external endpoint">

No GPU is required in the sandbox cluster. The endpoint must list the selected
model through `GET /models` under its API base URL and support streaming Chat
Completions with tool calls, tool-result continuation, `max_tokens`, and
streaming usage. Keep the `dynamo/` prefix used by the Pi adapter.

Edit the endpoint settings below and keep the rest of `harbor-job.yaml`:

```yaml title="harbor-job.yaml: agents"
agents:
  - import_path: dynamo_pi:DynamoPi
    # Keep the provider prefix; replace your-model-id with the served model ID.
    model_name: dynamo/your-model-id
    kwargs:
      version: "0.72.1"
      thinking: "off"
    env:
      # Use your provider's base URL, including its API prefix.
      DYNAMO_BASE_URL: https://api.example.com/v1
      # Set a quoted token count if the endpoint does not advertise its limit.
      DYNAMO_CONTEXT_WINDOW: ""
      DYNAMO_MAX_TOKENS: "8192"
      # Disable the extra session-final request for external endpoints.
      DYN_AGENT_SESSION_FINAL: "0"
```

Replace the HTTP rule with a TLS-passthrough rule matching your provider's
hostname and port. This permits HTTPS without intercepting its TLS connection:

```yaml title="egress.yaml: rules"
rules:
  - tlsPassthrough:
      # Match DYNAMO_BASE_URL, without the scheme or API path.
      hostnames: ["api.example.com"]
      ports:
        numbers: [443]
```

Supply the API key when [setting up the runner](#prepare-the-harbor-runner).
The first Pi trial checks tool calls and continuation against your endpoint.
Harbor results and sandbox metrics remain available; the Dynamo trace
walkthrough requires a Dynamo endpoint you control.

</Tab>
</Tabs>

Keep `DYN_AGENT_SESSION_FINAL: "0"` for the recommended recipe and external
endpoints. Set it to `"1"` only for a scheduler that consumes session-final
notifications, such as ThunderAgent. It sends an extra request when Pi exits
normally so the scheduler can release session state. Tracing does not require
this notification.

<Accordion title="Configure context and output limits">

`DYNAMO_MAX_TOKENS: "8192"` caps each response at 8,192 tokens.
`DYNAMO_CONTEXT_WINDOW` accepts a quoted token count. When it is blank, the
provider reads `context_window` from the endpoint's model listing, falling
back to 128,000 tokens if absent. Set the value explicitly if your endpoint
does not advertise its limit. Dynamo advertises the engine's serving limit.

</Accordion>

</Step>

<Step title="Configure Harbor access to Substrate" id="create-the-namespace-atespace-and-access-policy">

A Kubernetes namespace and a Substrate atespace are separate objects. This
tutorial uses `ate-env` for both. Run the Substrate commands as an administrator
with global ownership; an atespace-scoped owner cannot create an atespace:

```bash title="Workstation"
kubectl create namespace ate-env
kubectl-ate create atespace ate-env
kubectl-ate create access-policy \
  -a ate-env -f runner-access-policy.yaml
```

The policy grants the runner's ServiceAccount token the editor role on the
atespace. That covers creating and deleting actors, creating egress policies,
and listing templates. The ServiceAccount itself is created with the runner
Pod in the tutorial. If these objects already exist, inspect and reuse them.
For an existing access policy, preserve its current bindings and update with
its `uid` and `version`.

The same ServiceAccount supplies two credentials for different operations:

| Operation | Credential | Authorization control |
| --- | --- | --- |
| Create/delete actors and list templates | Projected token; principal `user:system:serviceaccount:ate-env:harbor-runner` | Atespace access policy (`runner-access-policy.yaml`) |
| Execute guest commands and transfer files | Projected pod certificate with the runner's SPIFFE ID | Router `ingressAllowedSPIFFEIDs` allowlist |

### Configure the router

In the `atenet-router` Deployment's container arguments, append
`spiffe://cluster.local/ns/ate-env/sa/harbor-runner` to the comma-separated
`--ingress-allowed-spiffe-ids` value. Use your installation's trust domain if it
differs from `cluster.local`, and preserve existing identities. If the argument
is absent, add it with this identity as its value.

In the same edit, set `--route-timeout=60m`. The rc1 default is five minutes,
which also bounds guest process-output streams. A 60-minute timeout accommodates
the task's 3,000-second deadlines:

```bash title="Workstation"
kubectl -n ate-system edit deployment atenet-router
kubectl -n ate-system rollout status deployment/atenet-router --timeout=300s
```

Preserve the other arguments. If you change the task deadlines, keep the route
timeout longer than the longest command.

Also add the identity to `ingressAllowedSPIFFEIDs` in `substrate-install.yaml`
(or your installation's managed configuration) so a later deploy preserves it.
For the example's initially empty allowlist, set:

```yaml
ingressAllowedSPIFFEIDs: spiffe://cluster.local/ns/ate-env/sa/harbor-runner
```

The installer accepts a comma-separated string, not a YAML list. Append to
existing identities rather than replacing them. On a shared installation,
have its operator make these changes.

Check the router arguments before creating actors:

```bash title="Workstation"
kubectl -n ate-system get deployment atenet-router \
  -o jsonpath='{.spec.template.spec.containers[*].args}' | tr ' ' '\n' \
  | grep -E 'ingress-allowed-spiffe-ids|route-timeout'
```

The allowlist must include `spiffe://cluster.local/ns/ate-env/sa/harbor-runner`,
and the route timeout must be `60m`. Keep that timeout in the installation's
managed router configuration when updating Substrate.

</Step>

<Step title="Create the worker pool" id="create-sandbox-capacity">

In `workerpool.yaml`, select a node that runs `atelet` and has matching gVisor
runtime assets. Allow capacity for the Harbor runner and Substrate control plane
in addition to the workers. Replace the hostname in the selected tab with that
node's name, and check its architecture:

```bash title="Workstation"
kubectl get node your-sandbox-node \
  -o jsonpath='{.metadata.labels.kubernetes\.io/arch}{"\n"}'
```

Edit the following fields in `workerpool.yaml`. Keep the other fields,
including resources and the `gvisor-default` SandboxConfig reference:

<Tabs>
<Tab title="x86-64 (amd64)">

The node must report `amd64`. Set these worker-pool fields:

```yaml
metadata:
  labels:
    demo.harbor.dev/sandbox: gvisor
    demo.harbor.dev/arch: amd64
spec:
  template:
    nodeSelector:
      kubernetes.io/arch: amd64
      kubernetes.io/hostname: your-amd64-sandbox-node
```

In `actor-template.yaml`, match the pool's architecture label:

```yaml
workerSelector:
  matchLabels:
    demo.harbor.dev/sandbox: gvisor
    demo.harbor.dev/arch: amd64
```

</Tab>
<Tab title="ARM64 (arm64)">

The node must report `arm64`. Set these worker-pool fields:

```yaml
metadata:
  labels:
    demo.harbor.dev/sandbox: gvisor
    demo.harbor.dev/arch: arm64
spec:
  template:
    nodeSelector:
      kubernetes.io/arch: arm64
      kubernetes.io/hostname: your-arm64-sandbox-node
```

In `actor-template.yaml`, match the pool's architecture label:

```yaml
workerSelector:
  matchLabels:
    demo.harbor.dev/sandbox: gvisor
    demo.harbor.dev/arch: arm64
```

</Tab>
</Tabs>

The supplied worker image supports both architectures. Keep its reference:

```yaml
spec:
  workerImage: ghcr.io/agent-substrate/substrate/ateworker-gvisor:v1.0.0-rc.1@sha256:02a31963cdfb1d250d205a55fb870385b1ba5bad1be1308d556a6296f76bf145
```

Keep the initial replica count and resources, then apply the edited file:

```bash title="Workstation"
kubectl apply -f workerpool.yaml
kubectl -n ate-env rollout status \
  deployment/harbor-workers --timeout=600s
```

`spec.replicas` counts worker Pods. The pool's `nodeSelector` places those Pods
on the node you selected. Its resource requests reserve two CPUs and 6 GiB
per worker. The actor template allocates one CPU and 4 GiB per task, leaving
room for one such actor per worker with capacity headroom.

To add nodes, first ensure that `atelet` and runtime assets are present there,
then adjust placement and replica count. To fit more actors per worker,
increase worker capacity while preserving per-actor limits.

The [installation guide](../../kubernetes/agent-sandboxes/install-substrate.mdx#resolve-low-port-permission-failures-when-needed)
includes the conditional low-port permission fix for platforms that need it.

</Step>

<Step title="Prepare the sandbox images" id="prepare-the-sandbox-images">

Build the guest and task images for the worker pool's architecture. The supplied
configuration defaults to `amd64`; use the `arm64` instructions for ARM64 nodes.
Use a native builder or configure
[Docker cross-platform builds](https://docs.docker.com/build/building/multi-platform/).
Prepared task images can be large. Reserve node image-cache space before adding tasks.

```bash title="Workstation"
git clone https://github.com/agent-substrate/env deps/env
```


</Tab>
<Tab title="ARM64 (arm64)">

### Prepare Pi and the task image

Fetch the pinned Pi integration and task dataset:

```bash title="Workstation"
git clone https://github.com/ai-dynamo/agent-plugins deps/agent-plugins
git -C deps/agent-plugins checkout 223a0b8823610d042e7479bfff9b93eeac4a23ec
for patch in pi-provider-limits pi-harbor-adapter; do
	git -C deps/agent-plugins apply < "$patch.patch"
done

git clone https://github.com/harbor-framework/harbor-datasets deps/harbor-datasets
git -C deps/harbor-datasets checkout 86723674f04e4209ac479d0fb75d9d9f44b4377e
export TASK=astropy__astropy-12907
```

The provider patch applies the model limits described above. The adapter patch
detects the prepared runtime, starts the optional TLS tool-event transport, and
otherwise falls back to the upstream installation, which needs registry egress.
The image contains Pi 0.72.1 and its compiled provider. It also holds the
repository's build requirements as wheels and the grader's packages in the uv
cache for this task. The wheel step reads `build-system.requires` from the
repository's `pyproject.toml`; the grader-cache step uses the versions pinned
in `Dockerfile.pi`. Other tasks may need different dependencies or environment
setup. Validate every prepared image with its own offline oracle trial.

The task base image already contains the Astropy checkout and its Conda test
environment. Our build adds Pi and the cached dependencies. Prepare its build
context once:

```bash title="Workstation"
mkdir -p .build/image
cp -a deps/agent-plugins/pi-plugin .build/image/pi-plugin
```

Select the sandbox architecture and replace `registry.example.com/harbor-substrate`
with a repository you can push to and the workers can pull from. Each tab pins
a task base image for that architecture:

In `actor-template.yaml`, replace `containers[0].image` with the pushed
repository and digest, such as `registry.example.com/harbor-substrate/astropy-pi@sha256:...`.
Use the digest printed by `docker push`, not the mutable tag, for the run.
`Dockerfile.pi` defaults to the pinned x86-64 image for this Astropy task;
the ARM64 command overrides that default. For another task, build a separate
prepared image with `--build-arg TASK_IMAGE=...`. Inspect the task's
`environment/Dockerfile` and resolve a base image for the intended architecture
to a digest. Not every task has a published ARM64 image. Changing `--platform`
does not convert an x86-64 base image into ARM64.

Do not reuse one task's repository image for another task. Keep endpoint
credentials, task instructions, candidate changes, and session state outside
the prepared image. Build time and the first image pull are preparation costs.

<Step title="Set up the Harbor runner" id="prepare-the-harbor-runner">

For an authenticated endpoint, provide the key as `DYNAMO_API_KEY`, the name
used by the current Dynamo Pi adapter. The optional Secret reference in
`harbor-runner.yaml` supplies that environment variable. Create the Secret
before starting the runner:

```bash title="Workstation"
read -rsp 'Model API key: ' MODEL_API_KEY
printf '\n'
printf '%s' "$MODEL_API_KEY" | kubectl -n ate-env \
  create secret generic harbor-model-api --from-file=api-key=/dev/stdin
unset MODEL_API_KEY
```

Skip this step for an unauthenticated endpoint. Keep the key out of saved job
files and images. The pinned adapter passes it through Harbor's command
execution environment, which Harbor includes in debug log records. Configure
your logging and artifact handling accordingly before using an authenticated
endpoint. A Kubernetes Secret does not redact those logs. Use a scoped key for
the run and treat captured logs as potentially credential-bearing.

The supplied image in `harbor-runner.yaml` supports both architectures. Start
the runner and install its pinned dependencies:

```bash title="Workstation"
kubectl apply -f harbor-runner.yaml
kubectl -n ate-env wait --for=condition=Ready \
  pod/harbor-runner --timeout=300s
kubectl -n ate-env exec harbor-runner -- \
  mkdir -p /work/example /work/tasks
kubectl -n ate-env cp deps/env/clients/python harbor-runner:/work/env-client
kubectl -n ate-env cp deps/agent-plugins/pi-plugin harbor-runner:/work/pi-plugin
kubectl -n ate-env cp substrate_environment.py harbor-runner:/work/example/substrate_environment.py
kubectl -n ate-env cp runner-kubeconfig.yaml harbor-runner:/work/kubeconfig
kubectl -n ate-env exec harbor-runner -- \
  pip install harbor==0.16.0 /work/env-client
```

`runner-kubeconfig.yaml` selects the in-cluster Kubernetes API and the runner's
projected ServiceAccount token. The Pod sets `KUBECONFIG` to that file. Substrate
uses a separate token projected for the audience `api.ate-system.svc`. The job
passes its file path and the control-plane endpoint to the adapter for
`kubectl-ate`, and the paths of the projected pod certificate and trust bundle
for the router. The env client is installed only for its generated gRPC stubs.
Harbor runs outside the actor. Pi, its tools, and the verifier run inside it.
The runner does not need a Docker daemon.

Download the Substrate CLI for the runner's architecture and verify its checksum:

```bash title="Workstation"
RUNNER_MACHINE="$(kubectl -n ate-env exec harbor-runner -- uname -m)"
case "$RUNNER_MACHINE" in
	x86_64) RUNNER_ARCH=amd64 ;;
	aarch64) RUNNER_ARCH=arm64 ;;
	*) echo "Unsupported runner architecture: $RUNNER_MACHINE" >&2; exit 1 ;;
esac
export RUNNER_ARCH
mkdir -p deps/runner-bin
export ATE_RELEASE=https://github.com/agent-substrate/substrate/releases/download/v1.0.0-rc.1
curl -fL "$ATE_RELEASE/kubectl-ate-linux-$RUNNER_ARCH" -o deps/runner-bin/kubectl-ate
curl -fL "$ATE_RELEASE/kubectl-ate-linux-$RUNNER_ARCH.sha256" -o deps/runner-bin/kubectl-ate.sha256
(cd deps/runner-bin && printf '%s  kubectl-ate\n' "$(cut -d ' ' -f1 kubectl-ate.sha256)" | sha256sum -c -)
chmod +x deps/runner-bin/kubectl-ate
kubectl -n ate-env cp deps/runner-bin/kubectl-ate harbor-runner:/work/kubectl-ate
```

Check the runner's control-plane access:

```bash title="Workstation"
kubectl -n ate-env exec harbor-runner -- \
  /work/kubectl-ate --context in-cluster --endpoint api.ate-system.svc:443 \
  --token-file /var/run/secrets/ateapi/token get actor-templates -a ate-env
```

The command must succeed, even if the template list is empty. It checks the
CLI connection, trust configuration, and the access policy for the runner's
token. A `PermissionDenied` error names the principal that is missing a role.

Upload the egress policy you edited with the inference endpoint:

```bash title="Workstation"
kubectl -n ate-env cp egress.yaml harbor-runner:/work/example/egress.yaml
```

The default policy allows only the model endpoint, so dependency downloads
are blocked. The prepared image carries what the verifier needs, and the
Harbor job tells pip and uv to work offline.

<Accordion title="Allow additional egress">

Add a rule only when a task needs one. Each rule names hosts and ports, and the
gateway decides by protocol:

```yaml
rules:
  - http: # cleartext HTTP, authorized per request
      hostnames: [mirror.example.internal]
      ports:
        numbers: [80]
  - tlsPassthrough: # TLS forwarded by server name, not inspected
      hostnames: [pypi.org, files.pythonhosted.org]
      ports:
        numbers: [443]
  - https: # TLS intercepted by the gateway
      hostnames: [api.example.com]
      ports:
        numbers: [443]
```

An `https` rule requires the actor to trust the gateway's interception CA. The
Substrate guide on
[MITM egress interception](https://github.com/agent-substrate/substrate/blob/v1.0.0-rc.1/docs/guides/egress-trust-bundle.md)
shows the `systemInfo` volume that mounts it. Raw TCP is not supported, which is
why the optional tool-event transport wraps its stream in TLS.

</Accordion>

Opening source hosting lets an agent retrieve an upstream fix, which changes
what a passing benchmark result means. Keep the default policy for results you
intend to compare.

</Step>

<Step title="Register the task and configure the job" id="configure-the-task-template-and-harbor-job">

Open `actor-template.yaml`. Check that `containers[0].image` contains the
prepared task image digest and `volumes[0].image.reference` contains the guest
image digest from the guest-image build step. Keep `metadata.name` as
`swe-astropy-12907-pi` for this first task.
Both image digests must match the architecture selected by `workerSelector`.

The actor template is a Substrate API object. Register it with `kubectl-ate`.
The Harbor job is a client configuration file, consumed by `harbor run`.
Neither file is a Kubernetes Job or a manifest for `kubectl apply`.

In `harbor-job.yaml`, keep the initial one-trial settings and the Astropy
task-to-template mapping. The model settings are the ones you edited earlier:

```yaml
job_name: swe-one
n_attempts: 1
n_concurrent_trials: 1
agents:
  - import_path: dynamo_pi:DynamoPi
    model_name: dynamo/RadixArk/GLM-5.3-Flash-NVFP4
    kwargs:
      version: "0.72.1"
      thinking: "off"
verifier:
  env:
    UV_OFFLINE: "1"
    PIP_NO_INDEX: "1"
    PIP_FIND_LINKS: /opt/wheels
environment:
  import_path: substrate_environment:SubstrateEnvironment
  delete: true
  kwargs:
    template_map:
      astropy__astropy-12907: swe-astropy-12907-pi
tasks:
  - path: /work/tasks/astropy__astropy-12907
```

This excerpt shows the selection fields. Keep the endpoint, environment
variables, and CLI settings from the complete `harbor-job.yaml`. The adapter
reads `/opt/pi-runtime.json` from the image and uses the baked Pi when its
version matches `version`. Without that file it installs Pi, which needs
registry egress and fails under the default policy. The verifier variables point
pip and uv at the wheels and cache in the image, so the unchanged test script
runs without a registry. `delete: true` removes the actor after result
collection.
The task directory name must match a key in `template_map`, and its value must
name the template built for that task. All values under `agents[].env` are strings.

<Accordion title="Actor template and Harbor job fields">

The template defines the sandbox that each trial starts:

| Field | Purpose and adjustment |
| --- | --- |
| `metadata.name` | Identifies this task image and runtime configuration. Choose a new name when either changes. |
| `containers[].image` | Pins the prepared task image. Each task needs its own image. |
| `volumes[].image.reference` | Supplies the environment guest executable mounted at `/ate`. |
| `containers[].wakeupProbe` | Requires the guest's `/readyz` endpoint before the actor is ready. |
| `resources.limits` | Allocates one CPU and 4 GiB to the actor. Increase these limits for tasks that need more resources, and increase worker capacity accordingly. |
| `workerSelector` | Matches the worker pool's sandbox and architecture labels. Keep the architecture aligned with the task and guest images; add placement constraints for prewarming or capacity isolation. |
| `snapshotConfig` | Starts with golden snapshots disabled. Enable them in a separate template after checking the prepared image. |

The job controls the trial lifecycle:

| Field | Purpose and adjustment |
| --- | --- |
| `tasks[].path` | Selects a dataset task copied into the runner. |
| `environment.kwargs.template_map` | Maps each task directory name to its prepared actor template. |
| `agents[].kwargs.version` | Must match the Pi version baked into the task image. |
| `verifier.env` | Directs pip and uv to offline dependencies in that image. |
| `n_concurrent_trials` | Limits whole trials, including setup, verification, and cleanup. Start at one. |
| `environment.delete` | Deletes the actor after artifact collection when `true`. |

</Accordion>

Copy the original task without changing its instructions or verifier. The
selected task retains its 3,000-second agent and verifier deadlines:

```bash title="Workstation"
kubectl -n ate-env cp "deps/harbor-datasets/datasets/swebench-verified/$TASK" "harbor-runner:/work/tasks/$TASK"
kubectl-ate create actor-template -f actor-template.yaml
kubectl-ate get actor-template swe-astropy-12907-pi -a ate-env -o yaml
```

Actor templates are immutable in the pinned Substrate release. To change an
image, resource limit, or snapshot setting, edit a copy, give it a new
`metadata.name`, and create it with the same CLI command. Update the job's
`template_map` to use that name. Keep the old template while existing trials
use it. To change a Harbor job, edit its YAML and upload the file again before
starting a new run. Use a new `job_name` for each run you want to compare.

Upload the configured job:

```bash title="Workstation"
kubectl -n ate-env cp harbor-job.yaml harbor-runner:/work/harbor-job.yaml
```

The template must be listed by the preceding `get` command, and the job's
mapping must name it before you continue.

</Step>

<Step title="Verify the sandbox and task verifier" id="prewarm-and-check-the-environment">

Check actor startup, then run the oracle to verify the task image without
calling a model.

### Start a disposable actor

Open a runner shell:

```bash title="Workstation"
kubectl -n ate-env exec -it harbor-runner -- \
  bash
```

Inside the runner, create a disposable actor, resume it, and watch it start.
Creation leaves the actor suspended; `resume` starts the guest:

```bash title="Harbor runner"
ATE="/work/kubectl-ate --context in-cluster --endpoint api.ate-system.svc:443 --token-file /var/run/secrets/ateapi/token"
$ATE create actor harbor-check-one -a ate-env --template swe-astropy-12907-pi
$ATE resume actor harbor-check-one -a ate-env
$ATE get actor harbor-check-one -a ate-env
```

The first image pull can take several minutes. Repeat the `get` until the
state is `ACTOR_STATE_RUNNING` and a worker Pod is listed. Investigate a start
that takes longer than the job's 1,200-second readiness budget. Then delete
the actor:

```bash title="Harbor runner"
$ATE delete actor harbor-check-one -a ate-env
exit
```

This pulls the image onto the worker that placed the actor and proves that the
template, the access policy, and the worker pool fit together. The oracle below
checks guest execution and the offline verifier. The first Pi trial checks the
prepared Pi runtime and model interaction. Every trial starts a fresh actor;
changes made in one trial's workspace do not carry into the next.

A prepared image avoids repeated package installation. Prewarming caches its
layers on the selected node. When adding nodes, repeat these checks with
placement constrained to each eligible node. A warm image on one worker does
not establish warmth on other workers.

### Check the verifier offline with the oracle

Harbor's oracle agent applies the task's reference patch instead of calling a
model, then the verifier runs as usual. Under the default egress policy, a
reward of 1 proves that the image and the job carry everything the verifier
needs. Copy the job on the workstation:

```bash title="Workstation"
cp harbor-job.yaml oracle-job.yaml
```

In `oracle-job.yaml`, set `job_name: swe-oracle` and replace the `agents` list
with the built-in agent:

```yaml
agents:
  - name: oracle
```

Upload and run it, then read the reward:

```bash title="Workstation"
kubectl -n ate-env cp oracle-job.yaml harbor-runner:/work/oracle-job.yaml
kubectl -n ate-env exec harbor-runner -- \
  harbor run --config /work/oracle-job.yaml -y
kubectl -n ate-env exec harbor-runner -- \
  sh -c 'cat /work/jobs/swe-oracle/*/verifier/reward.txt'
```

Expected reward:

```text title="Expected output"
1
```

Require a reward of 1 before running Pi. If the oracle fails, inspect the trial's
`result.json`, `exception_info`, and `verifier/test-stdout.txt`. Missing packages,
egress restrictions, timeouts, or task failures can cause an unsuccessful run;
no model was called. Repeat this check for every new task image.

</Step>

Retain the edited job YAML, templates, policies, dataset revision, and result

| Artifact | What to check |
| --- | --- |
| `result.json` | Trial outcome and `exception_info`; investigate setup or execution exceptions. |
| `substrate.json` | Actor identity for matching this trial to Substrate activity. |
| `substrate-timing.jsonl` | Time spent in environment preparation phases. |
| `agent/pi.txt` | Raw Pi events: a tool call, its result, and a subsequent model request; inspect assistant errors. |

Before continuing, confirm that:

- `result.json` contains no setup or execution exception.
- `agent/pi.txt` shows a tool call, its result, and a subsequent model request,
  without assistant errors.
- The `verifier/` directory contains the verifier output and reward.

worked. A single task result does not establish full-dataset accuracy. Repeat
this check after changing an endpoint, dependency, image, or cluster configuration.

### Optionally restore from a golden snapshot

This optional feature uses the object storage configured during Substrate
installation. With the default setup, golden snapshots go to
`s3://ate-snapshots/` in RustFS; no additional storage deployment is needed.
If you use remote S3 or GCS, verify that the configured bucket and credentials
are working before enabling snapshots.

Create separate files for the optional golden configuration on the workstation:

```bash title="Workstation"
cp actor-template.yaml golden-template.yaml
cp harbor-job.yaml golden-job.yaml
```

In `golden-template.yaml`, change `metadata.name` to
`swe-astropy-12907-pi-golden` and set:

```yaml
snapshotConfig:
  preferredFidelity: SNAPSHOT_FIDELITY_MEMORY
  goldenSnapshotConfig:
    mode: GOLDEN_SNAPSHOT_MODE_ENABLED
```

In `golden-job.yaml`, set `job_name: swe-golden` and map
`astropy__astropy-12907` to `swe-astropy-12907-pi-golden`. Create and inspect the
template:

```bash title="Workstation"
kubectl-ate create actor-template -f golden-template.yaml
kubectl-ate get actor-template swe-astropy-12907-pi-golden -a ate-env -o json
```

Read `status.goldenSnapshotStatus.goldenTag`, then fetch that tag:

```bash title="Workstation"
export GOLDEN_TAG=the-tag-from-template-status
kubectl-ate get tag "$GOLDEN_TAG" -a ate-env -o json
```

Wait for `status.snapshot.durableSnapshot.state` to become
`SNAPSHOT_STORAGE_STATE_COMPLETED`, and require `SNAPSHOT_FIDELITY_MEMORY`.
Repeat the prewarm actor creation, resume, status check, and deletion with
`--template swe-astropy-12907-pi-golden`. Then upload and run the golden job:


Golden snapshots reuse initial sandbox state. The prepared guest snapshot does

### Increase concurrency

On the workstation, repeat the image build and template
creation for each task. Give every template its own name, copy the corresponding
dataset directories to `/work/tasks`, and add each task to both `tasks` and
`environment.kwargs.template_map` in a copy of the job YAML. Keep each image
digest in its template.

Copy the job before configuring a batch:

```bash title="Workstation"
cp harbor-job.yaml batch-job.yaml
```

For a two-task batch, set `job_name: swe-batch` and
`n_concurrent_trials: 2` in `batch-job.yaml`. In `workerpool.yaml`, set
`spec.replicas: 2` to provide two workers. Apply the pool, upload the edited
job, and run it:

```bash title="Workstation"
kubectl apply -f workerpool.yaml
kubectl -n ate-env rollout status deployment/harbor-workers --timeout=600s
kubectl -n ate-env cp batch-job.yaml harbor-runner:/work/batch-job.yaml
kubectl -n ate-env exec harbor-runner -- \
  harbor run --config /work/batch-job.yaml -y
```

The selected node needs capacity for both worker Pods. Prewarm each additional
task image and validate any golden snapshots before starting the batch. Start
with a small task selection before expanding to the full Verified dataset.

A Harbor concurrency slot covers environment setup, agent setup, execution,
verification, and cleanup. It is not a count of simultaneous model requests.
Worker capacity limits resident actors, while the inference service has its own
request limit. This example keeps actors resident through each trial. It does
not automatically suspend Pi between model calls.

Repeat [Save and inspect the results](#save-and-inspect-the-results) with
`JOB_NAME=swe-batch`. Inspect each trial before adding more tasks or workers.

```bash title="Workstation"

kubectl -n ate-env delete pod harbor-runner
kubectl -n ate-env delete workerpool harbor-workers
```

for this walkthrough. Keep shared Substrate services, storage, and inference
endpoints. Follow the metrics guide's restore procedure before removing the
Collector. If you added tracing to an existing frontend, remove the tutorial's
trace additions by comparing with `.build/frontend-before.yaml`. For Kustomize,
remove those additions from the source or overlay and regenerate the manifest.
Apply the updated frontend manifest and stop the local viewer.

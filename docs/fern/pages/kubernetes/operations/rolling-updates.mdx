Update the workers of a running NVIDIA Dynamo `DynamoGraphDeployment` (DGD), check that the new workers are serving, and restore the previous configuration if needed. For generation routing and controller behavior, see [Rolling Update Architecture](../../developer-guide/knowledge-base/concepts/system-architecture/rolling-updates.md).

## Before You Start

- Start with a healthy DGD and its manifest in version control. If you need a deployment first, follow [Model Deployment](../model-deployment/introduction.mdx).
- Identify the backing resource for your workers: Deployment, Grove PodCliqueSet, or LeaderWorkerSet (LWS). Check `status.components` below; Grove components appear as `PodClique` or `PodCliqueScalingGroup`. See [Multinode Orchestration](../installation/multinode-orchestration.md) for provider selection.
- For Grove, this walkthrough assumes `RollingRecreate`. If you selected `OnDelete`, updates require manual pod replacement; see the [strategy reference](../../reference/kubernetes-api/dynamo-graph-deployment.mdx#rolling-update-controls).

The example uses a running disaggregated vLLM DGD named `vllm-disagg` in namespace `dynamo`, with components named `Frontend`, `PrefillWorker`, and `DecodeWorker`. Its source manifest is `vllm-disagg.yaml`. Substitute your deployment, namespace, and component names in the commands.

```bash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.components}{"\n"}'
```

<Note>
Changing any worker pod template rolls all worker components, including workers whose configuration did not change. Keep the frontend configuration unchanged for this procedure.
</Note>

## Plan the Rollout

### Capacity and Spare GPUs

<Anchor id="capacity-during-the-rollout" />
<Anchor id="control-the-pace" />
<Anchor id="deployment-backed-workers-1" />
<Anchor id="grove-backed-workers-1" />
<Anchor id="lws-backed-workers-1" />

Choose a budget for each worker component before editing the manifest:

| Backing resource | Plan | Capacity and GPU requirement |
|---|---|---|
| Deployment | `maxSurge: "1"`, `maxUnavailable: "0"` | Keep the desired number of available workers; reserve GPUs for one extra worker per component. |
| Deployment | `maxSurge: "0"`, `maxUnavailable: "1"` | Reuse existing GPUs; accept one unavailable worker per component, including an outage for a single-replica component. |
| Grove or LWS | At least two replicas per worker component | There is no surge; reserve enough serving capacity to tolerate replacement of a pod or replica. |

A surge worker needs its requested GPUs on one node. For example, a worker requesting four GPUs needs four free GPUs on a single node for its replacement to start before it exits. A smaller unavailable budget disturbs less capacity at once but can make the rollout take longer.

Set Deployment budgets with the annotations shown in the update procedure. For supported values, defaults, and annotation locations, see [Rolling Update Controls](../../reference/kubernetes-api/dynamo-graph-deployment.mdx#rolling-update-controls).

<Anchor id="zero-downtime-updates" />

<Tip>
To retain serving capacity, keep `replicas - maxUnavailable` at least 1 for Deployment-backed workers, and use at least two replicas per worker component with Grove or LWS. Avoid `Recreate` when an outage is unacceptable.

For disaggregated serving, replica counts alone do not guarantee uninterrupted service: a routable generation needs both prefill and decode workers. Check application traffic throughout the update. See [generation readiness](../../developer-guide/knowledge-base/concepts/system-architecture/rolling-updates.md#readiness-gates).
</Tip>

<Anchor id="warm-up-and-latency" />

<Note>
Roll during low traffic when possible. Replacement workers can start with an empty KV cache, so allow for higher latency while they warm up. See [KV Cache Offloading](../kv-cache-offloading/overview.mdx) if you rely on cache reuse across pods.
</Note>

### Request Draining

Check request durations and the current pods' shutdown settings before starting. Follow [Graceful Shutdown](../fault-tolerance/graceful-shutdown.md) for drain configuration and [Request Migration](../fault-tolerance/request-migration.md) if interrupted requests need recovery.

## Update the Workers

<Steps toc={true} tocDepth={3}>

<Step title="Prepare workers to drain" id="graceful-shutdown">

Check whether each worker's `podTemplate.spec.terminationGracePeriodSeconds` accommodates your request durations and cleanup time. Use the worker's P99 request duration as a starting point and add a buffer; configure the internal drain timeouts using the [graceful shutdown guide](../fault-tolerance/graceful-shutdown.md).

If changes are needed, make them in `vllm-disagg.yaml` before applying it in step 3. New settings apply to replacement pods; existing pods drain using their current settings.

</Step>

<Step title="Edit the worker configuration">

In the same manifest, add `--max-model-len, "32768"` to the `DecodeWorker` main container's existing `args` list. Preserve its other arguments, resource requests, and shutdown settings. Check that the model and GPU memory support the new context length.

For Deployment-backed workers, merge the budget selected above into each worker's `podTemplate.metadata.annotations`. This example keeps the desired number of available workers and permits one extra worker per component:

```yaml
podTemplate:
  metadata:
    annotations:
      nvidia.com/deployment-rolling-update-max-surge: "1"
      nvidia.com/deployment-rolling-update-max-unavailable: "0"
```

Grove and LWS do not use these Deployment annotations. Keep their replica counts consistent with the capacity plan.

</Step>

<Step title="Apply the updated manifest">

```bash
kubectl apply -n dynamo -f vllm-disagg.yaml
```

Both worker components roll, even when only the decode configuration changes. The frontend does not restart when its pod template is unchanged.

</Step>

<Step title="Verify the rollout" id="watch-the-rollout">

Inspect pod readiness and the generation label; rerun these commands as the rollout progresses:

```bash
kubectl get pods -n dynamo -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg \
  -L nvidia.com/dynamo-worker-hash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.state}{"\n"}'
```

Select the progress check for your backing resource:

<Tabs>
<Tab title="Deployment">

<Anchor id="deployment-backed-workers" />

```bash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.rollingUpdate}{"\n"}'
```

Expect `Pending`, then `InProgress`, then `Completed`. `updatedComponents` lists worker components that have finished.

</Tab>
<Tab title="Grove">

<Anchor id="grove-backed-workers" />

```bash
kubectl get podcliqueset vllm-disagg -n dynamo -o jsonpath='{.status.updateProgress}{"\n"}'
```

Check the current update's progress; `updateEndedAt` is set when Grove finishes replacing pods. Also verify pod readiness and generation labels.

</Tab>
<Tab title="LWS">

<Anchor id="lws-backed-workers" />

```bash
kubectl get leaderworkerset -n dynamo -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg
```

Check each worker's LeaderWorkerSet for ready and updated replicas, alongside pod readiness and generation labels.

</Tab>
</Tabs>

When the backing controller finishes, confirm `status.state` is `successful`, the expected worker replicas are Ready, and all worker pods carry the new generation hash. Inspect the completed generation with:

```bash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.metadata.annotations.nvidia\.com/current-worker-hash-v2}{"\n"}'
```

Keep sending requests through your application during the update. Confirm requests succeed and latency recovers before treating the update as complete.

</Step>
</Steps>

## Roll Back

<Warning>
For Deployment-backed workers, rolling back an update that is still in progress requires operator 1.5.0 or later. Earlier releases could delete the serving generation during a mid-rollout rollback.
</Warning>

<Steps toc={true} tocDepth={3}>

<Step title="Restore the previous manifest">

Retrieve the last known-good `vllm-disagg.yaml` from version control, including its worker pod templates and rollout settings.

</Step>

<Step title="Apply the previous manifest">

```bash
kubectl apply -n dynamo -f vllm-disagg.yaml
```

Rollback replaces workers through the same mechanism as a forward update. Allow for model loading and draining time.

</Step>

<Step title="Verify recovery">

Repeat [Verify the rollout](#watch-the-rollout). Confirm the backing controller has finished, the expected worker replicas are Ready on the restored generation, and application requests succeed.

</Step>
</Steps>

## Troubleshoot a Stalled Rollout

Inspect the DGD and pods before changing the rollout budget:

```bash
kubectl describe dgd vllm-disagg -n dynamo
kubectl describe pods -n dynamo -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg
```

| Symptom | Check |
|---|---|
| Replacement pods remain Pending | Read scheduling events; verify spare GPUs, placement constraints, and volume availability. |
| Pods start but do not become Ready | Read worker logs and probe failures; check model loading and the changed engine arguments. |
| Old pods remain Terminating | Inspect their drain logs and termination grace periods; forced deletion can interrupt requests. |
| Grove templates change but pods do not | Check whether `nvidia.com/grove-update-strategy` is `OnDelete`, which requires manual replacement. |
| Ready workers exist but requests fail | Check that prefill and decode are available in the same generation and inspect frontend discovery/routing logs. |
| A `RollingUpdateNotSupported` event appears | On Grove or LWS, use that controller's progress checks; the event means Dynamo's managed Deployment rollout does not apply. |

See [Health Checks](../../reference/observability/health-checks.mdx) for probe behavior and [Graceful Shutdown](../fault-tolerance/graceful-shutdown.md) for draining diagnostics.

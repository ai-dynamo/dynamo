This guide shows how to plan and perform zero-downtime updates to a `DynamoGraphDeployment` (DGD), roll back safely, and troubleshoot a stalled rollout. It covers worker and frontend updates, availability requirements, and version compatibility. For details on the design and architecture of NVIDIA Dynamo DGD rolling updates, see [Rolling Update Architecture](../../developer-guide/knowledge-base/concepts/system-architecture/rolling-updates.md).

## Before You Start

- Start with a healthy DGD and its manifest in version control. If you need a deployment first, follow [Model Deployment](../model-deployment/introduction.mdx).
- Record the current operator version and the current, target, and rollback runtime versions of each component.
- Identify the backing resources for your workers and frontend. Workers use Deployment, Grove, or LeaderWorkerSet (LWS); frontends use Deployment or Grove. Check `status.components` below; Grove components appear as `PodClique` or `PodCliqueScalingGroup`. See [Multinode Orchestration](../installation/multinode-orchestration.md) for provider selection.
- For Grove, this walkthrough assumes `RollingRecreate`. If you selected `OnDelete`, updates require manual pod replacement; see the [strategy reference](../../reference/kubernetes-api/dynamo-graph-deployment.mdx#rolling-update-controls).

The example uses a running disaggregated vLLM DGD named `vllm-disagg` in namespace `dynamo`, with components named `Frontend`, `PrefillWorker`, and `DecodeWorker`. Its source manifest is `vllm-disagg.yaml`. Substitute your deployment, namespace, and component names in the commands.

```bash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.components}{"\n"}'
```

<Note>
Changing any worker pod template rolls all worker components, including workers whose configuration did not change. A frontend-only change does not create a new worker generation.
</Note>

## Plan the Rollout

### Check Version Compatibility

Check every combination that will exist during the update and rollback, including old and new runtime versions running at the same time.

- **Operator and runtime:** the operator supports Dynamo runtimes within an N−2 window: its release line and the two preceding release lines. Both the current and target frontend and worker runtimes, as well as the rollback versions, must fall within that window. If necessary, upgrade the operator first, checking that it still supports the runtimes already serving traffic; use intermediate releases when a single upgrade would exceed the window.
- **Frontend and workers:** mixed versions are supported across the current release line and the two preceding release lines, in either age direction. Check [Mixed-Version Compatibility](../../reference/general/compatibility.mdx#mixed-version-compatibility) for the supported scope and feature-specific exceptions.
- **Prefill and decode:** when changing their protocol or backend/runtime combination, update prefill and decode together in the same DGD manifest. They form one new worker generation, isolated from the old generation. The existing generation can continue serving while the replacement becomes ready, subject to the capacity plan below. See [Generation Isolation](../../developer-guide/knowledge-base/concepts/system-architecture/rolling-updates.md#generation-isolation) for the design.

When changing a runtime image, update its `runtimeVersionOverride` in the same change, or remove the override if the image tag correctly identifies the contained Dynamo runtime. For sidecar workers, use the version of the `runtime` init container, not the engine image. See [Runtime Version Compatibility](../../reference/kubernetes-api/dynamo-component-deployment.mdx#runtime-version-compatibility).

### Choose the Update Order

Frontend and worker updates can run in parallel. During live traffic, update them separately and verify each rollout before starting the next. Choose frontend-first or workers-first based on the compatible intermediate versions and features identified above.

For a worker rollout, keep the frontend pod template unchanged. For a frontend rollout, preserve the current worker configuration. Keep a known-good manifest after each successful stage so rollback can target the affected components.

### Capacity and Spare GPUs

<Anchor id="capacity-during-the-rollout" />
<Anchor id="control-the-pace" />
<Anchor id="deployment-backed-workers-1" />
<Anchor id="grove-backed-workers-1" />
<Anchor id="lws-backed-workers-1" />

Choose a budget for each worker component before editing the manifest:

| Backing resource | Plan | Capacity and GPU requirement |
|---|---|---|
| Deployment | `maxSurge: "1"`, `maxUnavailable: "0"` | Keep the desired number of available workers; reserve GPUs for one extra worker per component. |
| Deployment | `maxSurge: "0"`, `maxUnavailable: "1"` | Reuse existing GPUs; accept one unavailable worker per component, including an outage for a single-replica component. |
| Grove or LWS | At least two replicas per worker component | There is no surge; reserve enough serving capacity to tolerate replacement of a pod or replica. |

A surge worker needs its requested GPUs on one node. For example, a worker requesting four GPUs needs four free GPUs on a single node for its replacement to start before it exits. A smaller unavailable budget disturbs less capacity at once but can make the rollout take longer.

Set Deployment budgets with the annotations shown in the update procedure. For supported values, defaults, and annotation locations, see [Rolling Update Controls](../../reference/kubernetes-api/dynamo-graph-deployment.mdx#rolling-update-controls).

Keep enough Ready frontend replicas behind the Service or load balancer to carry live traffic during replacement. For Deployment-backed frontends, use `maxUnavailable: "0"` and `maxSurge: "1"` and reserve the CPU and memory for the extra pod. For Grove frontends, use at least two replicas because there is no surge; scale up and wait for readiness before changing the image.

<Anchor id="zero-downtime-updates" />

<Tip>
To retain serving capacity, keep `replicas - maxUnavailable` at least 1 for Deployment-backed workers, and use at least two replicas per worker component with Grove or LWS. Avoid `Recreate` when an outage is unacceptable.

For disaggregated serving, replica counts alone do not guarantee uninterrupted service: a routable generation needs both prefill and decode workers. Check application traffic throughout the update. See [generation readiness](../../developer-guide/knowledge-base/concepts/system-architecture/rolling-updates.md#readiness-gates).
</Tip>

<Anchor id="warm-up-and-latency" />

<Note>
Roll during low traffic when possible. Replacement workers can start with an empty KV cache, so allow for higher latency while they warm up. See [KV Cache Offloading](../kv-cache-offloading/overview.mdx) if you rely on cache reuse across pods.
</Note>

### Request Draining

Check request durations and the current pods' shutdown settings before starting. Follow [Graceful Shutdown](../fault-tolerance/graceful-shutdown.md) for worker draining and the frontend's HTTP/streaming drain timeout. Allow frontend requests to finish within `DYN_HTTP_GRACEFUL_SHUTDOWN_TIMEOUT_SECS`, with enough additional pod termination time for cleanup.

Readiness must remove draining frontends from new traffic while healthy replicas remain reachable. New frontend replicas do not take over existing client connections. [Request Migration](../fault-tolerance/request-migration.md) can recover eligible worker interruptions; it does not preserve a stream whose frontend connection has closed.

## Update the Workers

<Steps toc={true} tocDepth={3}>

<Step title="Prepare workers to drain" id="graceful-shutdown">

Check whether each worker's `podTemplate.spec.terminationGracePeriodSeconds` accommodates your request durations and cleanup time. Use the worker's P99 request duration as a starting point and add a buffer; configure the internal drain timeouts using the [graceful shutdown guide](../fault-tolerance/graceful-shutdown.md).

If changes are needed, make them in `vllm-disagg.yaml` before applying it in step 3. New settings apply to replacement pods; existing pods drain using their current settings.

</Step>

<Step title="Edit the worker configuration">

For a configuration-only example, add `--max-model-len, "32768"` to the `DecodeWorker` main container's existing `args` list in the same manifest. Preserve its other arguments, resource requests, and shutdown settings. Check that the model and GPU memory support the new context length.

For a protocol or backend/runtime upgrade, instead update both `PrefillWorker` and `DecodeWorker` images and any associated version overrides in this edit. Apply them together in step 3; do not apply a prefill-only intermediate manifest for that upgrade.

For Deployment-backed workers, merge the budget selected above into each worker's `podTemplate.metadata.annotations`. This example keeps the desired number of available workers and permits one extra worker per component:

```yaml
podTemplate:
  metadata:
    annotations:
      nvidia.com/deployment-strategy: RollingUpdate
      nvidia.com/deployment-rolling-update-max-surge: "1"
      nvidia.com/deployment-rolling-update-max-unavailable: "0"
```

Grove and LWS do not use these Deployment annotations. Keep their replica counts consistent with the capacity plan.

</Step>

<Step title="Apply the updated manifest">

```bash
kubectl apply -n dynamo -f vllm-disagg.yaml
```

Both worker components roll, even when only the decode configuration changes. The frontend does not restart when its pod template is unchanged.

</Step>

<Step title="Verify the rollout" id="watch-the-rollout">

Inspect pod readiness and the generation label; rerun these commands as the rollout progresses:

```bash
kubectl get pods -n dynamo -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg \
  -L nvidia.com/dynamo-worker-hash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.state}{"\n"}'
```

Select the progress check for your backing resource:

<Tabs>
<Tab title="Deployment">

<Anchor id="deployment-backed-workers" />

```bash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.rollingUpdate}{"\n"}'
```

Expect `Pending`, then `InProgress`, then `Completed`. `updatedComponents` lists worker components that have finished.

</Tab>
<Tab title="Grove">

<Anchor id="grove-backed-workers" />

```bash
kubectl get podcliqueset vllm-disagg -n dynamo -o jsonpath='{.status.updateProgress}{"\n"}'
```

Check the current update's progress; `updateEndedAt` is set when Grove finishes replacing pods. Also verify pod readiness and generation labels.

</Tab>
<Tab title="LWS">

<Anchor id="lws-backed-workers" />

```bash
kubectl get leaderworkerset -n dynamo -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg
```

Check each worker's LeaderWorkerSet for ready and updated replicas, alongside pod readiness and generation labels.

</Tab>
</Tabs>

When the backing controller finishes, confirm `status.state` is `successful`, the expected worker replicas are Ready, and all worker pods carry the new generation hash. Inspect the completed generation with:

```bash
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.metadata.annotations.nvidia\.com/current-worker-hash-v2}{"\n"}'
```

Keep sending requests through your application during the update. Confirm requests succeed and latency recovers before treating the update as complete.

</Step>
</Steps>

## Update the Frontend

Use this procedure for a separate frontend rollout after completing any worker rollout, or before it when the planned intermediate versions are compatible. Keep worker templates unchanged.

<Steps toc={true} tocDepth={3}>

<Step title="Prepare frontend capacity and draining">

Confirm the remaining Ready frontend replicas can carry the traffic while one is replaced. If you need more replicas, increase the `Frontend` component's `replicas` in the manifest, apply it, and wait for those replicas to become Ready before changing the image. Grove requires at least two replicas for replacement without a frontend availability gap.

For a Deployment-backed frontend, merge these settings into the `Frontend` component's `podTemplate.metadata.annotations`, preserving other annotations:

```yaml
nvidia.com/deployment-strategy: RollingUpdate
nvidia.com/deployment-rolling-update-max-surge: "1"
nvidia.com/deployment-rolling-update-max-unavailable: "0"
```

Check the existing frontend pods' HTTP drain timeout and termination grace period against long-running and streaming requests. Timeout changes in the manifest affect replacement pods; existing pods still drain using their current settings.

</Step>

<Step title="Edit the frontend configuration">

In `vllm-disagg.yaml`, change the `Frontend` component's `podTemplate.spec.containers[name=main].image` or the intended frontend arguments. Preserve worker templates and other frontend settings. If the Dynamo runtime version changes, align any `runtimeVersionOverride` and confirm compatibility with every worker version that the frontend will discover.

</Step>

<Step title="Apply the frontend update">

```bash
kubectl apply -n dynamo -f vllm-disagg.yaml
```

Only the frontend's backing workload rolls when only its pod template changes. A frontend rollout does not advance the worker generation.

</Step>

<Step title="Verify the frontend rollout" id="verify-the-frontend-rollout">

Inspect the frontend pods and component status:

```bash
kubectl get pods -n dynamo \
  -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg,nvidia.com/dynamo-component=Frontend
kubectl get dgd vllm-disagg -n dynamo -o jsonpath='{.status.components.Frontend}{"\n"}'
```

<Tabs>
<Tab title="Deployment">

```bash
kubectl rollout status deployment -n dynamo \
  -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg,nvidia.com/dynamo-component=Frontend \
  --timeout=10m
```

</Tab>
<Tab title="Grove">

```bash
kubectl get podclique -n dynamo \
  -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg,nvidia.com/dynamo-component=Frontend \
  -o yaml
```

Check the frontend PodClique's observed generation and ready/updated replica counts against its desired state.

</Tab>
</Tabs>

Confirm all desired frontend replicas are Ready with the intended configuration. Through the normal Service or load-balancer endpoint, verify model discovery, new inference requests, and completion of requests and streams admitted before the update. Check error rates and latency throughout replacement.

`status.rollingUpdate` tracks Dynamo's managed worker rollout, not frontend replacement. Use the frontend's backing workload status and application traffic to verify this update.

</Step>
</Steps>

## Roll Back

<Warning>
For Deployment-backed workers, rolling back an update that is still in progress requires operator 1.5.0 or later. Earlier releases could delete the serving generation during a mid-rollout rollback.
</Warning>

<Steps toc={true} tocDepth={3}>

<Step title="Restore the previous manifest">

Restore the affected components from the last known-good `vllm-disagg.yaml`, including their image, arguments, version overrides, and rollout settings. Preserve unrelated successful changes. Roll back prefill and decode together after a protocol or backend/runtime upgrade.

Recheck compatibility with the operator and every component that remains upgraded. If restoring only one stage would exceed a supported version window, plan a compatible sequence of reversions rather than applying that intermediate combination.

</Step>

<Step title="Apply the previous manifest">

```bash
kubectl apply -n dynamo -f vllm-disagg.yaml
```

Rollback replaces the affected workers or frontend through the same mechanism as a forward update. Allow for draining and, for workers, model loading.

</Step>

<Step title="Verify recovery">

For workers, repeat [Verify the rollout](#watch-the-rollout) and confirm the expected replicas are Ready on the restored generation. For the frontend, repeat [Verify the frontend rollout](#verify-the-frontend-rollout). In both cases, confirm the backing controller has finished and application requests succeed.

</Step>
</Steps>

## Troubleshoot a Stalled Rollout

Inspect the DGD and pods before changing the rollout budget:

```bash
kubectl describe dgd vllm-disagg -n dynamo
kubectl describe pods -n dynamo -l nvidia.com/dynamo-graph-deployment-name=vllm-disagg
```

| Symptom | Check |
|---|---|
| Replacement pods remain Pending | Read scheduling events; verify spare GPUs, placement constraints, and volume availability. |
| Pods start but do not become Ready | Read worker logs and probe failures; check model loading and the changed engine arguments. |
| Frontend replacement stalls | Check its backing workload, CPU/memory scheduling, and readiness failures; worker `status.rollingUpdate` does not track this update. |
| Old pods remain Terminating | Inspect their drain logs and termination grace periods; forced deletion can interrupt requests. |
| Grove templates change but pods do not | Check whether `nvidia.com/grove-update-strategy` is `OnDelete`, which requires manual replacement. |
| Ready workers exist but requests fail | Check that prefill and decode are available in the same generation and inspect frontend discovery/routing logs. |
| Discovery or protocol errors appear after a version change | Recheck operator/runtime and frontend/worker compatibility, actual image versions, and `runtimeVersionOverride`; confirm prefill and decode were upgraded together. |
| Streams disconnect during frontend replacement | Inspect HTTP drain timeouts, pod termination, and load-balancer connection draining; Ready replacement pods cannot resume an existing client connection. |
| A `RollingUpdateNotSupported` event appears | On Grove or LWS, use that controller's progress checks; the event means Dynamo's managed Deployment rollout does not apply. |

See [Health Checks](../../reference/observability/health-checks.mdx) for probe behavior and [Graceful Shutdown](../fault-tolerance/graceful-shutdown.md) for draining diagnostics.

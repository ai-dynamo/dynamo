This guide covers an alternative EFA setup for Dynamo on EKS using
[DRANET](https://github.com/kubernetes-sigs/dranet) — the Kubernetes DRA-native network
driver — instead of the [EFA device plugin](efa-on-aws.mdx). Both approaches provide
GPU-Direct RDMA over EFA for KV cache transfer; this guide adds topology-awareness: the
DRA scheduler guarantees each worker's EFA interfaces share a PCIe root complex with its
GPU, eliminating PCIe crossings on every KV cache transfer.

For background on why RDMA matters for Dynamo disaggregated inference, see
[RDMA Setup](overview.md). For the device plugin approach (no k8s version requirement,
simpler setup), see [EFA on EKS](efa-on-aws.mdx).

## When to Use This Guide

| | Device plugin ([efa-on-aws.mdx](efa-on-aws.mdx)) | DRANET (this guide) |
|---|---|---|
| Kubernetes version | Any EKS version | **1.34+** |
| GPU scheduling | `nvidia.com/gpu` device plugin | `gpu.nvidia.com` DRA driver |
| EFA scheduling | `vpc.amazonaws.com/efa` (random allocation) | `efa.networking.k8s.aws` (topology-aware) |
| GPU + EFA co-location | Not guaranteed | Guaranteed via `pcieRoot` constraint |
| Pod security | `privileged: true` required | Not required |
| Coexistence | Device plugin must be present | Replaces device plugin for both GPU and EFA |

Choose DRANET when you are on k8s 1.34+ and want the scheduler to atomically allocate a
GPU and its co-located EFAs. On p5.48xlarge each H100 GPU shares a PCIe root complex with
exactly 4 EFA NICs; assigning a worker's EFAs from a different PCIe root adds a PCIe
crossing to every KV cache transfer.

## Prerequisites

**Supported GPU instance types** — same as [efa-on-aws.mdx](efa-on-aws.mdx):

| Instance family                | GPU              | Aggregate EFA bandwidth | Arch   |
|-------------------------------|-----------------|------------------------|--------|
| `p5.48xlarge` / `p5e.48xlarge` | 8× H100 / H200   | 3.2 Tbps               | x86_64 |
| `p5en.48xlarge`               | 8× H200          | 3.2 Tbps               | x86_64 |
| `p6-b200.48xlarge`            | 8× B200          | 3.2 Tbps               | x86_64 |

**Additional requirements beyond the device plugin setup:**

- Kubernetes 1.34 or later
- GPU driver ≥ 580 (required by `nvidia-dra-driver-gpu`)
- NRI (Node Resource Interface) enabled in containerd on every GPU node — see [Step 1](#step-1-enable-nri-in-containerd)
- `vllm-runtime:<version>-efa` container image (includes AWS EFA installer and NIXL LIBFABRIC plugin)

**Host kernel modules and GPU-Direct RDMA** are the same as the device plugin approach —
see [Step 2 of efa-on-aws.mdx](efa-on-aws.mdx#step-2-verify-host-kernel-modules).

## Architecture

DRANET publishes each node's EFA NICs as a `ResourceSlice` with one device entry per EFA,
annotated with `resource.kubernetes.io/pcieRoot`. The NVIDIA DRA GPU driver publishes a
parallel `ResourceSlice` for GPUs with the same attribute. A `ResourceClaimTemplate` with
a `matchAttribute: resource.kubernetes.io/pcieRoot` constraint instructs the DRA scheduler
to pick one GPU and its co-located EFAs in a single atomic allocation.

At container creation time, DRANET's NRI plugin injects only the allocated EFA NICs into
the container — `/dev/infiniband/uverbs*` device files for exactly the 4 allocated EFAs.
libfabric sees only those 4 devices, even though all 32 node EFAs are visible in
`/sys/class/infiniband/`.

**Why co-location matters for KV cache transfer performance.** GPU Direct RDMA (GDR)
lets an EFA NIC DMA directly into and out of GPU HBM without staging through CPU memory.
When the NIC and GPU share a PCIe root complex, this path is direct. When they do not,
the DMA must traverse the inter-root or inter-NUMA interconnect, adding latency and
reducing effective bandwidth. More importantly, when
all eight GPU workers transfer KV cache simultaneously, co-location guarantees eight
non-contending PCIe paths. Random assignment from the device plugin can serialize
transfers that should be parallel, with the effect compounding at high request concurrency
and showing up primarily in tail latency rather than mean throughput.

To measure the actual benefit for your workload, enable NIXL telemetry (see
[Verification](#verification)) and compare `nixl_bytes_transferred` rate with and
without co-location at your target concurrency.

```
PCIe Root pci0000:44            ← scheduler picks one root atomically
  GPU  gpu-0  0000:53:00.0  NVIDIA H100 80GB HBM3
  EFA  0000:4f:00.0  rdmap79s0   ─┐
  EFA  0000:50:00.0  rdmap80s0   ─┤  injected as /dev/infiniband/uverbs{0-3}
  EFA  0000:51:00.0  rdmap81s0   ─┤
  EFA  0000:52:00.0  rdmap82s0   ─┘
```

<Steps toc={true}>
<Step title="Enable NRI in Containerd" id="step-1-enable-nri-in-containerd">
DRANET requires NRI (Node Resource Interface) in containerd to inject EFA network
interfaces into containers at creation time. Add the following block to
`/etc/containerd/config.toml` on each GPU node, then restart containerd:

```toml
[plugins."io.containerd.nri.v1.nri"]
  disable = false
  socket_path = "/var/run/nri/nri.sock"
  plugin_config_path = "/etc/nri/conf.d"
  plugin_path = "/opt/nri/plugins"
```

```bash
systemctl restart containerd
```

<Info>
NRI must be configured **after** the EKS bootstrap script runs because bootstrap
regenerates the containerd config. If you bake this into a custom AMI, place it in node
userdata after `/etc/eks/bootstrap.sh`, not in the AMI itself.
</Info>

</Step>
<Step title="Install aws-dranet" id="step-2-install-aws-dranet">
The `aws-dranet` DaemonSet discovers EFA interfaces on each node and publishes them as
`ResourceSlice` objects with PCIe topology attributes.

```bash
helm repo add eks https://aws.github.io/eks-charts
helm repo update
helm install aws-dranet eks/aws-dranet --namespace kube-system
```

Wait for the DaemonSet to be ready on all GPU nodes:

```bash
kubectl rollout status daemonset/aws-dranet -n kube-system
```

Verify ResourceSlices are published and carry topology:

```bash
kubectl get resourceslices | grep dra.net
# Expected: one slice per GPU node

kubectl get resourceslices -o json | \
  jq '.items[0].spec.devices[0] | {name, pcieRoot: .attributes."resource.kubernetes.io/pcieRoot"}'
# Expected: {"name": "pci-0000-4f-00-0", "pcieRoot": {"string": "pci0000:44"}}
```

</Step>
<Step title="Install NVIDIA DRA GPU Driver" id="step-3-install-nvidia-dra-gpu-driver">
The DRA GPU driver publishes GPUs as `ResourceSlice` objects and **replaces** the
`nvidia.com/gpu` device plugin. They cannot coexist on the same node.

```bash
# Disable the device plugin in the GPU Operator ClusterPolicy
kubectl patch clusterpolicy cluster-policy --type=merge \
  -p '{"spec":{"devicePlugin":{"enabled":false}}}'

# Wait for device plugin pods to terminate
until ! kubectl get daemonset nvidia-device-plugin-daemonset -n gpu-operator &>/dev/null; do
  sleep 5; done

helm repo add nvidia https://helm.ngc.nvidia.com/nvidia
helm repo update nvidia
helm install nvidia-dra-driver-gpu nvidia/nvidia-dra-driver-gpu \
  --version 25.12.0 \
  --create-namespace \
  --namespace nvidia-dra-driver-gpu \
  --set gpuResourcesEnabledOverride=true \
  --set nvidiaDriverRoot=/run/nvidia/driver
```

**EKS-specific:** The controller ships with a `control-plane` node affinity that does not
apply to EKS (EKS has a managed control plane with no schedulable nodes). Patch it out:

```bash
kubectl patch deployment nvidia-dra-driver-gpu-controller \
  -n nvidia-dra-driver-gpu \
  --type=strategic \
  -p='{"spec":{"template":{"spec":{"affinity":null}}}}'
```

This patch is idempotent — safe to apply on upgrades.

Verify GPU ResourceSlices are published:

```bash
kubectl get resourceslices | grep gpu.nvidia.com
# Expected: one slice per GPU node, each with 8 GPU devices
```

</Step>
<Step title="Container Image" id="step-4-container-image">
Use the `-efa` image variant, which includes the AWS EFA installer (libfabric,
aws-ofi-nccl) and the NIXL LIBFABRIC plugin. DRANET injects the EFA kernel device files
(`/dev/infiniband/uverbs*`) into the container, and the `-efa` image provides the
matching userspace stack.

Pre-built images are published to NGC:

```
nvcr.io/nvidia/ai-dynamo/vllm-runtime:<version>-efa
nvcr.io/nvidia/ai-dynamo/tensorrtllm-runtime:<version>-efa
```

To build your own, see [Step 3 of efa-on-aws.mdx](efa-on-aws.mdx#step-3-build-a-dynamo-efa-image) —
the same `--make-efa` flag and `--target aws` apply.

</Step>
<Step title="Create a ResourceClaimTemplate" id="step-5-create-a-resourceclaimtemplate">
Create a template in each namespace where workers will run. The `matchAttribute`
constraint tells the DRA scheduler to allocate the GPU and EFAs from the same PCIe root:

```yaml
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: gpu-with-efa
  namespace: <your-namespace>
spec:
  spec:
    devices:
      requests:
      - name: one-gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          count: 1
      - name: local-efas
        exactly:
          deviceClassName: efa.networking.k8s.aws
          count: 4          # 4 EFAs per PCIe root on p5.48xlarge
      constraints:
      - requests: ["one-gpu", "local-efas"]
        matchAttribute: "resource.kubernetes.io/pcieRoot"
```

<Info>
The 32-device-per-ResourceClaim limit means you cannot use `allocationMode: All`
(all 32 node EFAs) together with a GPU in one claim. Use `count: 4` — one PCIe root's
allocation — which is also the right number for topology locality.
</Info>

</Step>
<Step title="Configure NIXL Backend" id="step-6-configure-nixl-backend">
NIXL backend selection and env vars are identical to the device plugin approach. See
[Step 4 of efa-on-aws.mdx](efa-on-aws.mdx#step-4-configure-nixl-backend) for the full
table and rationale. The key settings for vLLM disaggregated inference:

```yaml
# Decode worker
- python3 -m dynamo.vllm --model <model>
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_consumer",
    "kv_buffer_device":"cuda","kv_connector_extra_config":{"backends":["LIBFABRIC"]}}'

# Prefill worker
- python3 -m dynamo.vllm --model <model>
  --kv-transfer-config '{"kv_connector":"NixlConnector","kv_role":"kv_producer",
    "kv_buffer_device":"cuda","kv_connector_extra_config":{"backends":["LIBFABRIC"]}}'
```

**Required EFA environment variables** (same as device plugin):

```yaml
env:
  - { name: FI_PROVIDER,                value: efa }
  - { name: FI_EFA_USE_DEVICE_RDMA,     value: "1" }
  - { name: FI_EFA_ENABLE_SHM_TRANSFER, value: "0" }
  - { name: FI_EFA_ENABLE_SHM,          value: "0" }
  - name: LD_LIBRARY_PATH
    value: "/opt/amazon/efa/lib:/opt/amazon/efa/lib64:/opt/aws-ofi-nccl/lib:${LD_LIBRARY_PATH}"
```

</Step>
<Step title="Pod Resource Requests" id="step-7-pod-resource-requests">
Reference the `ResourceClaimTemplate` in the pod spec. Note the differences from the
device plugin approach: no `privileged: true`, no `hostIPC`, no `vpc.amazonaws.com/efa`
in resource limits. The container claims only the GPU explicitly — EFAs are injected
automatically by DRANET's NRI plugin.

```yaml
spec:
  resourceClaims:
  - name: gpu-efa
    resourceClaimTemplateName: gpu-with-efa
  containers:
  - name: main
    image: nvcr.io/nvidia/ai-dynamo/vllm-runtime:<version>-efa
    resources:
      claims:
      - name: gpu-efa
        request: one-gpu     # GPU only; EFAs injected via DRANET NRI
    env:
      # ... NIXL backend and EFA env vars from Step 6 ...
    securityContext:
      capabilities:
        add: [IPC_LOCK]
    # privileged: true is NOT required with DRANET
    # hostIPC: true is NOT required with DRANET
```

</Step>
</Steps>

## Verification

Verification steps 1–5 from [efa-on-aws.mdx](efa-on-aws.mdx#verification) apply
unchanged — check NIXL backend selection, plugin execution, GPU VRAM registration, NIXL
telemetry metrics, and decode-side cache hit rate.

Additionally verify DRANET-specific aspects:

**Confirm the correct EFAs were allocated (co-located with the GPU):**

```bash
kubectl get resourceclaim -n <namespace> -o json | jq -r '
  .items[] | "Claim: " + .metadata.name,
  (.status.allocation.devices.results[] |
    "  driver=" + .driver + " device=" + .device)
'
# Expected: one gpu.nvidia.com device and four dra.net devices per claim
```

**Confirm only the allocated EFAs are accessible inside the container:**

```bash
kubectl exec <worker-pod> -- ls /dev/infiniband/
# Expected: 4 uverbs devices (e.g., uverbs8 uverbs9 uverbs10 uverbs11)
# NOT 32 — DRANET injects only the allocated EFAs as device files

kubectl exec <worker-pod> -- /opt/amazon/efa/bin/fi_info -p efa | grep domain
# Expected: 4 EFA domains matching the allocated devices
```

**Visualize the PCIe topology on a node:**

```bash
# From the dynamo repo root
./deploy/utils/dranet_topo.sh <node-name>
```

Example output confirming each GPU has 4 co-located EFAs on the same PCIe root:

```
PCIe Root: pci0000:44
```

## Known Issues

The libfabric GB200 `fi_mr_reg` EFAULT issue documented in
[efa-on-aws.mdx Known Issues](efa-on-aws.mdx#known-issues) applies equally here —
DRANET changes how EFA interfaces are allocated and injected, but does not change the
libfabric version in the container.

## Common Failure Modes

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| TTFT ~100 s | Silent TCP fallback — NIXL backend not set | Verify Step 6 |
| TTFT ~10 s, 1–5 GB/s | UCX host-staged (no GPU-Direct) | Switch to LIBFABRIC |
| `/dev/infiniband/` missing in pod | NRI not enabled in containerd | Step 1 |
| `fi_mr_reg` EFAULT on GB200 | libfabric CUDA dmabuf bug | See [efa-on-aws.mdx](efa-on-aws.mdx#known-issues) |
| `rdma_write_bytes` shows 0 | Not a failure — EFA SRD uses SEND | Use `nixl_bytes_transferred` metric |

Dynamo benchmarking — three-tier coverage

What exists at each tier, what each covers, and where the request path is unmeasured.

Verified against origin/main @ cd6b63b0cc · working draft, not published guidance

§1The thesis

Layers are not a design principle to adopt up front. End-to-end measurement is primary; a component harness is justified only where e2e provably cannot answer the question. There is exactly one such case, and it is structural rather than a matter of resolution.

In a saturated system, only the bottleneck's capacity is observable. Everything else is idle-waiting, so its ceiling is invisible however finely you instrument. E2E names the current bottleneck; component isolation names the next one. The repo already recorded this: against mock workers the frontend sits at 60–85% of its pinned cores, so frontend optimizations "show flat e2e throughput."

§2The three tiers

What exists at each level, what it covers, whether anything runs it, and how to run it yourself. Nothing measures performance automatically — one tier executes in CI but discards its timings, the other two run only when a person starts them.

No runbook exists for any of the three, and that gap is louder than it looks. README.md cites headline numbers sourced from these suites — 7x and 750x throughput claims at lines 78 and 82, and a results announcement at line 231 — while the repository holds no procedure for reproducing any of them. The claims and the method live in different places, and only the claims are here.

A runbook for an externally-defined suite is not a script. It has to record which submission division or configuration was run, the exact Dynamo revision and deployment, who ran it and on what hardware, and how the published number maps back to a run someone could repeat. Absent that, a cited result cannot be checked, updated, or defended when the suite changes.

Six of the ten execute on every PR, and every timing is thrown away. dynamo-pipeline.yml:169 runs cargo test --all-targets, which includes bench targets; the other four are feature-gated (kv-router-stress, request-trace-bench, block-manager+testing-cuda, testing) and do not build in the default pipeline. Every [[bench]] sets harness = false, so criterion owns the binary, detects test mode, and runs each benchmark once for validation — no sampling, no timing, no comparison.

This was not a decision. --all-targets arrived in a CI consolidation (#8525) where it means "compile and test everything"; the benches were swept in and criterion's test mode is its designed response. The only later commit touching that line (#11853) treats the benches purely as an obstacle to keeping the test command green. Whether to gate on performance was never posed. The accidental upside is real: a bench that panics or stops compiling fails the pipeline, so none can silently bit-rot.

How to get actual numbers

# Time one crate, or one bench
cargo bench -p dynamo-kv-router
cargo bench -p dynamo-llm --bench tokenizer_simple

# Criterion's built-in A/B — reports % change, bootstrap CI, p-value
cargo bench -p dynamo-kv-router -- --save-baseline before
# ... make a change ...
cargo bench -p dynamo-kv-router -- --baseline before
What blocks a gate is the environment, not the benchmarks. Criterion compares against target/criterion/, which is ephemeral in CI — only sccache is configured, so no baseline survives a run. And the workflow documents that "under 12x contention 3/3 parallel shards segfault," while policy_queue.rs already sets .noise_threshold(0.03). First step is a measurement, not a proposal: run cargo bench twice on the same commit on the same runner. If variance exceeds 3%, the gate is not buildable on this infrastructure.

§4What the map says

  • Both micro-level holes sit at the client-facing edges. HTTP ingress and SSE relay have no bench — precisely where a closed-loop client's latency is most sensitive, and precisely what mock workers cannot speak to, since the mocker replaces generation.
  • Tier 1 is weaker than it looks. Every stage reads "strong" at e2e only because the client interval contains it. With no server-side capture in any recipe, that column measures the whole and attributes nothing.
  • KV management inverts the usual pattern — better covered at tiers 2 and 3 than at tier 1, because its metrics exist but are never collected during a benchmark.
  • Coverage tracks authorship, not the request path. Stages are covered where the people building them happened to add benchmarks. Nobody maintains a view of the whole.
  • One dead entry. llm/benches/kv_router_bench.rs yields no bench functions while remaining compile-gated in CI — build cost plus implied coverage that is not there.
Provenance. Tier contents, the 0-of-33 instrumentation count, the port collision between the two frontend harnesses, and the bench inventory were all verified against the tree. Coverage ratings are judgment applied to those facts.

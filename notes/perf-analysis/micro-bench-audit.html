The rubric

Six questions drawn from the procedure. A micro bench is not expected to answer all of them — §2's utilization loop and SLA constraints are e2e concepts — but the first four apply at any tier.

QuestionProcedureWhat a good answer looks like
Load defined?§1Input shape stated and reproducible, not an unexplained constant
Accuracy gated?§1.1Output validated; a wrong-but-fast result fails rather than scores
Target a curve?§2.1Sweeps an axis, so the shape is visible — not one point
Definition of good?§2.4A threshold or baseline that makes a result pass or fail
Data collected?§3Emits more than a duration — throughput, or a named unit
Analysis systematized?§5Programmatic → procedural → agent-runnable

What the audit says overall

  • One bench in ten defines "good." Only policy_queue.rs sets a threshold (noise_threshold(0.03)). The other nine produce a number with nothing to compare it against, which is §2.4 unanswered across the tier.
  • Accuracy gating splits the field cleanly. Four assert correctness; five do not; one is out of scope. Where it exists it is real — tokenizer_dataset counts mismatches and fails on any.
  • Sweeping is the norm, which is the procedure's strongest agreement. Seven of nine criterion benches sweep an axis, so §2.1's "target is a curve" is satisfied by habit rather than by policy.
  • Documentation is the weakest common axis. Five of ten have no module docs at all, so the load they assume is inferable only from code — the same "input distribution is never stated" problem found at Tier 2.
  • Nothing is systematized. §5's ladder — programmatic, then procedural, then agent-runnable — has no rung built at this tier. Results live in whoever ran cargo bench's terminal.

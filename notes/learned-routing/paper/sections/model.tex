\section{The learned policy}
\label{sec:model}

\lc{} takes over the final step of Dynamo's worker selection. Given the eligible candidates for
one request and the signals the router already tracks for them, it scores each candidate with a
linear utility over a handful of features and routes to the highest score. Three constraints
shape the design. It reads only inputs the live router has, so the coefficients tuned in replay
can run unchanged in a live router (\cref{sec:integration}). Its coefficients are shared by all
candidates and its features do not change when the candidate set is duplicated, so one coefficient
vector applies at every worker count, including counts that training never sees
(\cref{sec:set-size}). And one coefficient vector, $\theta = -\basis{0}$, reproduces the default
router, so tuning starts from the status quo and every learned coefficient reads as a deviation
from it (\cref{sec:parity}). The normative specification is \code{FEATURES.md} next to the Rust
code; this section follows it.

\subsection{Router integration}
\label{sec:integration}

% src: WT/lib/kv-router/src/plugins/worker_selection.rs (WorkerScorer, WorkerPicker, factory per
%      partition); WT/lib/router-plugins/builtin/src/learned_choice/mod.rs (policy, provider, register)
In the API of \cref{sec:background}, \lc{} registers under the type string
\code{learned-choice} as one scorer and one picker. The scorer is the default router's own cost
function evaluated at default weights; its output becomes feature 0 (\cref{sec:features}). The
picker (a \code{WorkerPicker}) computes the other features, the utilities and the choice. A
provider deserializes and validates the parameters once at startup and returns a factory that
builds one policy instance per routing partition and worker role; each instance owns its random
generator and its session map.

% src: learned_choice/mod.rs (required_worker_inputs = CACHE | LOAD); features.rs (accessors used)
The picker declares the plugin inputs \code{CACHE} and \code{LOAD}. Per request it reads the
prompt length $\ISL_j$, the request block count $\reqblocks_j$, the block size, the prefix block
hashes (feature set \code{v2} only) and the session identifier, if any. Per candidate
$i \in \cand$ it reads the router's cache estimate (overlap blocks $\ovl_i$ and estimated cached
tokens $\hit_i$), the router's own load tracking (active prefill tokens $\Lpf_i$, decode cost
blocks $\Ldec_i$ including this request's new blocks, active requests $\Lreq_i$) and the
configured KV capacity $\capb_i$ in blocks. Host pins and eligibility always win: a pinned request
goes to its pinned worker, and only eligible workers are candidates.

% src: learned_choice/parameters.rs (deny_unknown_fields, validate); FEATURES.md "Parameters";
%      CR/facts/build_rust.json tests.coverage_map (21 invalid, 5 valid specs);
%      CR/facts/STATE.md audit(build/leakage-features r1) ("67 malformed specs rejected at resolution, 15 valid accepted")
The coefficients are ordinary parameters in the policy YAML (\cref{fig:yaml}), so a new
coefficient vector is a new file rather than a rebuild. Each CMA-ES candidate in training is one
such file, and the file that training selects is the file a live router would load. Parsing is
strict: unknown keys at any level, a vector of the wrong length, a non-finite coefficient, a
negative or non-finite temperature, a context with both pooled and named forms, a context
direction without either, an unknown or repeated context source, and \code{max\_sessions: 0} all
fail at startup with a message naming the problem. The unit tests check 21 invalid and 5 valid
specifications through the same registry path the Python bindings use, and the build audit
checked 67 invalid and 15 valid ones independently.

\paragraph{Cost per decision.}
% src: learned_choice/mod.rs (decide: table.compute, effective_weights, dot per row);
%      choice.rs (Chooser::begin sorts rows by worker); features.rs (set_relative sorts, hash_home);
%      session_map.rs (HashMap + BTreeMap LRU); FEATURES.md "Utility and decision" ("O(N·d + r·d)")
The picker fills an $|\cand| \times \dfeat$ feature table, folds the context into one effective
weight vector ($\rank\dfeat$ operations), takes one dot product per candidate and makes one pass
for the maximum. Before that it sorts the candidates by worker ID, which fixes the visiting order
(\cref{sec:utility}). A decision therefore costs $O(\Nw\dfeat + \rank\dfeat)$ arithmetic plus an
$O(\Nw\log\Nw)$ sort; feature set \code{v2} adds three more sorts and $\Nw$ rendezvous hashes.
Feature 0 is the default scorer's output, which the default router computes anyway. Apart from
scratch buffers that are reused across decisions, the only state is the session map: at most
\code{max\_sessions} entries (default \num{65536}), updated in logarithmic time. The campaign did
not measure the per-decision latency of the Rust policy against \defaultcf{}; the bound above is
from the code.

\paragraph{Excluded inputs.}
% src: FEATURES.md "Excluded inputs"; CR/CONTRACT.md "learned-choice policy" ("Never used")
The policy never reads the request's expected output length, which offline replay fills with the
true output length, so reading it would give the policy future information that no live router
has. It never reads the modeled prefill backlog (the router's \code{PREFILL\_TIME} input) or any
other estimate from \ais{}, the performance model that times the simulated engines; that keeps
the policy independent of the simulator it is trained in, so at runtime it needs nothing a live
router lacks. Two independent audits checked these exclusions.

%      T* = 57th arrival burst, 965 decisions at or before T*, 19 in the T* burst; variants B (OSL x4

%      (tau 0.3), lc_v2_rich, default_seed1, sticky_bounded; control D (OSL x4 from 26 bursts
%      earlier): 210, 214, 282, 286, 286 decisions changed)
The first replayed the first 2,000 requests of a Mooncake trace at $\Nw = 4$ and, from a probe
arrival burst onward, either multiplied every output length by four or deleted the requests.
None of the 965 decisions made up to and including the probe burst changed, for three \lc{}
configurations (\code{v1} with a named context, \code{v1} with a pooled context at $\temp = 0.3$,
and \code{v2}) as well as for the default and sticky-session policies. The same perturbation
started 26 bursts earlier, as a positive control, changed 210 to 286 of those decisions.

The second audit reimplemented the feature map from the specification and matched the policy's
choice in all of \num{18000} random-coefficient trials across the three context forms, detected 30
of 31 deliberately mis-specified feature maps, and found that \num{16000} pairs of decisions that
differed only in excluded inputs never differed in outcome (positive controls changed 272 to 744).

\paragraph{Porting notes.}
% src: CR/audits/build/leakage-features-r1.md F4 (with_exclusive_affinity overrides theta6 live),
%      F1 (structural knobs redefine features 0/3/4/7); learned_choice/mod.rs (.with_exclusive_affinity(true));
%      choice.rs (Chooser::new: fresh entropy without seed); FEATURES.md "Information parity with the live router"
Three properties matter when the YAML leaves replay. First, like the default policy, \lc{} asks
the host to treat an eligible session-affinity target as exclusive. Replay never sets such a
target, but a live router with session affinity enabled pins every later turn of a session to
its target, so the decision never reaches the picker and the learned session coefficient
$\theta_6$ is replaced by hard stickiness. Shipping the learned behavior requires host session
affinity to be off, or accepting hard stickiness in its place. Second, the router settings that
track prefill tokens and assume KV reuse change what features 0, 3, 4 and 7 mean (and the
\code{v2} prefix key), so the live router must keep the values used in training. Third, without a \code{seed} each policy instance draws fresh
entropy, so router replicas do not break ties in lockstep. How replay's information differs from
a live router's (fresher cache state, one cache tier) is discussed in \cref{sec:aisim}.

\paragraph{The default cost it starts from.}
Feature 0 is the default cost function's own cost (\cref{eq:default-cost}, \cref{sec:default-cost})
at the default weights, computed by the default scorer that \lc{} composes as its one scorer.

\Cref{tab:features} defines the eight \code{v1} features, which have been frozen since
calibration began. They are built only from the inputs listed in \cref{sec:integration}.
\begin{itemize}
  \item \textbf{The anchor.} Feature 0 is the default cost divided by the request's block count.
    The division does not change the default's argmin, because $\reqblocks_j$ is the same for
    every candidate. Because the default scorer is composed into the policy, the cases it
    distinguishes (missing cache tiers, unavailable load, untracked prefill) are handled exactly as
    the default handles them, and the host's own score-weight settings do not change feature 0.
    % src: FEATURES.md row 0; tests.rs feature_zero_ignores_the_hosts_score_weights (200 random tables)
  \item \textbf{Cache.} Features 1 and 2 come from the router's accounting estimate. In replay
    the effective overlap equals the device-tier overlap and cached tokens are whole blocks.
    Feature 1 is not clamped; it stays at most 1 whenever the estimate does not exceed the prompt.
    % src: FEATURES.md "Feature set v1" preamble and row 1
  \item \textbf{Load.} Features 3 to 5 come from the router's own request tracking. Feature 4
    divides by the capacity a worker advertises, or by \num{65536} blocks when it advertises none;
    replay advertises the engine's \num{18863} blocks, so the fallback is unused here.
    % src: FEATURES.md row 4
  \item \textbf{Session.} Feature 6 needs state. Replay never sets the router's own affinity
    target, so the policy keeps a bounded LRU map from session identifier to the worker it last
    chose for that session, pinned choices included. It is 0 for every candidate when the request
    has no session or the session is new or evicted.
    % src: FEATURES.md row 6; session_map.rs; tests.rs a_host_pin_wins_and_rebinds_the_session
  \item \textbf{Prompt length.} A request quantity alone, such as $\ISL_j$, is the same for every
    candidate and cannot change an argmax. Prompt length matters only through features that
    combine it with a worker quantity (features 0, 1, 2 and 7; feature 7 is the explicit product
    of prompt length and queued prefill) or through the context term (\cref{sec:context}).
\end{itemize}

%      active_requests_s 0.060309; caveat: tables reconstructed approximately from default@defaults

The features are dimensionless, but they are not on a common scale. On candidate tables
reconstructed from the default router's train replays in the pilot, the within-set standard
deviation ranged from 0.060 (\code{active\_requests\_s}) to 6.6 (\code{default\_logit\_scaled});
the tables are approximate, because replay does not log candidate tables. Training therefore
bounds each coefficient relative to its feature's spread (\cref{sec:space}).

\paragraph{Reading the coefficients.}
% Derivation from eq. (default-cost) and tab:features; no campaign number involved.
With $\theta_0 = -1$, as in M1 and its variants,
$\util_i = -\cdef_i/\reqblocks_j + \sum_{f \ge 1}\theta_f x_{i,f}$, so every term is measured
in default-cost blocks per request block. Two consequences help when reading tuned values. When
the clip in \cref{eq:default-cost} is inactive, that is, when the overlap credit does not exceed
the prompt's blocks plus the queued prefill blocks, $\cdef_i$ contains $-\ovl_i$, so
$\theta_1 x_{i,1} = \theta_1\ovl_i/\reqblocks_j$ adds $\theta_1$ blocks of credit per
overlapping block to the default's one: $\theta_1 > 0$ is
more cache-seeking than the default. And features 0 and 1 are per request block while features
2--7 are not, so at fixed $\theta$ the anchor's differences between candidates shrink as
$1/\reqblocks_j$ relative to the load features: the balance between the default cost and the
learned load terms depends on prompt length by construction.

\paragraph{Feature set \code{v2}.}
% src: FEATURES.md "Feature set v2"; features.rs (LOG_TOKEN_SCALE 1024, SET_RELATIVE floors,

\Cref{tab:features-v2} lists 15 features that \code{v2} appends to the eight of \code{v1}, which
keep their indices. They are used by the M1-v2 arm (\cref{sec:ladder}). They add three things
\code{v1} cannot express. Log-scale load terms make products of loads linear in the utility, so
LMetric's multiplicative rule \citep{zhang2026lmetric} lies inside the model class:
$\theta = -(\basis{8} + \basis{10})$ routes to the minimum of
$(\Lpf_i + (\ISL_j - \hit_i)^+)(\Lreq_i + 1)$, LMetric's product with queued prefill, and
$\theta = -(\basis{9} + \basis{10})$ reproduces the branch's \code{lmetric} port as evaluated
(\cref{sec:ports}) without its hot-spot filter when cached tokens are whole overlapping blocks, as in
replay; a unit test checks
both on \num{1000} random tables. A prefix-hash home indicator marks two hash-chosen candidates per
prompt prefix, the consistent-hash candidate membership of DualMap and Lodestar
\citep{yuan2026dualmap,lim2026lodestar}.
Set-relative load terms make a worker's load count relative to the other candidates; they enter
nonlinearly, because a linear set-relative term would be a no-op (\cref{sec:context}). The ratio
form follows divisive normalization \citep{webb2021normalization}. The product of new prefill and
active requests stands for the prefill--decode interference that two routers model
\citep{jain2024intelligent,srivatsa2025preble}, and the attention term is SMetric's prefill cost
\citep{wang2026smetric}.

The home indicator keys on the prompt prefix only. An earlier version keyed on the session

A later operator decision (contract Amendment A16) admits a third set, \code{v3}, built on a
separate branch and build: the eight \code{v1} features plus five per-worker estimates from \ais{},
in seconds. They are this request's predicted prefill time for its uncached tokens on the worker

undercount context shared by co-resident requests. Arms on \code{v3} form a separate, secondary
league that is not part of the headline (\cref{sec:res-ais}).

\subsection{Utility and decision rule}
\label{sec:utility}

% src: FEATURES.md "Utility and decision"; CR/CONTRACT.md "Utility of candidate i in set S";
%      learned_choice/mod.rs (effective_weights, decide)
For request $j$ with candidates $\cand$ and features $\fvec_i$, the policy scores
\begin{equation}
  \label{eq:utility}
  \util_i = \theta^{\top}\fvec_i + \sum_{\cidx=1}^{\rank} \ctxv_{\cand,\cidx}\, p_{\cidx}^{\top}\fvec_i
          = \weff^{\top}\fvec_i,
  \qquad \weff = \theta + \sum_{\cidx=1}^{\rank} \ctxv_{\cand,\cidx}\, p_{\cidx},
\end{equation}
and decides
\begin{equation}
  \label{eq:decision}
  \temp = 0:\ \ i^{\star} \in \argmax_{i \in \cand} \util_i \ \text{(seeded tie-break)};
  \qquad
  \temp > 0:\ \ \Pr[i^{\star} = i] = \frac{\exp(\util_i/\temp)}{\sum_{i' \in \cand}\exp(\util_{i'}/\temp)} .
\end{equation}
With $\rank = 0$ this is a conditional logit, the simplest member of the generalized
extreme-value family of choice models \citep{train2009gev}: one coefficient vector shared by every
candidate, so the same parameters apply at any $\Nw$. The
context values $\ctxv_{\cand,\cidx}$ are scalars computed once per decision
(\cref{sec:context}); folding them into $\weff$ is what keeps a decision at $O(\Nw\dfeat)$. A
non-finite utility fails the selection rather than routing on it.

% src: FEATURES.md "Utility and decision" (temperature not range-normalized, LR-15);
%      default/picker.rs softmax_sample_index; CR/literature/LESSONS.md LR-05 (flat directions), LR-15 action 3
The temperature $\temp$ is not range-normalized, unlike the default's \code{router\_temperature},
which divides costs by their range before scaling; the two are different parameters. At a fixed
$\temp > 0$ the probability mass on workers other than the best grows with $\Nw$, so a sampled
policy does not mean the same thing at every worker count. M1, M2 and their variants are trained
and evaluated at $\temp = 0$, and a $\temp > 0$ variant is only a conditional robustness extra. At
$\temp = 0$, scaling $\theta$ and the $p_\cidx$ together never changes a decision, which is why
training pins $\theta_0 = -1$ (\cref{sec:space}).

%      hash_home)"); CR/literature/LESSONS.md LR-15 action 3
\Cref{alg:decide} gives one decision in full.

\begin{algorithm}[t]
\caption{One \lc{} decision. Before the call, the host has fixed the eligible set $\cand$ and
  written each candidate's default cost $\cdef_i$ at default weights. The draw discipline is
  \code{one\_draw}; under \code{reservoir} there is no up-front draw, a tie draws once per tied
  candidate during the scan, a sample draws one uniform, and a pin draws nothing, as in
  \defaultcf{}.}
\label{alg:decide}
% Unique hyperref anchors for this algorithm's line numbers (local to the float), so they do not
% collide with alg:train's ALG@line anchors.
\expandafter\def\csname theHALG@line\endcsname{decide.\arabic{ALG@line}}%
\begin{algorithmic}[1]
\Require parameters $\theta$, sources and directions $p_1,\dots,p_{\rank}$, temperature $\temp$;
  per-instance random generator and session map
\Require request $j$; candidates $\cand \ne \emptyset$ with their cache, load and capacity signals
\State \textit{draw} $\gets$ next 64-bit value of the generator \Comment{exactly one per decision}
\State sort $\cand$ by worker ID \Comment{all later loops and sums use this order}
\If{the host pins $j$ to a worker}
  \State $i^{\star} \gets$ the pinned worker
\Else
  \State \textit{prev} $\gets$ the worker the session map holds for $j$'s session, or none
  \State compute $\fvec_i$ for every $i \in \cand$ (\cref{tab:features}); $x_{i,6} = 1$ iff $i = $ \textit{prev}
  \State $\weff \gets \theta + \sum_{\cidx} \ctxv_{\cand,\cidx}\, p_{\cidx}$
  \State $\util_i \gets \weff^{\top}\fvec_i$ for every $i \in \cand$; \textbf{fail} if any is not finite
  \If{$\temp = 0$}
    \State \textit{tied} $\gets \{i \in \cand : \util_i = \max_{i'} \util_{i'}\}$, in sorted order
    \State $i^{\star} \gets$ \textit{tied}$\big[\lfloor \textit{draw} \cdot |\textit{tied}| / 2^{64} \rfloor\big]$
  \Else
    \State \textit{target} $\gets \lfloor \textit{draw}/2^{11} \rfloor\, 2^{-53} \cdot \sum_{i} e^{(\util_i - \max_{i'}\util_{i'})/\temp}$
    \State $i^{\star} \gets$ first $i$ whose running sum of $e^{(\util_i - \max_{i'}\util_{i'})/\temp}$ exceeds \textit{target}
  \EndIf
\EndIf
\If{$j$ has a session}
  \State session map $\gets$ ($j$'s session $\mapsto i^{\star}$); evict the least recently used entry beyond \code{max\_sessions}
\EndIf
\State \Return $i^{\star}$
\end{algorithmic}
\end{algorithm}

\paragraph{Determinism and tie-breaking.}
% src: FEATURES.md "Determinism"; choice.rs module docs; CR/literature/LESSONS.md LR-03;
%      tests.rs one_draw_per_decision_keeps_later_draws_aligned, fixed_seed_reproduces_sampled_decisions
Candidates are visited in worker-ID order, never in the host's unspecified row order, and set
means are summed in that order, so a seeded policy decides identically across processes. Each
policy instance owns one random generator. Under the default discipline, \code{one\_draw}, every
decision consumes exactly one 64-bit draw, whether it ends in a tie, a sample, a unique best or a
pin. Two policies with the same seed therefore stay on the same random stream even after one early
decision differs, which keeps common random numbers aligned across the CMA-ES candidates of a
generation (\cref{sec:noise}); a unit test checks that two policies differing in their first
decision break 40 later ties identically under \code{one\_draw} and not under \code{reservoir}.
The \code{reservoir} discipline reproduces the seeded default picker draw for draw and exists for
parity checks (\cref{sec:parity}). In replay, the harness sets the seed to $\krep + 1$ for
replicate $\krep$ (\cref{tab:notation}).

\subsection{Context terms and the IIA restriction}
\label{sec:context}

% src: WT/notes/learned-routing/campaign/PLAN.md M2 row ("captures interactions between
%      workers at any N"); CR/literature/notes/dcm-context.md §1 (LCL), §2.1 (Lemma 4.3);
%      CR/literature/LESSONS.md LR-05, LR-06
With $\rank = 0$, the policy inherits the conditional logit's independence of irrelevant
alternatives (IIA). At $\temp > 0$,
\begin{equation}
  \label{eq:iia}
  \frac{\Pr[i^{\star} = i]}{\Pr[i^{\star} = i']} = \exp\!\big(\theta^{\top}(\fvec_i - \fvec_{i'})/\temp\big),
\end{equation}
which depends only on the two workers' own features, and at $\temp = 0$ the same holds for which of
the two ranks higher. The exchange rate between features, for example how many queued prefill
tokens one cached block is worth ($\theta_1$ against $\theta_3$), is then the same whether the
other workers are idle or saturated. A router plausibly wants it to change: when every candidate
is busy, waiting behind the worker that holds the prefix may beat recomputing the prefix
elsewhere, and when idle workers exist it may not. This is a hypothesis about the best policy,
not an established property; the drift check described below measures it.

A set statistic added directly to the utility cannot express this. A term that is the same for
every candidate, or a linear set-relative feature such as $x_{i,f} - (\fbar)_f$, shifts every
utility in $\cand$ by the same amount and leaves the argmax unchanged. In the linear context
logit, choice likewise depends only on each item's deviation from the set mean
\citep[Lemma~4.3]{tomlinson2021lcl}. Set information has to change the coefficients instead, and
the context term in \cref{eq:utility} does exactly that: $\weff = \theta + \sum_\cidx
\ctxv_{\cand,\cidx}\,p_\cidx$, so the exchange rate between two features becomes a linear function
of the context values. This is the linear context logit (LCL) of \citet{tomlinson2021lcl},
$\util_i = (\theta + A\,\ctxv_{\cand})^{\top}\fvec_i$, with two changes: the mean feature vector is
replaced by a short vector of named set and request statistics, and $A$ is restricted to one free
column $p_\cidx$ per statistic. It is not their decomposed variant (DLCL), which is a mixture of
logits.

\paragraph{Named rather than pooled.}
% src: FEATURES.md "Context sources", "Guidance for search spaces"; CR/literature/LESSONS.md LR-05
%      (Ko & Li eq. 3 gauge), LR-06 (one-hot pooling); CR/CONTRACT.md "learned-choice policy" (pooled form)
The original contract specified a \emph{pooled} form, $\ctxv_{\cand,\cidx} = q_\cidx^{\top}\fbar$ with
a free $q_\cidx$. The policy still accepts it, but the campaign uses the \emph{named} form of
\cref{tab:sources}, for two reasons. The pooled form has a gauge freedom ($p_\cidx \to c\,p_\cidx$,
$q_\cidx \to q_\cidx/c$, including the sign), a flat direction in which CMA-ES spends budget for
nothing; low-rank choice models have the same non-uniqueness \citep{ko2024attention}. The named
form is linear in the free $p_\cidx$ and has none. And mean-pooling a one-hot feature leaks the set
size: the candidate mean of \code{session\_affinity} is $1/\Nw$ or 0. The named sources are
chosen to avoid that (\cref{sec:set-size}). Two redundancies remain and are handled in the
search space rather than in the policy: when \code{isl\_k} is a source, $\theta_7$ duplicates the
(\code{isl\_k}, feature 3) entry of the context term and is frozen at 0; and on traffic without
sessions \code{is\_first\_turn} is always 1, so its direction duplicates $\theta$. A unit test checks
both context forms against the literal bilinear formula on 100 random tables.

\paragraph{When context should pay.}
% src: CR/literature/LESSONS.md LR-15 (Tomlinson footnote 3; drift check); CR/facts/STATE.md
%      phase2-prep ("4 LR-15 drift runs at 96 evals"); CR/facts/gate.json full_plan.tiers;
%      CR/facts/tierA.json drift (final, with its interpretation)
A context term helps only where the best coefficients drift with the set statistics, and a larger
model that nests a smaller one can still lose to it on a fixed optimizer budget; Tomlinson and
Benson note that LCL, although it nests the conditional logit, can fail to beat it within a
training budget of 500 epochs \citep{tomlinson2021lcl}.
% src: CR/literature/pdfs/dcm-context/tomlinson2021-lcl-dlcl.pdf footnote 3 (pdf p.11): "LCL does not
%      beat MNL within the 500 training epochs"
 The campaign therefore measures drift before
relying on context: M1 is tuned at 96 evaluations separately on L1-only, L3-only, $\Nw{=}4$-only
and $\Nw{=}8$-only train cells, and each result is scored on the others. Cross-play losses beyond
the minimum detectable effect argue for context, and the drifting statistic is the natural
source. The check came out inconclusive. The one cross-play loss above the MDE, 0.087 for the
model tuned on L1 cells evaluated on L3 cells, rests on 3 cells and is 1.3 standard errors from
zero, and a single model tuned on all cells beat every regime specialist on the specialist's own
cells; the specialists, at a quarter of the budget, had moved only a third as far from their start
as the full M1. It is therefore read as an underpowered check with no evidence of drift, and it
was not used to choose M2's sources. Those were fixed before any M2 evaluation:
\code{isl\_k}, because the documented M1 failure axis is prompt length (\cref{sec:gaming}), and
\code{mean\_active\_prefill\_tokens\_k}, the candidate set's prefill pressure.

\subsection{Set-size invariance}
\label{sec:set-size}

% src: CR/cells/SPLIT_MANIFEST.json (train N {4,8}; test adds 2, 16, 32); FEATURES.md "Context sources"
%      (duplication paragraph); CR/literature/LESSONS.md LR-06; tests.rs
%      duplicating_the_worker_set_keeps_features_sources_and_choice (50 random tables, v2, random theta,
%      theta[hash_home] = 0, requests without a session)
Training sees $\Nw \in \{4, 8\}$; the test also scores $\Nw = 2$, 16 and 32 (\cref{sec:splits}).
Two properties make one coefficient vector meaningful at any worker count. First, the
coefficients are shared by all candidates and no feature is a worker's identity, so the policy is
defined for any number of candidates; Lodestar's router uses the same principle
\citep{lim2026lodestar}. Second, every feature and context source is designed to be invariant
under duplicating the candidate set: if every worker is replaced by two identical copies
($\Nw \to 2\Nw$), each candidate's features, every context value and the chosen worker (up to
which copy) stay the same. Means and maxima pass this test. Sums and counts grow with $\Nw$; a mean
of a one-hot feature is $1/\Nw$; a z-score is $\pm 1$ at $\Nw = 2$ whatever the gap; and a
leave-one-out rank fraction of 1 at $\Nw = 2$ becomes $2/3$ after duplication. For that reason
\code{v2}'s below-fraction counts strictly smaller loads over $|\cand|$, which keeps its value
($1/2$ in the same example). A unit test duplicates 50 random
candidate tables under random \code{v2} coefficients and checks that features, sources and the
chosen worker are unchanged. Two features are excluded from the property because they are
relations to particular workers: \code{hash\_home} (its coefficient is zero in the test) and
\code{session\_affinity}, since a copy of a session's previous worker did not serve the session
(the test uses requests without a session).
% src (LR-12): CR/literature/LESSONS.md LR-12 ("Matched per-worker load does not hold the routing
%      regime fixed across N")

Duplication invariance is necessary for transfer across worker counts, not sufficient. At a
different $\Nw$, the same load level produces different per-worker states, so the held-out worker
counts in the test measure transfer directly (\cref{sec:eval}).

\subsection{Parity with the default router}
\label{sec:parity}

% src: FEATURES.md "Parity anchor"; tests.rs theta0_picks_the_default_argmin (2,000 tables; shapes:
%      full, no tier overlaps, no worker loads, prefill untracked; >= 1,500 tie-free; v1 and v2 via YAML),
%      reservoir_tie_break_reproduces_the_seeded_default (500 tables, > 250 tied),
%      feature_zero_ignores_the_hosts_score_weights (200 tables)
With $\theta = -\basis{0}$, $\rank = 0$ and $\temp = 0$, \cref{eq:utility,eq:decision} pick
$\argmax_i (-\cdef_i/\reqblocks_j) = \argmin_i \cdef_i$, the default router's choice. Three unit
tests check this through the same YAML path a deployment uses. On 2,000 random candidate tables,
spread over the four input situations the default scorer distinguishes (complete inputs, no
per-tier cache matches, no load reports, prefill not tracked), \lc{} with \code{v1} and with
\code{v2} picks the default's unique minimum on every table that has one (at least 1,500 are
required). On 500 tables built to tie (more than 250 do), the \code{reservoir} discipline with the
same seed picks exactly what the seeded default picks. And on 200 tables, feature 0 stays at
default weights when the host is configured with other score weights. The one known exception is
two costs that differ by less than the rounding error of the division by $\reqblocks_j$.

In an earlier smoke replay of 1,000 Mooncake requests at $\Nw = 4$, the two disciplines gave the

\subsection{The nested-logit option}
\label{sec:nested}

% src: WT/notes/learned-routing/campaign/PLAN.md ladder (M3: "nested logit over node/DP groups,
%      only if DP > 1 matters"); CR/literature/notes/dcm-context.md §1 (Train 2009 §4.2.1, §4.2.3);
%      CR/literature/LESSONS.md LR-15 (nest parameters drop out of a deterministic argmax: "our corollary";
%      action 4: build M3 from nest-level features); CR/CONTRACT.md "Deployment" (TP2, aggregated)
The plan's third rung, M3, is a nested logit over groups of candidates, such as the data-parallel
ranks of one engine or the workers on one node. A nested logit lets unobserved utility be
correlated within a nest, so IIA holds within each nest but not across nests, and the choice
factors into a choice of nest, driven by the nest's inclusive value, times a logit within the nest
\citep{train2009gev}. Two observations limit its value here. Every worker in this deployment is one
engine with data-parallel size 1, so there are no nontrivial nests. And the nest parameters only
shape the distribution of the unobserved utility; in the deterministic limit the choice is the
argmax of the same systematic utilities, so at $\temp = 0$ they would not change a decision. This
corollary is ours, not Train's. Where nests exist, the useful part of M3 at $\temp = 0$ is
nest-level features, such as the aggregate load of a node or a data-parallel group, added to
$\fvec_i$. M3 was not run.

\subsection{Sticky-session policies}
\label{sec:sticky}

% src: WT/lib/router-plugins/builtin/src/sticky_session.rs (module docs, bound_row, default_choice,
%      policy: cost_scorer(config, config, role) = host weights, with_exclusive_affinity(true));
%      CR/CONTRACT.md "sticky-session policy"; sticky_session tests (reservoir == seeded default
%      without sessions); CR/facts/STATE.md audit(build/leakage-features r1) ("sticky vs contract
%      model 20,000 decisions 0 mismatches")
Session affinity is the simplest alternative to learning a session coefficient, so the campaign
added \policy{sticky-session} (\cref{sec:baseline-policies}), built from the same parts as \lc{}:
the canonical-order chooser with both draw disciplines and the bounded LRU session map. A pinned
request rebinds its session to the pinned worker. Without sessions, \policy{sticky-session} with
\code{reservoir} ties picks exactly what the seeded default picks, and the build audit's
independent model matched it on \num{20000} decisions. In the campaign both modes are tuned
baselines (\cref{sec:baselines}), tuning the default cost's knobs as well.

% src: CR/facts/build_rust.json smoke.checks (lc_affinity_sessions_on_one_worker, sticky_hard_sessions_on_one_worker,
%      default_sessions_spread: 14/20, 54/60, 1/10); smoke.notes ("session_affinity weight 1e6")
\lc{} can express hard stickiness: with $\theta = -\basis{0} + 10^{6}\basis{6}$ a session's later
requests stay on its previous worker whenever that worker is a candidate, and otherwise feature 6
is 0 for every candidate and the default cost decides. This matches \code{hard} mode with default
weights. In a build smoke test, both kept every session on one worker on three session workloads
with 20, 60 and 10 sessions, where the seeded default split 14, 54 and 1 of them across workers.
The \code{bounded} rule is a threshold on relative load, which a linear utility can only
approximate.

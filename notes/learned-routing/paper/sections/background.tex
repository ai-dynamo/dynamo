\section{Background: routing primitives and Dynamo's worker-selection API}
\label{sec:background}

Every routing rule in this study, Dynamo's default, the ported heuristics and the learned policy,
runs through one interface: Dynamo's worker-selection API, a contract between the router
\emph{host}, which owns the request path and the shared state, and a \emph{policy}, which turns that
state into a choice. This section describes the interface as a small set of routing primitives,
writes the default cost function and every other catalog policy in its vocabulary, shows how the
learned policy generalizes them, and lists the major caveats the campaign uncovered along the way.
The vocabulary is the one the code uses; type and method names are those of the router's plugin
API on the campaign branch.
% src: WT/lib/kv-router/src/plugins/worker_selection.rs (module doc: "Public filter, scorer, and
%      picker contracts and their input signals")

% ---------------------------------------------------------------------------------------------
\subsection{The decision and what the host owns}
\label{sec:api-host}

For each request $j$ the host builds a \emph{candidate table}: one row per eligible worker (or
worker and data-parallel rank). Eligibility is the host's: a worker must be in the request's
allowed set, available, not marked overloaded by the host's busy thresholds, routable, and must
satisfy the request's routing constraints. If the request is pinned to a worker, that worker is
the only candidate, and a policy may also ask the host to treat a session-affinity target as
exclusive, in which case an eligible target is pinned the same way. Pins and eligibility always
win over a policy's preference.
% src: WT/lib/kv-router/src/scheduling/filter.rs (RoutingEligibility: allowed_worker_ids,
%      overloaded_worker_ids, available_worker_ids, pinned_worker, affinity_target,
%      routing_constraints; WorkerEligibilityError variants); scheduling/selector/policy.rs
%      (with_exclusive_affinity: "Explicit request pins remain mandatory regardless of this option")

The host also owns the state a policy reads. It keeps the KV index that the engines' cache events
feed and computes each candidate's prefix overlap with the request, per cache tier; it books the
load of every request it dispatches (prefill tokens in flight, decode blocks, active requests); and
it knows each worker's configured KV capacity. A policy owns only its decision and whatever private
state it chooses to keep, such as a random generator, a session map or a sliding window. This split
is what makes a policy portable: the same policy file runs wherever a host can fill the inputs it
declares, including the offline replay used here (\cref{sec:aisim}).

\subsection{Filters, scorers and pickers}
\label{sec:api-components}

A worker-selection policy is an ordered composition of three kinds of component
(\cref{fig:api}).
\begin{description}
  \item[\code{WorkerFilter}] keeps or drops one eligible candidate. Filters run in declaration
    order and can only shrink the set.
  \item[\code{WorkerScorer}] writes one finite, lower-is-better cost for every surviving candidate
    in a single call. The host validates each contribution and adds the contributions of all
    scorers, so scorers compose additively.
  \item[\code{WorkerPicker}] receives the surviving candidates with their total costs and returns
    one row. It may ignore the costs entirely.
\end{description}
% src: worker_selection.rs (WorkerFilter::keep, WorkerScorer::score "Write one finite,
%      lower-is-better contribution", WorkerPicker::pick); selector/policy.rs (ComposedPolicyState:
%      filters, scorers, picker; WorkerSelectionPolicy::new_with_filters)
None of the builtin policies in this study uses a filter; candidate restriction, where a policy
needs it, happens inside its picker. Every builtin policy is therefore ``scorers plus a picker'',
and the interesting differences are in which inputs each reads and whether its choice for one
worker depends on the other candidates.
% src: grep of WT/lib/router-plugins/builtin/src for "impl WorkerFilter for": no builtin filter

\paragraph{Declared inputs.}
A component declares the optional worker signals it needs, as a set of \code{WorkerInputs}, and the
host materializes only the union of what the policy's components declared. Each component then sees
only its own declarations, even when another component of the same policy asked for more.
\begin{description}
  \item[\code{CACHE}] the accounting cache estimate (effective overlap blocks and estimated cached
    tokens), the per-tier overlaps (device, host, disk) and shared-cache hits.
  \item[\code{LOAD}] active prefill tokens, decode cost blocks and active requests, with a flag
    that separates an unobserved worker from an idle one.
  \item[\code{PREFILL\_TIME}] the host's modeled prefill backlog in milliseconds, available only when
    the router runs a prefill-load model (\code{router\_prefill\_load\_model: ais}).
  \item[\code{OCCUPANCY}] host-owned active-request counts.
  \item[\code{PREFERRED\_TAINT}] a cost multiplier from the request's preferred routing constraints.
\end{description}
% src: worker_selection/inputs.rs (WorkerInputs::{CACHE, LOAD, PREFERRED_TAINT, PREFILL_TIME,
%      OCCUPANCY}; WorkerCacheInput::accounting_cache_estimate, device/host/disk_overlap_blocks,
%      shared_hits; WorkerLoadInput::{is_available, active_prefill_tokens, decode_cost_blocks,
%      active_requests}; "Each scorer can access only its own declared optional inputs")
No policy in this study declares \code{OCCUPANCY}, and only the \ais{}-informed variants read
\code{PREFILL\_TIME} (\cref{sec:excluded}).

\paragraph{Request facts.}
Request-level values arrive through \code{WorkerSelectionContext}: the prompt length in tokens and
in KV blocks and the block size; the \emph{prefix hashes}, chained hashes of the prompt's complete
blocks, so that two requests share their first $i+1$ blocks exactly when their entry $i$ is equal;
whether the request is tracked for prefill load; the session context; the session-affinity target
the host resolved; the expected output length, if the request carries one; each worker's
advertised KV capacity; the policy class; the request's priorities; and a per-request router
temperature override. These are the only request facts a policy can use.
% src: worker_selection/context.rs (prompt_tokens, request_blocks, block_size, prefix_hashes,
%      tracks_prefill_tokens, session_context, affinity_target, expected_output_tokens,
%      worker_capacity, policy_class, priority_jump, strict_priority, router_temperature_override,
%      pinned_worker)

\paragraph{The policy catalog.}
A deployment selects policies with a YAML file. Its \code{worker\_selection} block names one
instance per worker role (aggregated, prefill, decode, encode) and lists named instances, each a
catalog \code{type} with a \code{parameters} mapping (\cref{fig:api}). A registered provider for
each type validates the parameters once, at startup, and returns a factory that builds one policy
instance per routing partition and worker role, so every instance owns its state. Unknown types and
malformed parameters fail at startup with a message naming the problem. The name \code{default} is
reserved for the builtin selector.
% src: worker_selection/config.rs (RawWorkerSelectionConfig: aggregated, prefill, decode, encode,
%      instances; "parameters must be a YAML mapping"; "instance name 'default' is reserved");
%      worker_selection.rs (WorkerSelectionPolicyFactory per routing partition);
%      CR/facts/setup.json policy_selection_evidence (unknown type and parameter rejected)
On this branch the offline replay host runs the same catalog; on Dynamo's main branch at the time of
the study, replay rejected catalog policies selected by YAML.

\subsection{Dynamo's default cost function}
\label{sec:default-cost}

% src: WT/lib/router-plugins/builtin/src/default/scorer.rs (score_worker, aggregated branch);
%      knobs in default/parameters.rs. The formula below is the aggregated, prefill-tracking path
%      replay uses; decode-only, host/disk-tier, shared-cache and taint terms are omitted.
In the API's terms, the default router (\defaultcf{} in the catalog) is one scorer and one picker.
The scorer declares \code{LOAD}, \code{PREFERRED\_TAINT} and, unless its overlap credit is zero,
\code{CACHE}, and assigns each candidate a cost in KV blocks:
\begin{equation}
  \label{eq:default-cost}
  \cdef_i = \bpf \max\!\Big(0,\ \frac{\Lpf_i + \ISL_j}{16} - \bov\,\gamma_i\,\ovl_i\Big)
           + \Ldec_i + \breq \Lreq_i,
\end{equation}
where $\ovl_i$ is the candidate's device-tier overlap in blocks, $\Lpf_i$ its active prefill tokens,
$\Ldec_i$ its decode cost blocks (including this request's new blocks), $\Lreq_i$ its active
requests, 16 the KV block size, and
\(
  \gamma_i = \big(1 + \bdecay\,(\Lpf_i - \min_{i' \in \cand}\Lpf_{i'})/(16\,\reqblocks_j)\big)^{-1}
\)
discounts the overlap credit of workers with more queued prefill than the least-loaded one. The
shipped defaults are an overlap credit $\bov = 1$, a decay $\bdecay = 0$, a prefill load scale
$\bpf = 1$ and a decode request weight $\breq = 0$, so the default router minimizes the prefill
blocks the worker would still have to compute plus its decode load. The full scorer also credits
host- and disk-tier hits and shared-cache hits, has a separate branch for decode-only workers, and
multiplies the cost by a preferred-taint factor; none of these enter the aggregated, device-tier-only
setting studied here, in which replay requests carry no taint preferences.
% src (taint): WT/lib/mocker/src/replay/offline/extensions/kv_router/mod.rs (routing_constraints:
%      RoutingConstraints::default(), so preferred_taints is empty and the multiplier is absent)

The picker takes the minimum cost. With a \code{router\_temperature} above zero it instead samples
from a softmax over costs normalized to their range across the candidates, so at positive
temperature the default is set-dependent. Ties are broken at random; on Dynamo's main branch the
generator is unseeded, so identical replays of one cell differ, and this campaign added a
\code{seed} parameter (\cref{sec:caveats}). The picker deliberately ignores the per-request
temperature override, and the default policy asks the host to treat an eligible session-affinity
target as exclusive.

%      #1 (seed), #4 and "Straight-main lane outcomes" #4 (override dropped on purpose, documented,
%      enforced by a test); WT/lib/router-plugins/builtin/src/default.rs (with_exclusive_affinity(true))

\subsection{The ported cost functions as instances of the API}
\label{sec:baseline-policies}

\Cref{tab:api-policies} writes every catalog policy type of the study in the API's vocabulary: its
components, the inputs and request facts it reads, whether its choice for one worker depends on the
other candidates (set dependence), the state it keeps, and the parameters this study tunes. The
pedagogical value of the table is that the policies differ along a few axes only. Most are a single
picker over \code{CACHE} and \code{LOAD}; they differ in how they combine overlap with load
(additive, multiplicative, thresholded or lexicographic), in whether they restrict candidates by a
hash of the prompt prefix, and in whether they compare a worker with the rest of the set.

We describe each rule in the router's terms. For request $j$ with candidates $\cand$, worker $i$
has overlap $\ovl_i$ blocks, $\Lpf_i$ active prefill tokens, $\Ldec_i$ decode cost blocks, $\Lreq_i$
active requests and a configured capacity of $\capb_i$ blocks; a KV block holds 16 tokens. The
ports read the device-tier overlap, which in replay equals $\ovl_i$, so worker $i$'s uncached prompt
is $\max(\ISL_j - 16\,\ovl_i, 0)$ tokens.
% src: FEATURES.md "Feature set v1" ("In replay the effective overlap equals the device overlap and
%      cached tokens are whole blocks"); WT/lib/router-plugins/builtin/src/signals.rs

\paragraph{Round-robin.}
The router's round-robin mode is not a catalog policy: it sends requests to the workers in turn and
reads neither cache nor load. It has no parameters and serves as a floor.
% src: CR/CONTRACT.md "Policy YAML" (round-robin uses router_mode="round_robin", no YAML)

\paragraph{Two-tier.}
% src: WT/lib/router-plugins/builtin/src/two_tier_cost_fn.rs (module doc, DEFAULT_* constants, select_row)
\policy{dynamo-two-tier-cost-fn} ports the thresholds and selection order of the experimental SGLang
router's \code{cache\_aware\_zmq} policy. Instead of one additive cost it applies the first of three
rules that holds. (1)~If the spread of active requests across candidates exceeds
\code{balance\_abs\_threshold} (default 32) and the largest count exceeds
\code{balance\_rel\_threshold} (1.1) times the smallest, it takes the worker with the fewest active
requests. (2)~Otherwise, if the largest overlap $\max_i \ovl_i$ exceeds \code{cache\_threshold}
(0.5) times the request's $\reqblocks_j$ blocks, strictly, it takes the least-loaded worker among
those holding that overlap. (3)~Otherwise it takes the least-loaded worker. Load means $\Lreq_i$
alone, and ties go to the lowest worker ID. The port reads Dynamo's KV-event overlap where the
SGLang router keeps its own approximate cache history.

\paragraph{LMetric.}
% src: WT/lib/router-plugins/builtin/src/lmetric.rs (module doc, Parameters::default, pick)
Following \citet{zhang2026lmetric}, the \policy{lmetric} port routes to
\begin{equation}
  \label{eq:lmetric-port}
  \argmin_{i\in\cand}\ \max(\ISL_j - 16\,\ovl_i,\ 1)\,(\Lreq_i + 1),
\end{equation}
the product of the worker's uncached prompt tokens and its batch size counting this request,
with ties to the lowest worker ID. A product needs no weight between its factors: a weight on
either one scales every candidate's score alike. A hot-spot detector handles a popular prefix
that few workers hold. Requests sharing their first \code{class\_prefix\_blocks} (4) blocks form a
class, and the workers whose overlap covers those blocks hold it. A class is alarmed when the
odds of its share of the last \code{window\_requests} (1000) decisions exceed the ratio of
holders to non-holders. While it is alarmed, once twice as many consecutive class requests as
there are holders would have gone to a holder, later ones go to the best non-holder. The paper
measures the window in time; the port counts decisions so that replay stays deterministic. The
paper's prefill factor also counts the prefill already queued on the worker, $\Lpf_i$; the port omits
that term, a gap that matters for the scope of the headline (\cref{sec:ports,sec:res-fairness}).

\paragraph{Ramjet.}
% src: WT/lib/router-plugins/builtin/src/ramjet.rs (module doc: Helix Ramjet src/router.rs;
%      Parameters::default; credited_affinity; pick)
The \policy{ramjet} port follows Helix's Ramjet load balancer \citep{ramjet}. Each worker scores
its credited prefix affinity minus \code{alpha} (default 4) times its load units, and the highest
score wins, then the deeper raw overlap, then a rotating tie-break. Affinity counts the cached
prefix in 512-token blocks (\code{affinity\_block\_tokens}). With the default \code{relative} basis,
which the port's documentation says Ramjet used in its published comparison with Dynamo, a worker is
credited the warmest candidate's affinity capped at \code{max\_affinity\_blocks} (32), minus how far
it trails that candidate, also capped; differences near the leader therefore survive the cap. A
worker's load units are $\Lreq_i + \Lpf_i/8192$ (\code{load\_unit\_tokens}). Ramjet charges each
in-flight request between 1 and 8 units according to its uncached prompt, but Dynamo exposes load
per worker rather than per request, so the port approximates Ramjet's phase-aware mode.

\paragraph{DualMap.}
% src: WT/lib/router-plugins/builtin/src/dualmap.rs (module doc, Parameters::default, hash_key, pick)
In the \policy{dualmap} port, following \citet{yuan2026dualmap}, two rendezvous hashes of a
prompt-prefix key pick two distinct candidates, so requests that share a prefix share candidates.
A candidate's backlog is $\Lpf_i + \max(\ISL_j - 16\,\ovl_i, 0)$, the prefill tokens it would carry
after taking the request. The request goes to the candidate with more overlap unless that
candidate's backlog would exceed \code{pending\_prefill\_token\_budget} (\num{65536} tokens); then,
and whenever the two overlaps are equal, it goes to the candidate with the smaller backlog. The key
hashes the first \code{hash\_prefix\_blocks} (4) blocks. A prefix is hot when its share of the last
\code{window\_requests} (1000) requests exceeds $2/|\cand|$, and a hot prefix's key doubles in depth,
up to seven times, which spreads its requests over more candidate pairs.

\paragraph{CHWBL.}
% src: WT/lib/router-plugins/builtin/src/chwbl.rs (module doc: KubeAI balance_chwbl.go, SGLang
%      prefix_hash defaults, Mirrokni et al. SODA 2018; Parameters::default; pick)
\policy{chwbl} is consistent hashing with bounded loads \citep{mirrokni2018chwbl}, ported from
KubeAI's balancer with the defaults of SGLang's \code{prefix\_hash} gateway policy. The key is the
prefix hash of the prompt's first 16 blocks (\code{prefix\_tokens}${}=256$), or of all its full
blocks if the prompt is shorter. The worker with the highest rendezvous weight owns the key and takes
the request while $\Lreq_i \le 1.25\,(1 + \sum_{i'\in\cand}\Lreq_{i'})/|\cand|$
(\code{load\_factor}${}=1.25$); otherwise the request walks the other workers in hash order to the
first one within that bound, and returns to the owner if none is. The policy reads no cache state,
so it routes the same with or without KV events.

\paragraph{llm-d precise prefix.}
% src: WT/lib/router-plugins/builtin/src/llm_d/precise_prefix.rs (Weights::default 2:1:1;
%      PrefixScorer, QueueScorer, KvCacheUtilizationScorer); llm_d/mod.rs (MaxScorePicker)
\policy{llm-d-precise-prefix} ports the precise prefix-cache profile of llm-d's inference scheduler
\citep{llmd2025kvcache}. It is the one policy here built from several scorers: a prefix scorer, a
queue scorer and a KV-utilization scorer, weighted 2:1:1, with a picker that takes the highest
total. At the shipped prefix-length weight of 0 it routes to
\begin{equation}
  \label{eq:precise-prefix}
  \argmax_{i\in\cand}\ \
    2\min\!\Big(1, \frac{\ovl_i}{\lfloor \ISL_j/16\rfloor}\Big)
    + \frac{\max_{i'\in\cand}\Lreq_{i'} - \Lreq_i}{\max_{i'\in\cand}\Lreq_{i'} - \min_{i'\in\cand}\Lreq_{i'}}
    + 1 - \min\!\Big(1, \frac{\Ldec_i}{\capb_i}\Big),
\end{equation}
where the queue term is 1 when every candidate has the same $\Lreq_i$, and ties rotate. A nonzero
\code{prefix\_match\_length\_weight} blends the first term with the squared matched length relative
to \code{prefix\_match\_length\_scale\_tokens} (8192), and per-class weights can follow the request's
policy class, which replay never sets.

\paragraph{llm-d optimized baseline.}
% src: WT/lib/router-plugins/builtin/src/llm_d/optimized_baseline.rs (module doc; Parameters::default;
%      TokenLoadScorer; AffinityPicker); docs table ("calibrated by llm-d for Qwen3-32B TP2 on H100")
\policy{llm-d-optimized-baseline} ports llm-d's optimized-baseline profile, a prefix-cache affinity
filter followed by a token-load scorer \citep{llmdsticky}. Workers whose overlap covers at least
\code{affinity\_threshold} (0.8) of the prompt's complete blocks are sticky. Each worker's TTFT is
estimated from its prefill backlog: with \code{ttft\_source: throughput} as
$1000\,\Lpf_i/\num{15928}$\,ms, where \code{peak\_prefill\_tokens\_per\_second}${}=\num{15928}$ is
llm-d's calibration for Qwen3-32B at TP2 on H100, and with \code{ttft\_source: modeled} from the
host's \code{PREFILL\_TIME} backlog. If the best sticky estimate trails the best non-sticky one by
more than \code{max\_ttft\_penalty\_ms} (\num{18000}), stickiness breaks and every worker stays in
play; otherwise only the sticky workers do, or all workers if none is sticky. Among those, the
request goes to the worker with the lowest token load $\Lpf_i + \max(\ISL_j - 16\,\ovl_i, 0)$ (scored
as one minus that load over \code{queue\_threshold\_tokens}, \num{4194304}, capped at 1), and ties
rotate. The port implements llm-d's filter inside its picker, since the API's filters cannot see
the other candidates. The headline league uses the throughput source; the modeled source reads a
performance-model estimate and belongs to the secondary \ais{} league (\cref{sec:excluded}).

\paragraph{Sticky sessions.}
% src: WT/lib/router-plugins/builtin/src/sticky_session.rs (module doc, Parameters, bound_row, policy());
%      session_map.rs (DEFAULT_MAX_SESSIONS = 65_536); CR/CONTRACT.md "sticky-session policy"
Dynamo's live router can pin a session to a worker, but offline replay never sets the router's
affinity target. The campaign therefore added \policy{sticky-session}, which keeps a bounded
least-recently-used map of up to \num{65536} sessions, each mapped to the worker that served its last
request. A request without a session, or the first of its session, takes the default cost
function's choice, built from the router's configured default-cost knobs. In \code{hard} mode a
later request goes to its session's worker whenever that worker is eligible; otherwise it takes the
default choice and the session rebinds. In \code{bounded} mode it also leaves the session's worker
when that worker's active requests exceed \code{load\_factor} (1.25) times the candidates' mean.
The policy mirrors the intent of the live router's session affinity; it is not a port of a published
method. On the flat traces (Mooncake and FAST25) open-loop requests carry no session and
closed-loop requests carry a single-use one, so both modes make the default choice there, apart from
tie-breaking.
% src: FEATURES.md "hash_home" paragraph (closed-loop flat traces get synthetic single-use session IDs)

\paragraph{ThunderAgent.}
% src: WT/lib/router-plugins/builtin/src/thunderagent/{mod.rs, worker_selection/mod.rs}
\policy{thunderagent}'s worker selection is a scorer of each worker's prefill tokens plus its decode
blocks in tokens and a picker that follows the affinity target its paired request classifier sets,
falling back to the lowest cost \citep{kang2026thunderagent}. Its program state lives in the
classifier, a separate kind of plugin that runs before worker selection. Replay runs worker-selection
policies but not request classifiers, so this policy was not evaluated (\cref{sec:excluded}).

\subsection{The learned policy as a generalization}
\label{sec:api-learned}

Each rule above hand-picks a functional form over a few of the declared inputs. \lc{}
(\cref{sec:model}) instead scores every candidate with one utility that is linear in a fixed vector
of features computed from the same inputs, and lets the coefficients be tuned. It is built from the
same parts as the rules it generalizes: the default cost function's own scorer supplies its first
feature, and a picker computes the rest and takes the argmax. Several of the heuristics are points,
or limits, of its parameter space.
\begin{itemize}
  \item $\theta = -\basis{0}$ is the default router (\cref{sec:parity}).
  \item A large positive session coefficient is hard stickiness (\cref{sec:sticky}).
  \item With the extended feature set \code{v2}, $\theta = -(\basis{8} + \basis{10})$ takes the
    argmin of LMetric's product with the queued-prefill term, and $-(\basis{9} + \basis{10})$
    reproduces the branch's \code{lmetric} port without its hot-spot filter
    (\cref{sec:features}).
  \item \code{v2}'s \code{hash\_home} indicator marks the two rendezvous-hashed candidates of a
    prompt prefix, the candidate set of DualMap and Lodestar \citep{yuan2026dualmap,lim2026lodestar}.
  \item Set-relative features and context terms let the comparison between two workers depend on
    the others (\cref{sec:context}), as the queue score of \policy{llm-d-precise-prefix} or the
    relative basis of \policy{ramjet} do by construction.
\end{itemize}
What it cannot express are hard thresholds and lexicographic rules (two-tier's tiers, DualMap's
budget, CHWBL's bound, the optimized baseline's TTFT gate) and history-dependent windows, which a
smooth utility can only approximate. The study's question is whether tuning a generalization
of this kind, with the same budget as each hand-picked rule, finds a better trade on one deployment.

\subsection{Major caveats uncovered by the campaign}
\label{sec:caveats}

Building, calibrating and auditing the study surfaced a number of properties of the API, of the
replay host and of the workloads that can change which policy wins. \Cref{tab:caveats} lists the
major ones with their evidence and status: \emph{fixed} (a fix exists on the campaign branch or
upstream), \emph{follow-up} (recorded for an upstream change, worked around here), or
\emph{inherent} (a property of the setting that this study can only scope). Several of them shape
the results in later sections, and we refer back to them there.

  Fixed: $\Ezero$ aligned with replay's decode context plus a $10^{-6}$ relative tolerance; windows

  Mooncake's arrivals sit on a \SI{3053}{ms} grid, with up to 47 requests per instant, and replay

  Follow-up: the harness spreads arrivals per replicate (\cref{sec:replicates}). \\

  the override. & Intentional upstream; documentation follow-up. \\

  A policy file edited during a replay benchmark run could be reported under a hash that does not
  match the policy that ran. & Fixed in the policy stack (\#15450): the benchmark hashes the file
  once and rejects a change before reporting. \\
13 & \aisim{} prices a mixed prefill pass at the batch mean. &
  Adding a short fresh prompt to a long-context chunk makes the pass cheaper than the chunk alone
  (0.73--0.82$\times$ in four probes), a simulator artifact a search could exploit. &
  Follow-up (not patched, it would change every cached result); the exploit check is negative for
  the headline policy (\cref{sec:gaming}). \\
14 & Catalog policies saw no device-tier overlap in replay on Dynamo's main branch. &
  Replay left the device-tier overlap at zero, which reduces every cache-aware port to load-only
  routing. & Fixed in the policy stack the campaign builds on, with a regression test. \\
15 & A request-count objective can be gamed. &
  The first tuned learned model kept one worker whose requests were all bad
  (\cref{sec:gaming}). & Remedied by a sign constraint on load coefficients; the remaining
  concentration is reported on every learned row. \\

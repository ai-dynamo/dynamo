\section{Introduction}
\label{sec:intro}

\paragraph{The decision.}
A KV-aware router places each request on the worker whose cache already holds the longest prefix
of its prompt, unless that worker is busy enough that recomputing the prefix elsewhere is cheaper.
On the deployment studied here, Qwen3-32B on vLLM with two H100 GPUs per worker, both sides of this
trade are large in the forward-pass performance model's estimates (\cref{sec:simulator}), from which
the times in this paragraph come.
% src: CR/facts/setup.json engine.ais_selected_estimation_mode ("op_level"); the two sources below
Reuse saves prefill: a \num{120000}-token prompt has a
time to first token of \SI{17.8}{s} on an idle worker that lacks its prefix and \SI{56}{ms} on an
idle worker that already holds the first \num{119808} tokens.
% src: CR/audits/setup/determinism-cost-context-r1.md "New: long prefix reuse at 120K"
%      (17,815.54 ms without the prefix; TTFT 56.06 ms with reused_input_tokens 119,808);
%      CR/facts/setup.json long_context.evidence.single_request_ttft_ms_ais."120000"
Load costs decode speed: one decode step at \num{8192} tokens of context takes \SI{15.3}{ms} at
batch size 1 and \SI{109.9}{ms} at batch size 256, so each request placed on a worker slows the
token stream of every other request there.
% src: CR/facts/setup.json ais_active_evidence.decode_step_ms_by_batch_and_context
%      (b1_ctx8192 15.3367 ms, b256_ctx8192 109.935 ms)
Dynamo's default router makes the trade with a fixed weighted sum: the prefill blocks a worker
would still have to compute plus its decode load (\cref{eq:default-cost}). Published routers draw
the line elsewhere. LMetric multiplies a worker's prefill work by its number of running requests
instead of adding the two \citep{zhang2026lmetric}. DualMap hashes a prefix of each prompt to two
candidate workers and picks between them by their current state \citep{yuan2026dualmap}. Lodestar
applies a similar two-choice hash filter under high memory utilization \citep{lim2026lodestar}. SMetric
keeps a session's follow-up turns on the worker that holds its context while that worker can still
meet a latency deadline \citep{wang2026smetric}.
% src: CR/literature/LESSONS.md LR-04 (LMetric P-token x batch; SMetric Fig 13 rule) and LR-07
%      (Lodestar k = 2 filter above 80% cluster memory utilization, pdf p.6; DualMap pdf p.5-6), all
%      VERIFIED; the Lodestar threshold is stated in sec:related.

These rules disagree, and which one wins depends on the traffic. LMetric's authors report that the
product beats linear scores tuned for each workload, Dynamo's among them, on their traces
\citep{zhang2026lmetric}. SMetric's authors put the ideal prefix reuse of those traces at about
50--70\%. On an agentic workload with 82\% ideal reuse and no global KV tier (a cluster-wide KV
store from which any worker can load a cached prefix), which is the setting of our replay, they
measured LMetric 36\% below a tuned linear score in throughput within SLO, because its reuse ratio
fell to 45\% against 74\% \citep{wang2026smetric}. Even the best linear weight moves: LMetric's own
sweep put the best weight on the KV-cache term of a linear score at 0.7 on one workload and 0.55 on
another with a similar access pattern \citep{zhang2026lmetric}.
% src: CR/literature/LESSONS.md LR-07 evidence (SMetric pdf p.6; LMetric pdf p.6, p.11: "the optimal
%      linear KV weight is 0.7 on ChatBot and 0.55 on API"), VERIFIED
An operator has to choose one rule and tune it for a deployment whose traffic may change.

\paragraph{Why the choice is hard to settle.}
Three properties of the problem make the comparison expensive.
\begin{enumerate}
  \item \emph{No per-decision label.} A routing decision changes the cache contents and queues
    that later requests meet, so its quality shows only in aggregate, over minutes of traffic at a
    realistic load. A policy can be scored only on whole episodes.
  \item \emph{Small differences next to workload variation.} A cell is one workload at one load and
    worker count; a segment is a disjoint piece of one trace, which several cells can share. On this
    deployment, the two strongest tuned heuristic types, \policy{ramjet} and
    \policy{llm-d-precise-prefix}, finished within 0.002 of each other in mean validation score over
    cells (a clipped log-ratio of goodput against the untuned default router, the reference for all
    scores), and their order flipped between that cell mean ($+0.0018$, \policy{ramjet} minus
    \policy{llm-d-precise-prefix}) and the mean over independent workload segments ($-0.0087$)
    (\cref{sec:res-selection}). Detecting effects of a few percent needs many cells, replicates and
    independent segments.
    % src: CR/facts/finalists.json rankings_val_k3_10.baseline_pool (ramjet 0.14113, ablabase 0.14054,
    %      llmdpp 0.13934; ablabase is ramjet with a tuned router queue threshold, the same type, so
    %      "heuristic types"); CR/facts/tierBC.json decisions.val_best_baseline ("margin +0.0018 cell mean
    %      (SE 0.0061, 9/14 cells) but -0.0087 segment mean (3/6 segments): a near tie"), the margin of
    %      ramjet, the val-best baseline, over llm-d-precise-prefix (sections/results.tex sec:res-selection);
    %      sections/notation.tex (\piref = default@defaults, shipped parameters, the normalizer of every ratio)
  \item \emph{Regime dependence.} In classical load balancing, how much waiting a dispatch
    policy can avoid depends on the number of servers and on the load
    \citep{vanderboor2022survey}. In a measured study of learned routing for disaggregated
    serving, the learned router tied join-the-shortest-queue at decode width 3, led at width 4
    and tied round-robin again at width 6 \citep{tumkur2026calibrate}. A policy tuned at
    one worker count can therefore lose at another.
    % src: CR/literature/LESSONS.md LR-12 evidence (CtR pdf p.4-5), VERIFIED
\end{enumerate}
Settling the choice by measurement means many long runs. LMetric's authors note that they could
not sweep all configurations because replaying each trace on their testbed consumes substantial GPU
time \citep{zhang2026lmetric}. The tuning in this study replays far more than one trace per
configuration: 66 CMA-ES restarts in total over all tuned policies, learned and heuristic, each of
400 evaluations, every evaluation replaying all 34 train cells on 2 workload replicates, plus
validation. Each train cell simulates 6 to 29 minutes
of serving on 4 or 8 workers, that is, 8 to 16 GPUs.

\paragraph{Approach.}
We first describe the router's worker-selection API (\cref{sec:background}). A routing policy is a
YAML instance of a catalog type that composes filters, scorers and a picker over inputs it declares:
cache overlap, load, capacity and request facts. Dynamo's default cost function, the learned policy,
and the heuristics on our code branch, which are our reimplementations (ports) of published routers
as Dynamo catalog policies, are all such instances, so all of them are configured, tuned and
replayed through the same interface.
% src (ports gloss): sections/baselines.tex sec:baselines ("evaluated as implemented on the study's
%      branch ... the six ported policies as in an unmerged pull-request stack") and sec:ports
For development we then use offline replay (\cref{sec:simulator}). AISimulate provides both the
replay engine (\aisim{}) and the forward-pass performance model (\ais{}) that this study uses.
% src: WT/lib/mocker/src/replay/offline/README.md (event loop and mock engine driver "live in
%      aisimulate_core::replay"); CR/facts/setup.json engine.ais_selected_estimation_mode ("op_level")
\aisim{} runs Dynamo's router, including the builtin policy catalog the live router loads, against
mock vLLM engines in simulated time, and times every forward pass with \ais{} for the configured
model, GPU and parallelism. A \num{2000}-request trace replays in about \SI{1.5}{s} of one CPU
core, and identical inputs replay identically, so competing policies can be compared on common
random numbers.
% src: CR/facts/setup.json replay_cost (about 1.5 s per 2,000-request replay in a fresh process);
%      CR/CONTRACT.md A1 (identical re-runs are deterministic)
In that environment we tune a worker-selection function, \lc{} (\cref{sec:model}). It is a
conditional-logit choice model: it scores every candidate worker with one shared utility, linear
in features the live router already computes, and picks the highest. CMA-ES tunes the coefficients
on windowed goodput, the good requests per second inside a measurement window, where a request is
good if its mean inter-token latency and its end-to-end slowdown over its own uncontended latency
both stay within bounds (\cref{sec:objective,sec:training}); \cref{fig:loop} shows this training
loop. The simulator only trains and scores:
the headline policy reads no performance-model signal, so the YAML file that training writes runs
in the live router unchanged.\footnote{A separately reported set of variants, the \ais{}-informed
  league, may also read \ais{}'s estimates at runtime; it never enters the headline
  (\cref{sec:res-ais}).}

The choice-model form gives three properties the study relies on. It is defined for any candidate
set, so a policy tuned at $\Nw \in \{4, 8\}$ can run at $\Nw = 2$ or 32 and be tested there. It
contains the default router: weight $-1$ on the default-cost feature and 0 on every other feature
reproduces the default router's choice (\cref{sec:parity}),\footnote{In the notation of
  \cref{sec:model}, this is the coefficient vector $\theta = -\basis{0}$.} so training starts from
the status quo and every learned coefficient reads as a change to it. And it is cheap: a decision
costs $O(\Nw\dfeat)$ operations for $\dfeat$ features (8 in the base set, 23 in the extended feature
set the headline policy uses).

\paragraph{How ``better'' is decided.}
The comparison is on equal footing. Every policy, the learned variants and each of 11 tuned
heuristic baselines,\footnote{The 11 are Dynamo's default cost with tuned parameters, the eight
  other catalog types that replay can run (ThunderAgent's routing needs a request classifier that
  replay cannot run), with sticky sessions in two variants, and \policy{ramjet} with a jointly
  tuned router queue threshold (\cref{sec:baselines}).}
% src: CR/facts/finalists.json rankings_val_k3_10.baseline_pool (11 tuned baselines incl. ablabase);
%      sections/baselines.tex tab:baselines; sections/discussion.tex (ThunderAgent's classifier);
%      sections/model.tex tab (M0: the default cost with 5 tuned parameters, the "m0" pool entry)
is one configuration tuned on the pooled train cells with the same CMA-ES budget and restarts and
selected on validation; the best baseline, and by the same rule the headline learned variant, are
chosen on fresh validation replicates (\cref{sec:baselines,sec:eval}).
% src: CR/CONTRACT.md A2.1, A17.2; CR/facts/finalists.json selection
The cells replay five trace sources that differ in where prefix reuse comes from. Requests in the
public Mooncake trace and in two test-only traces from the same project's FAST'25 release share
system prompts \citep{mooncake}; generated multi-turn sessions resend the whole conversation at
every turn; and agent runs (plays) recorded in the public AgentX corpus carry long contexts across
tool calls \citep{agentxtraces}. Seeded transforms rescale prompt length, output length and think
time, and multiply the number of distinct shared system prompts (\cref{sec:workloads}).
% src: sections/simulator.tex sec:workloads (tab:trace-stats, tab:families; Mooncake, FAST25, sessions,
%      AgentX paragraphs); CR/traces/MANIFEST.json roles; CR/cells/SPLIT_MANIFEST.json segments_by_split
%      (FAST25 test only); WT/benchmarks/learned_routing/learned_routing/workloads/transform.py docstring
%      (prefix_root_mult duplicates root segments, "a shared system prompt"; isl_*_mult, osl_mult, think_mult)
The comparison is made once, on a test set frozen with SHA-256 hashes before any tuning. Its 60
cells come from 12 independent workload segments and are held out along six axes: time windows,
agent plays, session seeds, a trace family, transform ranges and worker counts
(\cref{sec:freeze}). The headline is a one-sided exact Wilcoxon signed-rank test over the segments,
registered before training. Reported but not tested are robustness to the SLO scale and definition,
to stale router state (replay gives the router perfectly fresh cache and load information, a live
router does not) and to engine timing, and a check of the ranking on GPUs.

\paragraph{What we found.}
% src: CR/facts/test_results.json headline, report_must_state; CR/facts/fairness_in_class_heuristic.json;
%      CR/facts/robustness.json; CR/audits/phase2-mid/gaming-concentration.md
% prov: "Stated as the final audit allows" (report_must_state MS-RH2-F1-scope)
% src (M1-v2 gloss): sections/model.tex ladder table (M1-v2: features v2, extended);

In AIS-timed simulation, M1-v2, the headline learned router (the extended-feature \lc{} model,
with 23 features, trained under the load-sign constraint of \cref{sec:gaming}), beats the branch's
ported heuristics, each tuned with an equal budget.\lmetricfix{}
The validation-selected best of those baselines is tuned \policy{ramjet}, a port of Helix's Ramjet
load balancer \citep{ramjet} that scores each worker by its cached-prefix affinity minus a multiple of its load.
M1-v2 is ahead of it on 10 of the 12 test segments: all 8 non-session segments and 2 of the 4 session
segments. In all four session segments both policies serve nearly every request well, and the
differences, of either sign, are below 0.001.
% src: CR/facts/test_results.json headline.by_segment (sessions:s6 -0.0000146, s7 -0.0000974,
%      s8 +0.0000453, s9 +0.000594; the 8 other segments +0.0051 to +0.1009), segments_ahead 10;
%      sections/results.tex sec:res-headline families paragraph (sessions at ceiling)
The headline statistic, the segment-mean clipped log-ratio, takes the log
of M1-v2's windowed goodput over \policy{ramjet}'s on each cell and replicate, clips it at
$\pm\log 3$, and averages it within each segment and then over the 12 segments. It is $+0.0316$
(a geometric-mean goodput ratio of 1.032 over segments, a point estimate), with one-sided exact
Wilcoxon $p = 0.0017$ (\cref{sec:res-headline}).
% src: CR/facts/test_results.json headline.geomean_segment_ratio (1.03206)
M1-v2's largest learned term makes uncached prefill more expensive the busier a worker is; zeroing
it costs 0.018 of validation score (\cref{sec:res-coefficients}).
% src: CR/report/REPORT.md section 6; CR/audits/final/refute-headline-2.md (theta21 = 0: -0.0178 on val k0-2)
Among the 17 policies re-run for robustness (the default router, every tuned baseline and five
learned variants), M1-v2 stays first under router-state lag of 10 to \SI{200}{ms} and under four
engine-timing perturbations, and it ranks first under all four alternative definitions of a good
request.
% src: CR/facts/robustness.json set (17 policies), lr14_summary.headline_rank (1 in every condition);
%      CR/facts/test_results.json a14_sla_transfer.variants (rank_of_headline 1 for the four definitions)

Four findings bound this result. First, only the sign is a claim: the effect is below the
pre-registered minimum detectable effect (0.038) and below the spread that the timing perturbations
induce (0.060), both on the scale of the headline statistic. Second, the result is not ``learning
beats every heuristic''. The baseline pool holds the branch's ports as implemented, and its
\policy{lmetric} port lacks LMetric's queued-prefill term; the faithful LMetric rule, with that term,
was not among the tested baselines. Faithful LMetric lies inside the learned model's class.
Untuned, it beats every tuned baseline on validation, and the default cost plus faithful LMetric
reproduces 53--66\% of M1-v2's validation margin over tuned \policy{ramjet}
(\cref{sec:res-fairness}). Third, the gain is a request-count property: a token-weighted goodput is
mixed, and prompts of 32K to 64K tokens see a higher time to first token than under
\policy{ramjet} (\cref{sec:gaming}). Fourth, black-box search games a request-count objective. The
first tuned model drew very long prompts to the worker with the most outstanding prefill; on the
heaviest cell one worker received only such prompts and served none of them within the SLO, while
the hot workers served many short cached requests well. Constraining load coefficients so that load
cannot attract removed this, and every later learned variant runs under that constraint
(\cref{sec:gaming}).

A live check, registered after the simulated test pass and before any finalist live run, with its
cells, policies and noise bar, then served six of the $\Nw = 4$ test cells on H100 GPUs with
Dynamo's router running the same policy files (\cref{sec:live}).

1.00), and M1-v2 leads \policy{ramjet} in each of the five cells where simulation predicts a lead,

\paragraph{Contributions.}
\begin{itemize}
  \item A description of Dynamo's worker-selection API as routing primitives, with the default
    cost function and nine other catalog policy types written in that vocabulary, and the major
    caveats the study uncovered in the API, the replay harness and the workloads, each with its
    evidence and status (\cref{sec:caveats}; full list in \cref{app:caveats}).
  \item \lc{}, a deployable worker-selection policy for Dynamo's router plugin catalog: a
    discrete-choice model over router-observable features that contains the default router as one
    coefficient setting and reads no simulator signal (\cref{sec:model}).
  \item A tuning method for routing policies in replay: CMA-ES on an episodic, windowed goodput
    objective with common-random-number workload replicates, applied with the same budget,
    restarts and selection rule to the learned model and to every heuristic baseline
    (\cref{sec:training,sec:baselines}).
  \item An objective and evaluation protocol for routing studies: goodput defined by inter-token
    latency and end-to-end slowdown over a request's own uncontended latency, measured in a window
    that excludes warm-up and drain; held-out worker counts; a pre-registered test over independent
    workload segments (\cref{sec:setup,sec:eval}); and staged adversarial audits, in which
    independent auditors reviewed each stage before the next began (\cref{sec:audits,app:audits}).
    % src (audits gloss): sections/evaluation.tex sec:audits ("Each stage of the study ended at a
    %      checkpoint that independent auditors reviewed before the next stage started")
  \item Results with their scope: the headline and its strata, worker-count extrapolation, the
    model ladder, the learned coefficients, robustness, the objective-gaming finding and its
    remedy, the secondary metrics that bound the claim, and a pre-registered live GPU check of the
    ranking (\cref{sec:results,sec:gaming,sec:live}).
\end{itemize}

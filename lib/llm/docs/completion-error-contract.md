# Chat and completion HTTP errors

Errors returned by the chat and completion handlers before streaming headers
are sent use a nested `error` object. This applies to custom paths registered
through the same handlers, not just the default endpoint names.

```json
{
  "error": {
    "message": "Invalid request",
    "type": "BadRequestError",
    "param": "reasoning_effort",
    "code": 400
  }
}
```

`param` is null unless an explicitly public, validated field identity reaches
the HTTP boundary. Existing safe structured details remain optional under
`error.details`; private diagnostics must never become the public message or
parameter. The status code and existing overload classification are retained.
The existing 422-to-400 middleware policy also preserves the nested envelope.

## Producing public parameter metadata

Python callers may use `HttpError(400, diagnostic, param="field_name")` or attach
`param` to the explicitly public `InvalidArgument` exception. The field must
be a reviewed top-level schema name, never a request value, model name, path,
or text extracted from an exception message. Syntax validation alone does not
establish that a string is safe to disclose.

The vLLM adapter accepts only a `VLLMValidationError.parameter` found in the
native chat or completion request declarations. Unknown and nested names are
not promoted. Generic duck-typed HTTP exceptions do not gain public metadata
merely by having a `param` attribute. `HttpError` diagnostic text stays private;
the public message for its validated parameter case is `Invalid request`.

Rust producers use `PublicParameter` with
`DynamoErrorBuilder::public_message_with_parameter`. Parameter names are ASCII
identifiers of at most 128 bytes. Metadata is optional inside the existing
public `message` variant; malformed optional metadata is ignored without
destroying the error. Older tolerant readers may drop it, and old writers
produce no parameter. This is not a promise that historical releases return
the new HTTP envelope or metadata.

## Scope and limits

- This changes the former flat error body from the chat/completion handlers.
  Clients parsing the old body must read `error.message` and `error.code`.
- Unrelated endpoints keep their existing error contracts.
- Errors generated by outer middleware or the router before a handler runs
  are not made uniform by this adapter.
- Once an SSE response has started, HTTP status cannot be changed. Existing
  in-stream error handling remains a separate contract; this change does not
  claim full native-server error parity.
- The bounded tests cover serialization, metadata privacy, handler errors,
  middleware envelope preservation, and Python failures both when invoking the
  callable and when polling its async generator. Historical-release runtime
  comparisons and complete OpenAPI route/schema integration are separate work.

# KV DC Relay Protocol

`dynamo_llm::kv_dc_relay::protocol` defines the producer-side wire contract for exporting
data-center-local Relay pools. It contains generated protobuf and tonic types, typed identity
validation, Cuckoo Bucket Images v1 (CBI1), and the descriptor set used by gRPC reflection.

The protobuf package is `dynamo.kvrelay.v1`. `RELAY_PROTOCOL_VERSION` is `1`, and every top-level
request and response carries `RELAY_CONTRACT_MARKER` (`0x4B565231`). The marker makes this schema a
clean break from the retired prototype v1 contract. There is no compatibility mode for the old
model-key streams, flat model bindings, or four-RPC API.

## RPC Contract

The `KvEventRelay` service has five methods:

| RPC | Response |
| --- | --- |
| `GetRelayInfo` | One `RelayInfo` with the protocol version and typed Relay identity. |
| `WatchKvPoolCatalog` | A stream of revisioned, complete `KvPoolCatalogSnapshot` values. |
| `SubscribeKvPool` | An initial CBI1 snapshot followed by contiguous deltas and heartbeats for one exact `KvPoolId`. |
| `SubscribeServingReadiness` | A stream of complete readiness projections for all current model registrations. |
| `SubscribeKvPoolLoad` | A stream of complete load windows for all active pools. |

Streaming requests require a non-empty `subscriber_id` of at most 128 bytes. The server enforces a
separate subscriber limit for each stream type. Pool subscribers also have bounded message and byte
queues.

## Identity

`RelayIdentity` separates two lifecycles:

- `drt_instance_id` identifies the backing Dynamo runtime instance.
- `relay_incarnation` is generated by each `KvDcRelay::start` call and fences in-process Relay
  restarts that reuse the runtime instance.

`KvPoolId` contains:

- an identity composition version;
- an `IndexerDomainId` with cache-semantics and routing-scope digests;
- the `IdentitySource` of each digest;
- the logical `DcId`.

`ProducerIdentity` adds the producer incarnation, layout generation, and complete CKF format. Every
filter, readiness, and load entry carries that producer identity. A consumer must reject identity,
layout, or format drift before applying state.

The serving `DynamoEndpointId` is descriptor metadata. It does not replace or extend `KvPoolId`.

## Catalog and Model Registrations

Each `KvPoolDescriptor` contains one producer, one serving endpoint, and nested model
registrations. The Relay producer emits one canonical base target and any LoRA targets backed by
that model. Each registration has:

- a canonical model ID;
- a `ModelTarget` for either a base model or a Low-Rank Adaptation (LoRA) adapter with its backing
  base model;
- zero or more aliases.

The wire contract does not publish derived model-to-pool or alias-to-model indexes. Consumers build
those indexes, if needed, from the current catalog snapshot. Independent endpoints that advertise
the same canonical model remain independent descriptors and physical pool streams.

`WatchKvPoolCatalog` sends the current complete snapshot immediately. Later updates are also
complete snapshots and may skip revision numbers when watch notifications coalesce. A reconnecting
consumer replaces its local catalog with the first snapshot on the new stream.

## Pool Filter Stream

`SubscribeKvPool` selects one exact `KvPoolId`. The server lazily initializes that pool's
publication hub on the first subscription. Each client receives:

1. One or more `FILTER_UPDATE_KIND_SNAPSHOT_CHUNK` frames covering the complete CKF.
2. `FILTER_UPDATE_KIND_DELTA` frames with contiguous `base_sequence -> sequence` transitions.
3. `FILTER_UPDATE_KIND_HEARTBEAT` frames carrying the current sequence when no delta is emitted
   during the heartbeat interval.

Every `FilterUpdate` repeats the Relay and producer identities. Heartbeats contain no CBI1 payload
and do not advance the sequence. A lagged subscriber is disconnected with `RESOURCE_EXHAUSTED`; it
must open a new stream and install the replacement snapshot before applying deltas.

If snapshot encoding fails or the publication hub encounters an identity, lease, sequence, or
bucket invariant failure, the Relay fences the producer generation. Catalog withdrawal is the
authoritative signal that the generation is no longer publishable.

## Readiness Stream

`SubscribeServingReadiness` sends one complete projection immediately, then sends revisions and
heartbeats. Each entry is keyed by `ProducerIdentity`, canonical model ID, and `ModelTarget` and has
one of these states:

- `READY`
- `UNAVAILABLE`
- `UNKNOWN`

`present_roles` and `missing_roles` explain the evaluated worker topology. LoRA entries also depend
on adapter membership for their backing base model. Readiness is independent of CKF publication;
reopening this stream does not require a pool snapshot.

## Load Stream

`SubscribeKvPoolLoad` sends the current complete load update followed by one update per configured
window. `window_sequence` orders complete windows. Each pool entry reports absolute values,
capacity, and independent observed/expected rank coverage for:

- KV block use;
- active decode blocks;
- active prefill tokens.

An empty `pools` list is a valid idle window. A lagged client receives `RESOURCE_EXHAUSTED` and
reopens only the load stream. Consumers use local receive time for cross-data-center freshness;
`observed_ms` is producer wall-clock metadata.

## CBI1 Payload

`FilterUpdate.payload` carries CBI1 bytes for snapshot chunks and deltas. All multi-byte integers
are little-endian. Identity and gRPC stream sequencing remain in the protobuf envelope; the CBI1
header repeats the CKF format and data-center dimension so a decoder can reject drift before
applying bucket words.

### Header

Every snapshot chunk and delta begins with this 48-byte header:

```text
[0..4]   magic: b"CBI1"
[4..6]   wire_version: u16       (=1)
[6..8]   flags: u16              (1=snapshot chunk, 2=delta)
[8]      fingerprint_bits: u8    (=16)
[9]      slots_per_bucket: u8    (=4)
[10..12] format_version: u16     (=1)
[12..20] seed: u64
[20..28] bucket_count: u64
[28..36] dc_id: u64
[36..44] epoch: u64
[44..48] body_checksum: u32      (low 32 bits of xxh3_64(body))
```

The decoder validates the magic, wire version, flags, checksum, filter format, and bucket bounds.
Before applying the decoded frame, a consumer also verifies that its `dc_id` matches the protobuf
pool identity.

### Snapshot Chunks

A complete CKF lane is encoded as dense `u64` bucket words. Each chunk body is:

```text
[0..4]   chunk_index: u32
[4..8]   chunk_count: u32
[8..16]  bucket_offset: u64
[16..]   bucket words: u64[]
```

One chunk contains at most 512 Ki buckets, or 4 MiB of bucket words. `SnapshotAssembly` accepts only
ordered contiguous chunks from one epoch that cover the declared bucket count.

### Deltas

A delta body contains absolute bucket images:

```text
[0..8]   base_epoch: u64
[8..12]  image_count: u32
for each image:
  [0..4]   bucket: u32
  [4..12]  absolute bucket word: u64
```

Absolute images are idempotent at the bucket level. A delta is capped by `max_delta_images()` so it
cannot exceed `IMAGES_MAX_FRAME_BYTES`; a larger publication becomes a chunked snapshot.

## Consumer Recovery Rules

A consumer keeps catalog, pool filter, readiness, and load as independent state machines:

- Replace catalog and readiness state from the first complete snapshot after reconnecting.
- Do not expose a pool filter until all snapshot chunks are validated and installed.
- Apply a delta only when its Relay identity, producer identity, format, and base sequence match the
  installed generation.
- Retire only the affected pool after a pool stream gap, lag disconnect, malformed CBI1 frame, or
  identity drift.
- Replace load state from the next complete window; load gaps do not invalidate CKF state.

## Feature Gates

The `kv-dc-relay-proto` feature exposes the generated client/messages and pure wire helpers. The
`kv-dc-relay-wan` feature includes the proto feature and enables producer integration plus the mTLS
server. The default `dynamo-llm` build keeps the Relay local-only. `ckf-diagnostics` is independent
and can be combined with either build.

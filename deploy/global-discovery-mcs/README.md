# Multi-Cluster Services registry

This module implements the Kubernetes Multi-Cluster Services API
(KEP-1645, `multicluster.x-k8s.io/v1beta1`) across the member clusters of a
Dynamo Global Router deployment. It has three binaries:

- `mcs-registry`: the registry server. It keeps the clusters, their
  ServiceExports and endpoint sets in memory or in one DynamoDB table
  (replicated as a Global Table across regions), merges the exports of a
  Service from every cluster into one ServiceImport, and serves the
  `dynamo.mcs.v1` API over gRPC and REST.
- `mcs-controller`: runs in every member cluster. It registers the cluster
  with the registry, writes the cluster's ServiceExports and their
  endpoints, and materialises the ServiceImports of the clusterset with
  their derived Services and EndpointSlices.
- `mcs-admin`: inspects a store, deletes a cluster, and creates the
  DynamoDB table.

The Global Discovery Service (`lib/global-discovery-service`) reads the
EndpointSlices that `mcs-controller` imports; see
[How the Global Discovery Service reads the imports](#how-the-global-discovery-service-reads-the-imports).

The module was ported from an internal codebase, without its pool layer:
the Global Discovery Service derives pools from imported EndpointSlices.
The port is tracked in #17601.

Module: `github.com/ai-dynamo/dynamo/deploy/global-discovery-mcs`.

## Build and test

Run from this directory. Tools install into `bin/` at the versions pinned in
the Makefile.

```bash
make build             # bin/mcs-registry, bin/mcs-controller, bin/mcs-admin
make test              # unit and envtest suites with -race; fails below 85 percent coverage of ./internal/...
make envtest           # the mcs-controller envtest suite alone
make test-integration  # DynamoDB store and mcs-admin against amazon/dynamodb-local (Docker)
make lint              # golangci-lint, integration tests included
make proto             # after editing api/proto; proto-check fails on drift
make manifests         # after changing +kubebuilder:rbac markers
make sync-crds         # after changing the sigs.k8s.io/mcs-api version
make check             # check go mod tidy, regenerate everything and fail on a dirty tree
make e2e              # end-to-end test on three kind clusters; see "End-to-end test" below
make docker-build IMG=global-discovery-mcs:dev
make help
```

`make test-integration` starts `amazon/dynamodb-local` through
testcontainers-go and skips when Docker is unreachable. It takes
`DOCKER_HOST` from the current docker context (colima, Docker Desktop);
`MCS_TEST_DYNAMODB_ENDPOINT=http://localhost:8000` uses a running endpoint
instead.

The image built from `Dockerfile` holds `/mcs-registry` (the entrypoint),
`/mcs-controller` and `/mcs-admin`, runs as user 65532, and ships the CRDs
in `/opt/global-discovery-mcs/crds`. Its `linter` and `tester` stages run
golangci-lint and `make test`.

## End-to-end test

`make e2e` builds the image, creates three kind clusters (hub, a and b) with
distinct pod and service subnets and static routes between their nodes,
installs the Helm chart (the registry in the hub, a controller in each
cluster) and runs three phases: registration, export and import (phase 1);
endpoint updates, a `v1alpha1` ServiceExport, a conflicting export, lease
expiry and deletion (phase 2); and the Global Discovery Service in
`--pool-discovery mcs` reading the imports (phase 3, which builds
`container/Dockerfile.global-discovery-service`). It prints a pass and fail
summary and exits non-zero on a failure.

```bash
make e2e E2E_PHASES="1 2 3"
make e2e E2E_PHASES=2 E2E_KEEP=always E2E_SKIP_BUILD=1   # iterate against kept clusters
make e2e-down
```

`kind` installs into `bin/`. The Docker host needs `fs.inotify.max_user_instances`
of at least 256 for three clusters (colima: `colima ssh -- sudo sysctl -w
fs.inotify.max_user_instances=512`). `test/e2e/README.md` lists the
settings and every assertion.

## Run locally

```bash
go run ./cmd/mcs-registry --region=local --log-level=debug
```

The registry listens on `:9090` (gRPC), `:8080` (REST) and `:9091`
(admin). Register a cluster, export a Service with one ready endpoint and
read the merged import:

```bash
curl -sX PUT localhost:8080/v1/clustersets/dev/clusters/a -d '{"region":"local"}'
curl -sX PUT localhost:8080/v1/clustersets/dev/clusters/a/exports/llm/frontend -d '{
  "spec": {"type": "SERVICE_TYPE_CLUSTER_SET_IP", "ports": [{"name": "http", "port": 8000}]}}'
curl -sX PUT localhost:8080/v1/clustersets/dev/clusters/a/exports/llm/frontend/endpoints -d '{
  "endpoints": [{"addresses": ["10.0.0.5"], "conditions": {"ready": true},
                 "attributes": {"targetRef.name": "frontend-0"}}]}'
curl -s 'localhost:8080/v1/clustersets/dev/imports?includeEndpoints=true'
curl -sN localhost:8080/v1/clustersets/dev/imports:watch
curl -s localhost:9091/readyz
```

A write without a generation asks the registry to assign one, which suits
curl; controllers and clients send their own.

Run the controller out of cluster against the current kubeconfig and the
local registry:

```bash
kubectl apply -f config/crd/bases
go run ./cmd/mcs-controller --registry-url=http://localhost:9090 \
  --registry-allow-insecure-http --clusterset-id=dev --cluster-id=a --region=local \
  --leader-elect=false --metrics-bind-address=:18080 --health-probe-bind-address=:18081
```

## mcs-registry flags

Every flag has an `MCS_` environment fallback named after it, for example
`MCS_REFRESH_INTERVAL` for `--refresh-interval`; a flag on the command line
wins.

| Flag | Default | Meaning |
| :---- | :---- | :---- |
| `--grpc-listen-address` | `:9090` | gRPC listener (h2c, or TLS) |
| `--http-listen-address` | `:8080` | REST gateway listener |
| `--admin-listen-address` | `:9091` | `/metrics`, `/healthz`, `/readyz`, `/debug/pprof` |
| `--region` | `$AWS_REGION` | Region reported by `GetServerInfo` and used by the DynamoDB store; the flag wins, then `MCS_REGION`, then `AWS_REGION` |
| `--store` | `memory` | `memory` or `dynamodb` |
| `--dynamodb-table` | `global-discovery-mcs` | DynamoDB table |
| `--dynamodb-endpoint` | none | DynamoDB endpoint override, for dynamodb-local |
| `--refresh-interval` | `2s` | Full reload of each clusterset from the store |
| `--lease-eval-interval` | `1s` | Lease evaluation without a store read |
| `--clusterset-discovery-interval` | `30s` | Listing of the store's clustersets |
| `--lease-skew` | `2s` | Clock skew allowance before a lease expires |
| `--retention` | `24h` | How long the records of an expired cluster are kept |
| `--compaction-interval` | `10m` | Interval of the retention cleanup |
| `--bookmark-interval` | `5s` | Interval of watch bookmarks |
| `--watch-history` | `10000` | Events kept per clusterset for resume |
| `--watch-queue-size` | `1024` | Per-watcher queue; an overflowing watcher is re-snapshotted |
| `--max-watchers` | `5000` | Concurrent watch streams per replica |
| `--max-message-bytes` | `4194304` | gRPC message size limit |
| `--advertise-endpoints` | none | JSON list of `{"region","grpcUrl","httpUrl","primary"}` returned by `GetServerInfo` |
| `--tls-cert-file`, `--tls-key-file` | none | TLS on the gRPC and REST listeners |
| `--shutdown-drain` | `5s` | Time reported not ready before the replica stops serving |
| `--shutdown-timeout` | `25s` | Graceful stop of the gRPC and REST servers |
| `--otel-enabled` | `false` | OTLP tracing configured by the `OTEL_*` environment |
| `--log-level` | `info` | `debug`, `info`, `warn` or `error` |

The gRPC server pings idle connections after 60 s (timeout 20 s) and
accepts client pings every 10 s or more, also without active streams.

Operations:

- Readiness (`/readyz` and the gRPC health service) requires a store ping,
  one completed refresh of every clusterset the store knows, and a view
  younger than three refresh intervals.
- On SIGTERM the replica reports not ready, drains for `--shutdown-drain`,
  ends watches with `UNAVAILABLE SHUTTING_DOWN`, stops REST and gRPC within
  `--shutdown-timeout` and flushes traces. Set
  `terminationGracePeriodSeconds` above drain plus timeout.
- Metrics are `dynamo_mcs_registry_*`: clusters, exports, endpoints and
  ServiceImports per clusterset, lease expirations, watchers, watch events,
  resyncs and rejections, view refresh duration, failures and age, store
  request duration and conditional failures, compaction deletions, build
  info, and the gRPC server metrics `dynamo_mcs_registry_grpc_server_*`.
- Logs are zap JSON; every call logs `finished call` with the method, code,
  duration, peer, clusterset, cluster, namespace, name and `x-request-id`.
- Traces: one otelgrpc server span per call with `dynamo.clusterset` and
  `dynamo.cluster.id`, a client span per store call (`mcs.store.<op>`) and
  spans for refreshes (`mcs.view.refresh`) and compaction
  (`mcs.view.compact`). The REST gateway forwards `traceparent`,
  `tracestate`, `baggage` and `x-request-id`.

## mcs-admin

```bash
mcs-admin create-table --table=global-discovery-mcs --region=us-east-1
mcs-admin --dynamodb-table=global-discovery-mcs --region=us-east-1 create-table
mcs-admin --store=dynamodb --region=us-east-1 describe
mcs-admin --store=dynamodb --region=us-east-1 describe --clusterset=prod --output=json
mcs-admin --store=dynamodb --region=us-east-1 delete-cluster --clusterset=prod --cluster=use1-a --yes
```

The store flags before the command (`--store`, `--dynamodb-table`,
`--dynamodb-endpoint`, `--region`, `--lease-skew`) and their `MCS_`
fallbacks match `mcs-registry`. `describe` lists the clusters, exports and
endpoint sets of each clusterset. `delete-cluster` names what it would
delete and exits with status 2 without `--yes`. Both default to
`--store=memory`, which opens an empty in-process store, so they print a
warning to stderr and find nothing; use `--store=dynamodb` to inspect a
deployment. `create-table` creates the table, enables TTL and
point-in-time recovery, and only checks an existing table; against
dynamodb-local pass `--endpoint=http://localhost:8000 --pitr=false`
(`docs/storage.md`). Its `--table`, `--region` and `--endpoint` default to
the store flags `--dynamodb-table`, `--region` and `--dynamodb-endpoint`,
so `mcs-admin --dynamodb-table=Y --region=X create-table` creates table Y
in region X. The precedence is the subcommand flag, then the store flag,
then its `MCS_` environment variable, then the built-in default (for the
region, `AWS_REGION`, then the shared AWS configuration). `--help` on a
command prints its flags and exits 0.

## How the Global Discovery Service reads the imports

The Global Discovery Service runs with `--pool-discovery mcs` in a cluster
where `mcs-controller` imports the clusterset. It does not call the
registry; it watches the EndpointSlices the controller writes:

- It selects imported slices by the label
  `multicluster.kubernetes.io/source-cluster` and groups them by
  `multicluster.kubernetes.io/service-name`. The controller writes one set
  of slices per source cluster, the local cluster included, so every
  cluster's endpoints of a Service are told apart. Each slice also carries
  `topology.kubernetes.io/region` when the source cluster registered a
  region. The service reads it as the pool's region once ai-dynamo/dynamo#17604
  lands; until then a pool's region is its cluster id.
- A pool is a Service named `<DGD name><--pool-service-suffix>` (default
  `-pool-relay`) in a source cluster; the Global Router's replicas are the
  ready endpoints of the Service given by `--router-namespace` and
  `--router-service`.
- Only Ready endpoints count. The controller copies the `ready`, `serving`
  and `terminating` conditions of every exported endpoint.
- Ports are looked up by name and TCP protocol (`--router-port-name`); the
  controller keeps the port names of the merged import on every slice.
- A router replica is named after its pod (`<cluster>/<pod>`), and the
  service groups a relay pod's addresses by pod before binding one relay
  per pool. `mcs-controller` exports the `targetRef` kind, name and UID of
  every endpoint as the attributes `targetRef.kind`, `targetRef.name` and
  `targetRef.uid`, and the importer sets the imported endpoint's
  `targetRef` from them (kind Pod when none was exported), so the pod name
  survives the trip across clusters. An endpoint without one is named after
  its address.

Export the PoolRelay and Global Router Services by labelling them
`dynamo.nvidia.com/mcs-export: "true"` (or by creating their
ServiceExports), in every cluster that runs them.

## Follow-up

Open work after the port is tracked in #17601: exporting `targetRef.namespace`
so imported targetRefs carry a namespace.

When a registry with the memory store restarts, importers receive an empty
snapshot and garbage-collect every import at SNAPSHOT_END until the
controllers re-register (up to TTL/3 later); deferring the garbage
collection of an empty snapshot from a new view epoch would avoid the gap.
